# Architecture: blog block engine, chart, lint

Detail moved out of CLAUDE.md.

- `services/blog_blocks.py` (MON-255, MON-256, MON-257, MON-264) - block engine of a blog post: a registry of blocks with two renderers each and eight public functions (`list_block_templates` came with MON-264 and is described with `BlockDefinition` below; `collect_block_assets(markdown) -> BlockAssets` and `find_block_issues(markdown) -> list[BlockIssue]` came with the graphic blocks of MON-257, `iter_source_lines(markdown) -> list[SourceLine]` with the post lint of MON-262; these three are described at the end of this entry): `render_post_html(markdown) -> str` (the post page), `render_post_markdown(markdown) -> str` (the markdown form of the same post, for the `.md` twin), `strip_block_markers(markdown) -> str` (the source without block markers: the `> [!TYPE]` line of a known alert and the `:::` lines of a closed container, the `:::details Title` opening included, with fenced code left alone; `blog.py` runs it before `extract_summary` for the list teaser and the meta description, `blog_ai.py` for the frontmatter `description`) and `extract_structured_data(markdown) -> dict` (MON-256, described below). None of them ever raises, whatever the input string: an empty post (after `strip()`) is an empty string from both renderers, and an unexpected error is logged and answered with the escaped source in one `<p>` (HTML) or the source unchanged (markdown, `strip_block_markers`). `BlockDefinition` is a frozen dataclass (`name`, `to_html`, `to_markdown`, and since MON-264 `syntax_template: str = ""`) whose `__post_init__` raises `TypeError` when either renderer is not callable. Every entry of `TEXT_BLOCKS` and `CONTAINER_BLOCKS` has a non-empty `syntax_template`: valid source that `render_post_html` renders as that block (a container template starts with `:::<name>` and ends with a `:::` line). A seventh public function, `list_block_templates() -> list[dict[str, str]]` (MON-264), returns `{"name": <registry key>, "template": <syntax_template>}` in the order `[*TEXT_BLOCKS, *CONTAINER_BLOCKS]`, read from the registries at call time (not from a copy); it feeds the "Wstaw blok" menu of the dashboard wiki editor, so a new block needs a template to show up there. `TEXT_BLOCKS` (key == `definition.name`) holds `callout`, `quote`, `figure`, `code`, `heading`, `footnotes`, all sharing one `to_markdown` that returns the source unchanged; `CONTAINER_BLOCKS` holds 13 containers: the 4 graphic ones of MON-257 (`chart`, `diagram`, `terminal`, `graphic`, described at the end of this entry) and 9 structural ones (MON-256): `faq` (each `### Question` heading opens an item, the markdown below it is the answer; the headings are consumed, so they produce no `<h3>` and take no heading slug), `steps` (an ordered list; a bold start of an item is the step name, the rest is its body, and an item without a bold start has no name), `stats` (list items `- **value** - label`), `compare` (a markdown table; the optional attribute `highlight="N"` marks column N, 1-indexed, and a non-number or an out-of-range value means no highlight), `details` (the title is the rest of the opening line, `:::details Title`, and an empty title becomes `Szczegóły`), `gallery` (markdown images, in one paragraph or in separate ones), `video` (a video address in the first line, then a markdown description), `cta` (a paragraph with exactly one link, which becomes the button) and `glossary` (list items `- **term** - definition`). Container parser: an opening line `:::type` with optional `key="value"` attributes and a closing `:::`, no nesting (a `:::type` line inside a container is plain text) and never inside a fenced code block. Dispatch (MON-256): `_resolve_containers` and `_CONTAINER_OPEN` are unchanged; a new shared parser, `_split_containers`, cuts the source into runs of plain lines and closed containers of a type registered in `CONTAINER_BLOCKS` (type, rest of the opening line, inside lines) and serves the HTML renderer, the markdown renderer, `strip_block_markers` and `extract_structured_data`; the plain runs, closed containers of an unknown type included, still go through `_resolve_containers`. For HTML the renderer of a registered type is called first and its result is parked on a placeholder token (`blogblock{nonce}c{i}c`, next to `blogblock{nonce}n{i}n` of the text blocks) before the rest of the post is sanitized. `:::details Title` has an opening pattern of its own, because `_CONTAINER_OPEN` accepts only `key="value"` attributes. An unknown type still renders its inside as ordinary markdown with the `:::` lines dropped; an unclosed container renders the whole text as ordinary markdown with the `:::type` line visible. A registered container with a wrong structure or an empty inside (e.g. `gallery` without images, `cta` with no link or with two) degrades the same way: its inside as ordinary markdown, no block wrapper, no error; a renderer that raises does not break the page either. Container HTML uses fixed `blog-*` classes only (`blog-faq` with `<details class="blog-faq-item">`, `<ol class="blog-steps">`, `blog-stats`, `blog-compare` with `blog-compare-highlight` on the cells of the marked column, `<details class="blog-details">`, `blog-gallery` with `<figure class="blog-gallery-item">` and `loading="lazy"`, `blog-video`, `blog-cta` with `blog-cta-button`, `<dl class="blog-glossary">`). `:::video` (MON-256): the address is parsed with `urllib.parse.urlsplit`, must be `https` and its host must equal one entry of an exact allowlist (`youtube.com`, `www.youtube.com`, `m.youtube.com`, `youtu.be`, `vimeo.com`, `www.vimeo.com`, `player.vimeo.com`; host comparison, never a substring). The server never emits an `<iframe>` and no thumbnail from a video host, so the page makes no request to YouTube or Vimeo before a click: it renders `<div class="blog-video" data-provider="youtube|vimeo" data-video-id="ID">` with a plain link to the original address (`blog-video-play`, `target="_blank"`, `rel="noopener noreferrer nofollow"`) and the description. `static/blog/blocks.js` builds the iframe on click (`https://www.youtube-nocookie.com/embed/<id>` or `https://player.vimeo.com/video/<id>`) from `data-provider` and `data-video-id` only, re-validating the id and never reading `href`; without JS the link stays. An address outside the allowlist renders the description plus, for `http`/`https` only, a plain link, with no `blog-video*` class and no `data-video-id`. Text blocks in HTML: a GitHub alert in the first line of a quote (`[!NOTE]`, `[!TIP]`, `[!IMPORTANT]`, `[!WARNING]`, `[!CAUTION]`, `[!TLDR]`, `[!QUOTE]`, marker case-insensitive) becomes `<aside class="blog-callout blog-callout-<type>">` with a Polish label in `<p class="blog-callout-title">` (`quote` has no label), and an unknown marker stays a plain `<blockquote>`; a quote whose last line is `-- Name, role` becomes `<figure class="blog-quote">` with `<figcaption>`, without that line it stays a plain `<blockquote>`; an image with a title that is the only content of its paragraph becomes `<figure class="blog-figure">` with `<figcaption>`, `loading="lazy"` and `decoding="async"`, while an inline image or one without a title stays `<img>` in `<p>`; every fenced code block is wrapped in `<div class="blog-code">` with a `blog-code-header` holding the copy button (`blog-code-copy`), plus a `blog-code-title` when the fence has `title="..."`, and the language as `language-*` on `<code>`; H2-H4 get an `id` from the slug of their text (lowercase, Polish letters transliterated to ASCII, `sekcja` for an empty slug), duplicates suffixed `-2`, `-3`, a slug starting with `blog-` prefixed with `post-` (so a heading can never take a footnote id), and H1, H5, H6 get none; footnotes (`[^label]` with a `[^label]: text` definition) are numbered in order of first reference and render as `<sup>` links, the first reference of each carrying `id="blog-fnref-N"`, plus a closing `<section class="blog-footnotes">` with `<li id="blog-fn-N">` and a back link, while a reference without a definition stays plain text. `render_post_markdown` returns all of these text blocks verbatim and strips the `:::` lines of a closed container; the inside of a registered container is kept unchanged and preceded by a one-line label and a blank line (MON-256): `**FAQ**`, `**Kroki**`, `**Statystyki**`, `**Porównanie**`, `**<Title>**` for `details` (`**Szczegóły**` without a title), `**Galeria**`, `**Wideo**`, `**Wezwanie do działania**`, `**Słownik**`. The four graphic containers have no fixed label; their markdown form is listed with them below. An empty inside gets no label, and no line of the result starts with `:::` outside a fenced code block. `extract_structured_data(markdown) -> dict` (MON-256) always returns `{"faq": [...], "steps": [...], "videos": [...]}` (empty lists when the post has no such block) and never raises: `faq` items are `{"question", "answer"}` as text without markdown or HTML markup, `steps` items are `{"name", "text"}` (`name` is an empty string for an item without a bold start), `videos` items are `{"url", "description"}` for allowlisted addresses only. Containers inside fenced code are skipped (same parser) and `glossary` is deliberately left out. Nothing in `src/` calls it yet: it is the input for the AI-layer ticket (JSON-LD). Security model: there is ONE `nh3` pass and it runs on the author's content only. `render_post_html` first renders registered containers (all author markdown in them goes through `_clean`, the same `nh3` call: the block bodies, and through `_inline`, which is `_clean` minus the wrapping `<p>`, also the short values, i.e. a FAQ question, a step name, a stat value and label, a glossary term and definition, so inline markdown works in them; `html.escape` covers what is not markdown: the `details` title, the video address and id, and the `src`/`alt` of a gallery image and the `href` of the CTA button, both re-escaped after being read back from cleaned HTML; the tag and attribute allowlists in `services/wiki.py` are not widened for them, so `details`, `summary`, `dl`, `iframe` or `class` written by the author are still removed, inside a container too), then cuts fenced code, quotes and footnote definitions out of the source and parks each as a placeholder token carrying a per-render random nonce (so a post cannot fake a block), then renders the rest to HTML and cleans it with `nh3` using the tag list and URL schemes imported from `services/wiki.py` (`_PUBLIC_ALLOWED_TAGS`, `_PUBLIC_URL_SCHEMES`: `http`, `https`, `mailto`) and its own attribute list (`href`, `title` on `a`; `src`, `alt`, `title` on `img`), which has no `class` and no `id`. The order after that is fixed: captioned figures are built on the cleaned HTML, then the tokens are replaced by block HTML, and only then heading anchors and footnote references are added over the whole result, so headings and footnote references work inside alerts and quotes too. A token is replaced only where it stands as a paragraph of its own (`<p>token</p>`); a token anywhere else is removed, because a block must not land in an unknown context such as an attribute value. Known limitation: a block with its own renderer (code, alert, quote with author) placed inside a raw HTML block written by the author is not rendered. Every author value inside a block is either escaped with `html.escape` (code, file name, quote author, and the `src`, `alt` and caption of a figure, re-escaped explicitly because the caption moves from an attribute into element content) or was cleaned by the same `nh3` call (alert and quote bodies, footnote text). So `class` and `id` come only from the renderers (prefix `blog-`, `language-*` on `<code>`, heading anchors), and a hand-written `class="blog-callout-note"` or `id` in raw HTML is removed, like `<script>`, `on*` attributes and `javascript:` / `data:` URLs; links keep `rel="noopener noreferrer nofollow"`. The dashboard renderer `render_markdown_html()` is untouched: no sanitization and no blocks. Graphic blocks (MON-257): four containers whose source is text (a table, a description, code) with the graphic as a layer over it, so a model reading the markdown twin and a reader without JS get the same content; no block accepts raw HTML, CSS or JS from the author. They go through the same dispatch as the structural containers (rendered onto a token, inserted after the `nh3` pass), attribute values (`title`, `type`, `name`) are read with `dict(_ATTR.findall(container.attrs))`, and the fenced block inside `diagram` and `terminal` is found by `_split_fenced` (the first closed fence of the container, language lowercased) and always escaped, never interpreted. Titles placed in element content (the `<figcaption>` of a chart and of a diagram, `blog-terminal-title`) go through `_text_escape`, i.e. `html.escape` plus `[` written as `&#91;`, because `_link_footnotes` runs after the blocks are inserted and would otherwise turn a `[^label]` in a title into a footnote reference. `chart` (`:::chart type="bar|line|pie" title="..."` over a markdown table): `<figure class="blog-chart blog-chart-{type}">` with the inline SVG from `services/blog_chart.py` and the table in `<details class="blog-chart-data"><summary>Dane wykresu</summary>`; when the table cannot be read as chart data, `type` is missing or unknown, or the data cannot be drawn (`pie` with a negative value or a sum of 0), it is `<figure class="blog-chart">` with the inside through `_clean`, no `<svg>` and no `<details>`; a non-empty title is an escaped `<figcaption>` in both variants. `diagram` (`:::diagram title="..."`: a description paragraph plus a `mermaid` fence): `<figure class="blog-diagram" data-blog-diagram>` with the optional `<figcaption>`, `<div class="blog-diagram-description">` (omitted when there is no description), `<div class="blog-diagram-canvas" hidden>` and `<pre class="blog-diagram-source"><code>` holding the escaped source, deliberately without `language-mermaid`, so that the word `mermaid` in the page HTML means only the library script; the source is the first closed fence of the container and only when its language is `mermaid` and it is not empty. A first fence in another language is the author's content: it stays in the description (rendered as ordinary markdown, kept in the `.md` twin too) and the figure carries the description alone (no `data-blog-diagram`, canvas or source), as it does without any fence; an empty `mermaid` fence is dropped, and when nothing else is left the inside degrades to ordinary markdown. `terminal` (`:::terminal title="..."` over a fence, `console` by convention but any language or none is accepted): `<figure class="blog-terminal" data-blog-terminal>` with `blog-terminal-bar` / `blog-terminal-title` (escaped title) and `<pre class="blog-terminal-body"><code>` holding the full escaped content from the start; no fence or an empty one degrades to ordinary markdown. `graphic` (`:::graphic name="<name>"` plus a description paragraph): `<div class="blog-graphic" data-blog-graphic="<name>">` around `<div class="blog-graphic-description">` (through `_clean`); `BLOG_GRAPHICS` (`frozenset`, today only `agent-loop`) is the closed registry of component names, the attribute is emitted only on an exact match, and an unknown or missing name renders the same wrapper without `data-blog-graphic`, i.e. the description alone, so an author's name never reaches a file path. A graphic must have content: a `:::graphic` without a description renders nothing (empty inside, like any container), loads no component and is reported by `find_block_issues`. Markdown form (`to_markdown`, no HTML in any of them): `chart` is `**title**` (when non-empty) and the inside, i.e. the source table; `diagram` is `**title**`, the description and a `mermaid` fence; `terminal` is `**title**` and a `console` fence whatever the source language was; `graphic` is the description alone, without a label or the component name. A rebuilt fence is made longer than any backtick run in its content, and a block without its fence falls back to title plus inside (for a `diagram` with an empty `mermaid` fence: title plus the description, the empty fence dropped). `collect_block_assets(markdown) -> BlockAssets` (frozen dataclass: `has_diagram: bool`, `graphics: tuple[str, ...]`) tells the page what to load, over the same `_split_containers` path as the renderer, so containers inside fenced code and unclosed ones do not count: `has_diagram` is true when at least one `:::diagram` has a non-empty `mermaid` fence (exactly the ones that get `data-blog-diagram`), and `graphics` lists the `BLOG_GRAPHICS` names used by a `:::graphic` with a non-empty inside, without duplicates, in order of first use; it never raises (`BlockAssets(False, ())` on error). `blog.py::public_page` passes both to the template as `has_diagram` and `graphics` (a list), and `templates/blog/page.html` emits, in `{% block head %}` after `blocks.css` and BEFORE `blocks.js` (MON-272; `blocks.js` was first until then, and `defer` scripts run in document order), one `<link>` and one `<script defer>` per name from `/static/blog/graphics/<name>.css|.js` and, only when `has_diagram`, exactly one `<script src="https://cdn.jsdelivr.net/npm/mermaid@11.17.2/dist/mermaid.min.js" integrity="sha384-..." crossorigin="anonymous" defer>` (pinned version with SRI; an external script on top of the Tailwind CDN one that `layouts/landing.html` loads on every page), so a post without a diagram contains the string `mermaid` nowhere in its HTML; `layouts/landing.html` is unchanged. `static/blog/blocks.js` starts its block initialization (`initBlocks`: diagrams, terminals, graphics) only when the document is ready (MON-272): at once for `document.readyState === "complete"`, otherwise on `DOMContentLoaded` with `load` as a fallback, and a flag makes the second call a no-op, so nothing renders twice. It then calls `mermaid.initialize({startOnLoad: false, securityLevel: "strict", theme})` and renders each source (read with `textContent`) into the canvas, adding `blog-diagram-rendered`, which hides the source in CSS, while a missing library or a render error leaves description and source visible; types `[data-blog-terminal]` content when it scrolls into view, skipped under `prefers-reduced-motion: reduce`; and calls `window.BlogGraphics[name].mount(el)` for each `[data-blog-graphic]`, adding `blog-graphic-mounted` on success (the description then stays in the DOM for screen readers only), with an exception in `mount` leaving the description. Components live in `static/blog/graphics/<name>.js` and `.css`; the contract (one `mount(el)` function, no external requests, `prefers-reduced-motion`, rules scoped to `.blog-graphic[data-blog-graphic="<name>"]`, dark theme through `.dark`) is in `static/blog/graphics/README.md`, and a new component is its two files plus an entry in `BLOG_GRAPHICS`, reviewed in an MR. Chart colours come from the CSS variables `--blog-chart-1..6` (plus axis, grid, label and surface) defined on `.blog-content .blog-chart` and overridden under `.dark` in `static/blog/blocks.css`. `find_block_issues(markdown) -> list[BlockIssue]` (frozen dataclass: `rule`, `level`, always `error`, `line`, the 1-based line of the container's opening, taken from the new `_Container.line`, and a Polish `message`) is the lint helper for graphic blocks, with fixed rule names: `graphic-missing-description`, `graphic-unknown-name` (a name outside `BLOG_GRAPHICS` or no `name`), `chart-missing-data` (no table that `parse_chart_table` can read), `diagram-missing-description`, `diagram-missing-source` (no non-empty `mermaid` fence), `terminal-missing-content` (no fence or an empty one). One container can yield two issues, a post without graphic blocks or with correct ones yields an empty list, and it never raises (empty list on error). It checks neither the chart `type` nor whether a `pie` can be drawn, and since MON-262 its only caller is the post lint, `services/blog_lint.py`. `iter_source_lines(markdown) -> list[SourceLine]` (MON-262; frozen dataclass: `number` from 1, `text`, `in_code`, true for a fence line and its content, and `container`, the type of the closed registered container the line belongs to, its `:::` marker lines included, or `None`) gives the lint the source lines with the context the renderers use, following the rules of `_split_containers`, so an unclosed container and a container of an unknown type are plain lines; it never raises (empty list on error) and changes neither `find_block_issues` nor any renderer. Tests: `tests/unit/test_blog_blocks.py`, `tests/unit/test_blog_chart.py`, `tests/integration/test_blog_public.py`
- `services/blog_chart.py` (MON-257) - server-side SVG chart for the `:::chart` block, stdlib only, called by `blog_blocks.py`. `parse_chart_table(markdown) -> ChartData | None` reads the first markdown table (header row, `|---|` separator row, data rows): the first column holds the labels, every further column is a series named by its header. It returns `None` when there is no table, no data row, fewer than 2 columns, a row with a different cell count than the header, or a non-numeric series cell; a number has its whitespace removed and `,` read as the decimal separator, and its shape is checked by a regex before `float()`, so `nan`, `inf` and `1_0` are not numbers. `render_chart_svg(chart_type, title, data) -> str | None` builds the SVG for a type from `CHART_TYPES` (`bar`, `line`, `pie`): `bar` and `line` draw every series (a legend appears above the plot when there is more than one) and accept negative values, `pie` draws the first series only. It returns `None` for an unknown type, no labels or series, a series whose length differs from the labels, and a `pie` with a negative value or a sum of 0 or less. The root is `<svg class="blog-chart-svg" role="img" viewBox="0 0 640 360" xmlns="http://www.w3.org/2000/svg">`, whose first children are `<title>` (`Wykres` for an empty title) and `<desc>` (a Polish text summary of the data: chart kind, series and value per label), and the result is well-formed XML. Security model: the SVG is built only from parsed data and is appended after sanitization, so it never passes through `nh3` and the tag allowlist in `services/wiki.py` is not widened for it; every author text (title, labels, series names) goes through `_esc`, which is `html.escape` plus `[` written as `&#91;` (the SVG lands in the page before `_link_footnotes` runs, so no author text in it may contain the sequence `[^`, or a footnote reference would be substituted inside the chart), every number in an attribute comes from a `float`, so a `<script>` label creates no element. The SVG carries no colour: shapes have `blog-chart-series-N`, legend swatches `blog-chart-swatch-N` (N = 1..6, cycling), axes `blog-chart-axis`, grid lines `blog-chart-grid`, texts `blog-chart-label`, with no hex value and no `style` attribute. `ChartSeries` (`name`, `values`) and `ChartData` (`labels`, `series`) are frozen dataclasses. Neither function ever raises (errors are logged and answered with `None`). Tests: `tests/unit/test_blog_chart.py`
- `services/blog_lint.py` (MON-262) - lint of a blog post for AI readers, behind `lint_blog_post` (MCP), `GET .../blog/posts/{page_id}/lint` (API v2) and `monolynx blog lint` (CLI). `lint_post(markdown, meta, *, today=None) -> LintResult` is pure (no DB, no network) and never raises, whatever the text (empty, frontmatter only, an unclosed container); `today=None` means `date.today()`. `LintMeta` (frozen dataclass: `description`, `last_verified_at`, `has_translation`) carries what the text does not hold, `LintIssue` is `rule`, `level`, `line`, `message` (Polish), and `LintResult` is `issues` sorted by `(line, rule)` plus `score`, with the properties `error_count`, `warning_count`, `info_count` and `has_errors`. Score: `max(0, 100 - 20 * errors - 5 * warnings)` (`ERROR_PENALTY`, `WARNING_PENALTY`); an `info` issue does not lower it. `line` is the 1-based line of the SOURCE: a leading `---...---` frontmatter is skipped by the analysis but does not shift the numbering, and metadata issues and issues with no place in the text have `line = 0`. Rules, errors: `description-missing`, `description-length` (outside 50..300 after `strip()`; the upper bound is `DESCRIPTION_MAX_LENGTH` from `services/blog.py`), `tldr-missing` (the first non-empty line after the frontmatter and an optional single H1 is not `> [!TLDR]`), `tldr-points` (list items in the TLDR block outside 2..5), `image-alt-short` (alt text shorter than 11 characters after `strip()`), `heading-multiple-h1` (the second and every further H1), `heading-level-skip` (a heading more than one level below the previous one; the start level is 1, so a first H3 is a skip), and the six rules of `blog_blocks.find_block_issues` under their own names, with the line in source numbering. Warnings: `h2-starts-with-pronoun` (the first text line under an H2 starts with an entry of `REFERRING_PRONOUNS`, PL and EN), `h2-no-question` (no H2 ends with `?`, also when there is no H2), `link-non-descriptive` (link text in `NON_DESCRIPTIVE_LINK_TEXTS`, e.g. `tutaj`, `kliknij`, `here`, `link`), `last-verified-missing`, `last-verified-stale` (older than `LAST_VERIFIED_MAX_AGE_DAYS`, 180), `em-dash` (U+2014 in a text line, one issue per line). Info: `translation-missing`. Headings, images, links and em-dashes inside fenced code (backticks or tildes) do not count, and a `###` inside `:::faq` is not a section heading. The spec rule "numbers and product claims carry a date or a version" is deliberately not implemented. `lint_post_by_id(db, user, project, page_id, *, content_fn=None)` follows `get_post`: `ensure_permission()` for `wiki:read` first, then `Strona wiki nie istnieje` / `Wpis bloga nie istnieje`, the content through an injectable `content_fn` (lazy import of `services.wiki.get_page_content`), and `has_translation` true when the post has `translation_of_id` or another `BlogPost` points at it; a pure read, no commit. An unexpected error inside `lint_post` is logged and answered with the single error `lint-failed` (line 0) instead of an exception. Two helpers keep the channels equal: `lint_result_dict(page_id, result)` builds the dict shared by the MCP tool and the v2 response, and `format_lint_table(result)` the markdown table with the score line that only the MCP tool adds as `table`. The source lines come from `blog_blocks.iter_source_lines`. `LintResult` is the input of the publish gate: `services/blog.py::publish_post` (MON-263) calls `lint_post_by_id` and refuses the publication on `has_errors` unless `force` is set, naming the rules of level `error`. Tests: `tests/unit/test_blog_lint.py`

## Decisions

- Blog post blocks (MON-255, MON-256, MON-257): a block is written as plain, readable markdown (GitHub alerts, a `-- Author, role` line, an image title, `title="..."` on a fence, `:::type` containers) and the server generates its HTML from a closed list of renderers in `services/blog_blocks.py`; every block has two renderers, `to_html` and `to_markdown`. Author content is sanitized by a single `nh3` pass that allows no `class` and no `id`, and block HTML is inserted after it through placeholder tokens with a random nonce, so `blog-*` classes and `id` attributes can only come from a renderer, never from the post. The container registry (`CONTAINER_BLOCKS`) holds 13 blocks: 9 structural ones since MON-256 (`faq`, `steps`, `stats`, `compare`, `details`, `gallery`, `video`, `cta`, `glossary`) and 4 graphic ones since MON-257 (`chart`, `diagram`, `terminal`, `graphic`). A registered container is rendered onto a token before the rest of the post is sanitized, all author markdown in it (bodies and short values such as a FAQ question, a step name or a glossary term) through the same `nh3` cleaning and only non-markdown values (the `details` title, the video address, gallery `src`/`alt`, the CTA `href`) through `html.escape`, without widening the allowlists in `services/wiki.py`; an unknown or unclosed `:::` container, and a registered one with a wrong structure or an empty inside, degrades to ordinary markdown and never to an error. `:::video` accepts only `https` addresses whose host is on an exact YouTube/Vimeo allowlist, and the server emits neither an `<iframe>` nor a thumbnail from the video host: `static/blog/blocks.js` builds the iframe (`youtube-nocookie.com` / `player.vimeo.com`) after a click, from `data-provider` and `data-video-id` only, and without JS a plain link stays. In the markdown twin a registered container loses its `:::` lines and gets a one-line label (`**FAQ**`, `**Kroki**`, ...). `extract_structured_data()` returns the `faq`, `steps` and `videos` of a post as a dict for the future AI layer (JSON-LD), with `glossary` deliberately left out. Graphic blocks (MON-257) keep the rule that the author injects no HTML, CSS or JS: the source of every graphic is text (a table, a description, code) and the graphic is a layer over it, so each one has content without JS and in the markdown twin (`chart` = title + table, `diagram` = description + `mermaid` fence, `terminal` = `console` fence, `graphic` = description). The chart SVG is generated on the server by `services/blog_chart.py` from parsed numbers and escaped texts and appended after sanitization, without widening the `nh3` allowlist, and it carries only `blog-chart-*` classes, with colours from CSS variables for both themes. A diagram is rendered in the browser by Mermaid, loaded from a pinned CDN address (`mermaid@11.17.2` on jsdelivr, with an SRI `integrity` hash and `crossorigin="anonymous"`) only on a post that has a diagram and initialized with `securityLevel: "strict"`; it is an additional external script next to the Tailwind CDN one from `layouts/landing.html`, which every blog page already loads, and the application sends no CSP header. Custom JS lives only in the repository, as a named component in `static/blog/graphics/<name>.js|.css` listed in the closed registry `BLOG_GRAPHICS`; a name outside it renders the description alone and loads nothing, and a component's files are attached only to a post that uses it (`collect_block_assets()` -> `has_diagram`, `graphics` in the template context). `find_block_issues()` reports graphic blocks without their content (description, data, source, registered name) for a future post lint. Block styles live in `static/blog/blocks.css` and the script in `static/blog/blocks.js`; `templates/blog/page.html` loads both, plus the per-post graphic assets since MON-257. Three markdown renderers now coexist: `render_markdown_html()` (dashboard, tickets, comments; no sanitization), `render_markdown_public()` (sanitized, no blocks, kept in `services/wiki.py` with its tests but no caller in `src/`) and `render_post_html()` (blog posts)
