# Architecture: MCP server, RBAC, blog permission

Detail moved out of CLAUDE.md.

## MCP Server (`mcp_server.py`)

- FastMCP-based server mounted at `/mcp` in the main app
- 125 tools across all modules: projects, 500ki issues, monitoring, Scrum (tickets, sprints, board, comments), Time Tracking (`log_time` writes, `get_work_report` reads the aggregated report), Wiki (CRUD, semantic search), Blog post metadata, lint and publication (`list_blog_posts`, `get_blog_post`, `set_blog_post_meta`; MON-261; `lint_blog_post`, MON-262: returns a dict with `page_id`, `score`, `error_count`, `warning_count`, `info_count`, `issues` and `table`, a markdown table `| Linia | Poziom | Reguła | Komunikat |` followed by the line `Ocena: <score>/100`, or `Brak problemów.` and the score line when there are no issues; `publish_blog_post(project_slug, page_id, force=False)` and `unpublish_blog_post(project_slug, page_id)`, MON-263: publish runs the lint and then makes the page public, returning the post view of the other blog tools (15 fields, with `public_url` and `markdown_url`) plus `lint`, the dict of `lint_blog_post` without `table`; with lint errors and no `force` the tool fails with the text `Publikacja odrzucona: wpis ma błędy lintu ...` listing the rules and the page stays private; unpublish returns the post view with `is_public` false and both URLs `null`), Wiki LLM method (`get_wiki_config`, `set_wiki_config`, `bootstrap_wiki_llm`, `lint_wiki`, `get_wiki_backlinks`, `regenerate_wiki_index`, `append_wiki_log`), Graph (node/edge CRUD, bulk operations, `replace_graph` full-replace sync, query, path finding, stats), Work Plan (`schedule_ticket`, `update_work_plan_entry`, `delete_work_plan_entry`, `list_work_plan`, `get_today_tasks`, `get_ticket_schedule`), Pipelines (`create_pipeline`, `create_pipeline_job`, `update_pipeline_job`, `append_job_log`, `finish_pipeline`, `list_pipelines`, `get_pipeline`, `get_pipeline_job_log`, `clean_pipeline_logs`), project summary. The `list_tickets` text table ends with a tenth column, `Blocked by` (blocker keys in ascending number order, joined with `, `; `--` when there are none; MON-246)
- Every tool carries MCP `ToolAnnotations` via one of three module-level constants: `READ_ONLY` (55 tools: `get_*`/`list_*`/`search_*` plus `query_graph`, `find_graph_path`, `lint_wiki`, `lint_blog_post`, `install_monolynx_skills`), `WRITE` (53: creates and updates, additive, `publish_blog_post` among them), `DESTRUCTIVE` (17: `delete_*`, `remove_member`, `clean_pipeline_logs`, `replace_graph`, `unlink_ticket_from_settlement`, `unpublish_blog_post`, which takes a public address offline). `openWorldHint=False` everywhere - the domain is the project's own database. These are hints for the client (permission handling, tool choice), never a substitute for the per-tool `_auth(ctx)` check. A new tool MUST declare one; `tests/unit/test_mcp_server.py` fails otherwise
- Role permissions (MON-241, MON-242): `_auth(ctx)` only resolves the user from the token and `_get_user_and_project(ctx, project_slug)` adds the active-project and membership check; on top of that the Scrum, Wiki, 500ki, Monitoring, Heartbeat, Connections (graph) and Pipelines tools and `get_activity_log` additionally enforce the role permission, returning the text `Brak uprawnienia {module}:{action}` on refusal. A tool that delegates to a service with its own check (`services/tickets.py`, `services/projects.py` labels, `services/wiki.py` reads, `services/wiki_attachments.py`) gets no second check. A tool with no such service calls `ensure_permission()` inline as its first step: `start_sprint`, `complete_sprint`, `add_attachment`, `log_time` -> `scrum:write`; `get_burndown`, `get_attachment` -> `scrum:read`; `create_wiki_page`, `update_wiki_page`, `regenerate_wiki_index`, `append_wiki_log` -> `wiki:write`; `delete_wiki_page` -> `wiki:delete` (plus the account-level `blog:write` when the page or any of its descendants is public, MON-272: `ensure_can_delete_page()` from `services/wiki.py` after the page lookup, refusal text `Brak uprawnienia blog:write`, nothing deleted); `search_wiki`, `lint_wiki`, `get_wiki_backlinks` -> `wiki:read`. The blog tools (MON-261) follow the same module: `list_blog_posts` and `get_blog_post` -> `wiki:read`, checked by `services/blog.py` (`get_blog_post` also calls `_require()` first), and `set_blog_post_meta` -> `wiki:write` through `_require()` before any id or date parsing, with `set_post_meta` checking it again. `lint_blog_post` (MON-262) -> `wiki:read` through `_require()` before the UUID parsing, with `lint_post_by_id` checking it again. `publish_blog_post` and `unpublish_blog_post` (MON-263) -> `wiki:write` through `_require()` before the UUID parsing, with `publish_post` / `unpublish_post` checking it again before the page lookup and the lint. Blog permission (MON-270): publishing has a separate, account-level permission, `blog:write` (`User.can_edit_blog`, always true for a superuser, granted and revoked only by a superuser on the account edit page `/dashboard/users/{user_id}`; no MCP tool, v2 endpoint or CLI command grants it). `set_blog_post_meta`, `publish_blog_post` and `unpublish_blog_post` need `wiki:write` AND `blog:write`, checked in this order by `services/blog.py` before the page lookup and the lint, and `create_wiki_page` with `is_public=true` and `update_wiki_page` with a change of `is_public` or, since MON-271, with a changed title or content of an already public page need `blog:write` too (checked by `services/wiki.py`); the refusal text is `Brak uprawnienia blog:write` and nothing is written. The reads `list_blog_posts`, `get_blog_post` and `lint_blog_post` stay on `wiki:read`. An account without the permission does not see the three blog write tools on the tool list: `_MCPBearerAuthMiddleware` filters the `tools/list` response through the pure function `_hide_blog_write_tools(body: bytes) -> bytes`, which drops the names in `BLOG_WRITE_TOOLS` (`set_blog_post_meta`, `publish_blog_post`, `unpublish_blog_post`). Since MON-271 the response is buffered and filtered only for a request that carries `tools/list`: for such an account the middleware peeks at the POST body (up to 64 KiB), replays it unchanged to the app and reads `method` of the JSON-RPC object or of every element of a batch array; any other request (e.g. `tools/call`) goes through the plain `send`, with no buffering and no change of `content-length`. When the method cannot be determined (body over the limit, invalid JSON, no body) the response is buffered and filtered as before, the safe default. `_hide_blog_write_tools` also filters a batch response: every array element that is an object with `result.tools`. The registry (`mcp.list_tools()`) and the tool count are unchanged, a call of a hidden tool still answers `Brak uprawnienia blog:write`, and `create_wiki_page` / `update_wiki_page` stay visible. MON-242 adds the module checks through one helper, `_require(db, user, project, module, action)` in `mcp_server.py` (a thin wrapper over `ensure_permission`), called as the first step after `_get_user_and_project`, before the resource lookup, id parsing, input validation and the `graph_service.is_enabled()` check, so a refusal never writes anything: `list_issues`, `get_issue` -> `500ki:read`; `update_issue_status`, `create_issue` -> `500ki:write`; `create_ticket_from_issue` -> `500ki:write` and `scrum:write`; `list_monitors`, `get_monitor` -> `monitoring:read`; `create_monitor`, `update_monitor` -> `monitoring:write` (`delete_monitor` keeps its own `monitoring:delete` check and message); `list_heartbeats`, `get_heartbeat` -> `heartbeat:read`; `create_heartbeat`, `update_heartbeat` -> `heartbeat:write`; `delete_heartbeat` -> `heartbeat:delete`; `list_graph_nodes`, `get_graph_node`, `query_graph`, `find_graph_path`, `get_graph_stats` -> `connections:read`; `create_graph_node`, `create_graph_edge`, `bulk_create_graph_nodes`, `bulk_create_graph_edges` -> `connections:write`; `delete_graph_node`, `delete_graph_edge`, `replace_graph` -> `connections:delete`; Pipelines has no permission module of its own, so `list_pipelines`, `get_pipeline`, `get_pipeline_job_log` -> `scrum:read`, `create_pipeline`, `create_pipeline_job`, `update_pipeline_job`, `append_job_log`, `finish_pipeline` -> `scrum:write`, and `clean_pipeline_logs` (deletes wiki pages) -> `wiki:delete`; `get_activity_log` -> `settings:read`. The dashboard Pipelines routes follow the same mapping (`scrum:read` via `require_permission`). Still membership only: `get_project_summary`, `get_work_report` and the Work Plan tools, while `set_wiki_config` and `bootstrap_wiki_llm` keep `settings:write` and the role and settlement tools keep their `settings:*` / `rozliczenia:*` checks. The account the agents run under (plugin skills) therefore needs a role with the matching permissions: the default `member` reads and writes tickets and wiki pages but cannot delete them. An account that publishes blog posts (the `blog-post` skill, `wiki create --public`) additionally needs the blog permission granted by a superuser, since no role carries it (MON-270)
- Bearer token auth via `Authorization` header (tokens managed in `/dashboard/profile/tokens`)
- `.mcp.json` at project root configures Claude Code connection (env var `MONOLYNX_MCP_TOKEN`)
- `install_monolynx_skills` tool serves skill copies from `static/skills/` for manual install into a project's `.claude/skills/` (used by claude.ai web and environments without plugin support)

## Services

- `services/permissions.py` - RBAC per module and action: `check_permission(db, user_id, project_id, module, action)` returns a bool (superuser bypass, then the member's `role_obj.permissions`, then `DEFAULT_ROLE_PERMISSIONS` for a legacy `member.role`); `require_permission()` raises `HTTPException(403)` for dashboard routes; `ensure_permission()` raises `ValueError("Brak uprawnienia {module}:{action}")` for services and MCP tools (MON-241), the text `api/v2/common.py::service_error()` maps to 403; `get_user_permissions()` returns the user's full permission map in a project. Blog permission (MON-270), account-level and outside the role map: `has_blog_permission(db, user_id) -> bool` is true for an active superuser and for an active account with `User.can_edit_blog`, whatever the role in any project; `ensure_blog_permission(db, user_id) -> None` raises `ValueError("Brak uprawnienia blog:write")`, returned as text by MCP, mapped to 403 by `service_error()` and ending a CLI command with exit code 3. These two are the only source of truth for publishing; `blog` is not a key of `PERMISSION_MODULES`, so no role (owner and admin included) grants it
- `services/mcp_auth.py` - MCP token generation (`osk_<random>` prefix), SHA256 hashing, verification with `last_used_at` tracking; `verify_bearer_token(raw_token, db, *, legacy_verifier=None)` is the shared Bearer-auth entry point for both MCP (`mcp_server._verify_token`) and API v2 (`api/v2/deps.py::get_api_user`) - tries OAuth access token first, then falls back to legacy `osk_*`, rolling back the shared `db` session before the fallback if the OAuth path raises. `legacy_verifier` defaults to `None` and is resolved to this module's own `verify_mcp_token` at call time (never bound as a default argument value), because this module's own unit tests (`tests/unit/test_mcp_auth.py`) patch the module-level name `monolynx.services.mcp_auth.verify_mcp_token`; `mcp_server._verify_token` passes `legacy_verifier=verify_mcp_token` explicitly for a different reason - the pre-existing MCP test suite (`tests/unit/test_mcp_server.py` and others) patches `monolynx.mcp_server.verify_mcp_token` instead, and without the explicit pass that patch would have no effect on the fallback

## Decisions

- RBAC is enforced in all three channels with one source of truth, `check_permission()` in `services/permissions.py` (MON-241): the dashboard calls `require_permission()` from that module (`HTTPException(403)`), services and MCP tools call `ensure_permission()` (`ValueError("Brak uprawnienia {module}:{action}")`, returned as MCP error text), and API v2 turns that `ValueError` into 403 problem+json via `service_error()` or calls its own `require_permission()` from `api/v2/common.py` where the service takes no user. Project membership alone no longer grants access to the Scrum, Wiki, 500ki, Monitoring, Heartbeat, Connections or Pipelines modules, or to `get_activity_log`, through a token. The default `member` role has `scrum` and `wiki` `read` + `write` but neither `scrum:delete` nor `wiki:delete` (`DEFAULT_ROLE_PERMISSIONS` in `constants.py`), so a token with that role cannot delete tickets, acceptance criteria or wiki pages; `owner` and `admin` keep full access to both modules. Since MON-242 the 500ki, monitoring, heartbeat, graph and pipelines MCP tools and `get_activity_log` check the role permission through `_require()` in `mcp_server.py` (a thin wrapper over `ensure_permission()`; mapping in the MCP Server section)
- Blog publishing is an account-level permission, not a role permission (MON-270). Before it, `wiki:write` was enough to publish, and since any signed-in user can create a project and becomes its owner, anyone could put a page on the public blog (which is not scoped to a project). Now `User.can_edit_blog` (bool, default false, migration `k1f2a3b4c5d6`) decides, a superuser always has it, and only a superuser grants or revokes it, with the switch on the account edit page `/dashboard/users/{user_id}` (`templates/dashboard/users/edit.html`, form to `POST /dashboard/users/{user_id}/blog-permission`; the user list `/dashboard/users` only shows a "Blog" badge); a project owner or admin cannot grant it through any channel, and there is no MCP tool, v2 endpoint or CLI command for it. One source of truth: `has_blog_permission()` / `ensure_blog_permission()` in `services/permissions.py`, refusal `ValueError("Brak uprawnienia blog:write")` (MCP error text, 403 problem+json in API v2, exit code 3 in the CLI). Gated: `set_post_meta`, `publish_post`, `unpublish_post` (`wiki:write` first, then `blog:write`, both before the page lookup and the lint) and, in `services/wiki.py`, `is_public=true` at page creation, every change of `is_public` at update and, since MON-271, an update that changes the title or the content of an already public page, so the dashboard form, MCP, API v2 and the CLI share it and a refusal writes nothing. MON-272 adds two more gates for a public page: uploading a file to it (dashboard `POST /dashboard/{slug}/wiki/upload?page_id=` and the FilePond attachment route: 403 JSON; MCP `add_wiki_page_attachment`: error text), and deleting a page that is public or has a public descendant (`ensure_can_delete_page()` in `services/wiki.py`, next to `wiki:delete`: MCP `delete_wiki_page`, v2 `DELETE .../wiki/pages/{page_id}` with 403 problem+json, the dashboard with 403, the CLI through v2 with exit code 3). Not gated: the blog reads (`wiki:read`), an update of a public page that leaves its title and content unchanged, and deleting an attachment of a public page (`wiki:delete` only, deliberately left out of MON-272). In MCP an account without the permission does not see the three blog write tools (`BLOG_WRITE_TOOLS`, filtered out of the `tools/list` response in `_MCPBearerAuthMiddleware`, batch requests included, while responses to other requests are not buffered; the registry and the tool count are unchanged). Pages and posts public before the change stay public, with no data migration; accounts that published until now (e.g. the account the plugin agents run under) need the permission granted by a superuser. Tests: `tests/unit/test_blog_permission.py`, `tests/integration/test_blog_permission_channels.py`, `tests/integration/test_users_blog_permission.py`, `tests/integration/test_blog_permission_migration.py`
