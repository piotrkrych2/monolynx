# Architecture: sprint-run dispatcher, work skills, test queue

Detail moved out of CLAUDE.md.

- Plugin 1.8.0 (MON-167) adds the `sprint-run` dispatcher: `/monolynx:sprint-run [slots]` is one idempotent tick that reads the active sprint plus `claude agents --json --all`, starts a named background session per free ticket (`MONOLYNX_SPRINT_RUN=1 claude --bg --worktree <KEY> --name <slug>-<KEY>-<model> "/monolynx:work <KEY>"`, permission mode taken from the start command in the skill's KROK 4, overridable via `MONOLYNX_SPRINT_PERMISSION_MODE`), collects finished ones (comment with the session id, then `claude rm`) and ends with the frozen status line `SPRINT-RUN: remaining=<n> running=<m> waiting=<k> done=<d>` (corrected for sessions started in the same tick). It never works on a ticket itself. Since MON-249 the Claude start command also carries `--allowedTools "Bash(git fetch origin <B>),Bash(git merge --ff-only origin/<B>)"` with the literal `BASE_BRANCH` from the preflight, placed before `--permission-mode` (the option is variadic and would swallow the prompt if it stood right before it) and omitted when `BASE_BRANCH` is empty, does not match `^[A-Za-z0-9][A-Za-z0-9._/-]*$` or contains `..`: an exact allow rule is resolved before the auto-mode classifier, in subagents too, and covers no other branch or command form; the `codex` backend start is unchanged, and so is the tracked `.claude/settings.json`. Per-ticket verdicts (`done`, `needs_human`, `waiting`, `free`, `running`) are computed by `plugin/scripts/sprint_run_state.py` from session list, ticket statuses and log tails, never guessed from prose. Since 1.8.1 (MON-172) the session-state logic is a closed dead-list (`exited`, `completed`, `failed`, `stopped`, `killed`, `done`, `error`; a missing field is `exited`, any unknown literal counts as alive with a warning in `reason`, because a false `exited` triggers an auto-resume and a duplicate session), log tails are ANSI-stripped with `\r` as a line separator (the real `claude logs` render), and batch vs interactive mode is signalled by `MONOLYNX_SPRINT_RUN_MODE=batch` exported by `sprint_run.sh` (`[ -t 0 ]` is false inside the Bash tool even in an attended session). Captured CLI fixtures live in `tests/fixtures/claude/` per `.claude/rules/external-tool-output.md`. MON-252: a live session also gets `waiting` when its last answer block holds a numbered option list (at least two `<digit>. text` / `<digit>) text` lines) together with a decision phrase (`Decyzja dla Ciebie`, `wybierz`, `opcja 1`), even without a question mark, or ends with a waiting phrase (a sentence starting with `Czekam` or containing `waiting for`), and a user input line `❯ <text>` clears every such signal that precedes it, the `SPRINT-RUN STOP:` marker included. A stall detector (`claude` backend only) keeps a sha256 of each live session's log tail, volatile status lines dropped, in `stall.json` under `TICK_DIR` (outside `logs/`, passed via `--state-dir`); a tail unchanged for `MONOLYNX_SPRINT_STALL_TICKS` consecutive ticks (default 2) turns `running` into `waiting` with the reason `brak postępu od <n> ticków`, and a missing or malformed state file never yields `waiting`, because a false `waiting` is undone by the next tick while the dispatcher leaves `waiting` sessions untouched. The loop lives outside the skill: `/loop 15m /monolynx:sprint-run` in an interactive session, or `plugin/scripts/sprint_run.sh` (fresh `claude -p` per tick; tmux/VPS/cron, exit codes 0/2/3/4). Preflight requires `MONOLYNX_AUTOTEST`, `MONOLYNX_AUTOCOMMIT` and `MONOLYNX_AUTOPUSH` in the project's tracked `.claude/settings.json` or in the environment of the process that starts the tick (a worktree does not see `settings.local.json`); background sessions inherit the environment, not the shell. `MONOLYNX_BASE_BRANCH` and `MONOLYNX_MR_TARGET` name one branch: setting one is enough (normally `MONOLYNX_MR_TARGET`, the only one that also sets the `work` MR target), both set and different is a preflight `ERROR` (MON-219). With `BASE_BRANCH_STALE=true` KROK 4 first runs `sprint_run_tick.py sync-base --base-branch <b> --project-dir <dir>` (MON-142; fast-forward only: `git fetch origin <b>` + `git merge --ff-only origin/<b>`, never reset/rebase/checkout) and prints one frozen line `SYNC-BASE: ok|skipped|failed reason=<reason>` (exit 0 for ok/skipped, 2 for failed, 64 usage); `ok` dispatches normally, `skipped`/`failed` keep the old path (interactive warning, batch `SPRINT-RUN STOP`); a checkout on another branch is left alone (`skipped reason=not-on-base-branch`), because `claude --bg --worktree` takes the main checkout's HEAD. Session names and the status-line format are a frozen contract. Models are explicit per role, because a process without `--model` takes the account default (which can be the most expensive model) and a subagent without `model` inherits its parent session's model: `sprint_run.sh` runs `claude -p --model "${MONOLYNX_SPRINT_TICK_MODEL:-opus}"` for the tick and `--close` (sessions `<slug>-sprint-run-<model>`, `<slug>-sprint-end-<model>`, `<slug>-retro-<model>`; every session name ends with its model, see `.claude/rules/session-name-model.md`), the skill starts background sessions with `--model "${MONOLYNX_SPRINT_MODEL:-opus}"` and the same value as the session-name suffix (`sprint_run_state.py` matches `<slug>-<KEY>` with any model suffix or none, so a model change between ticks never hides a live session and starts a duplicate; Fable for the ticket coordinator only via an explicit override), and `work` / `work-simple` spawn every subagent with an explicit model ("Model subagentow" section: Researcher `sonnet`, developer from the agent's `model:` frontmatter or `sonnet` when missing, critic `opus`; the one exception is the Codex critic of `work`, which is not an `Agent()` call and takes its model from `MONOLYNX_CRITIC_CODEX_MODEL` or the Codex configuration, see the MON-274 entry below); role table in the `Modele` section of `plugin/README.md`
- Plugin 1.8.3 (MON-166) splits lint/test commands by environment. The `toolchain` wiki page gains a `## Worktree` section with `lint:` and `test:` fields, written by `/monolynx:project-toolchain` (Docker stack -> `docker compose -p <compose-project> --profile <p> run --rm --no-deps -v "$PWD":<workdir> <service> <command>`, otherwise the value `jak wyzej`, which points back at `## Lint` / `## Test`). `work` and `work-simple` detect a git worktree on the host by running `git rev-parse --git-dir` and `git rev-parse --git-common-dir` as two separate commands and comparing the results, then pick that section automatically, because `docker compose exec` enters a running container that mounts the main checkout and would lint and test a different tree. The command they actually run carries no `$VAR` or `$(...)`: the worktree isolation guard rejects those, so `"$PWD"` is replaced with the literal `pwd` output and the variant carries no `--env-file` (it relies on compose and app defaults; a project that needs env vars gets a literal absolute path added at confirmation time). A page with no such section keeps 1.7.0 behaviour outside a worktree, and inside one the skills stop and point at `/monolynx:project-toolchain`. MON-252: the `## Worktree` section always carries a third field, `izolacja testów: tak|brak` (whether parallel test runs from different worktrees share state such as a fixed database name, port or directory); when the project has an isolation parameter, `project-toolchain` adds it to `test:` with a `<KEY>` placeholder that whoever runs the command replaces literally with the ticket key, and `/monolynx:setup` reports BRAK for a page without the field. MON-249: after resolving the base branch, `work` (substep 2c.1) and `work-simple` (step 0.45) fetch it and, when the working branch is behind `origin/<base>` with no commits of its own and a clean tree, fast-forward it themselves with `git merge --ff-only origin/<base>`, without asking and also under `MONOLYNX_SPRINT_RUN=1`; own commits or a dirty tree mean no merge (the divergence goes into the plan comment), and only a rejected fast-forward is a blocker (`SPRINT-RUN STOP: fast-forward do origin/<base> odrzucony`), never worked around with `pull`, `rebase`, `reset`, `git -C` or a compound command
- Test queue between worktrees (MON-251): `plugin/scripts/test_lock.py` (stdlib only, copied by `scripts/sync_skills.py` into `scripts/` of the `work` and `work-simple` skills only) runs `python3 <skill dir>/scripts/test_lock.py [--timeout <s>] -- <test command>`: it takes an `fcntl.flock` on `<git-common-dir>/monolynx/test.lock`, shared by the main checkout and every worktree (a blocking `flock`, FIFO in practice, no guessing from containers), then runs the command without a shell (argv after `--`). Frozen stderr lines: `TEST-LOCK: acquired`, one `TEST-LOCK: waiting holder=<pid>/<worktree>` (or `holder=unknown`) when the lock is busy, `TEST-LOCK: timeout`. `--timeout` is an integer in 0..86400 (24 h; a larger value is exit 64), default 3600 (60 min), `0` is a single attempt. Exit codes: the command's own code; 75 lock timeout (the command was not run); 64 usage or wrapper-environment error (syntax, `--timeout` out of range, not a git repository, lock file cannot be opened; message `test_lock: ...`, the command was not run); 127 command not found; 126 permission denied; 128+N killed by a signal - a command that itself returns 64/75 is told apart only by the `TEST-LOCK:` / `test_lock:` lines. `work` and `work-simple` wrap every test command (never lint) per `plugin/skills/work/lint-test.md`, unless the `toolchain` wiki page has `izolacja testów: tak` in `## Test`. Exit 75 and an environment collision (mass setup `errors` while the tests narrowed to the changed area are green) are not red tests: no agent fix, no fix-limit use, one rerun for the collision, never a wait loop; a background session ends the turn with `SPRINT-RUN STOP: kolizja testów`. Tests: `tests/unit/test_test_lock.py`, `tests/unit/test_bash_guard.py`, `tests/unit/test_sync_skills.py`
- Full test run locally or in CI (MON-269): the `toolchain` wiki page takes an optional field `pełny przebieg: lokalnie|ci` in `## Test` (ASCII spelling `pelny przebieg:` is equal, the label is case-insensitive, the same field in any other section is ignored), written by `/monolynx:project-toolchain` right under `framework:` and reported by `/monolynx:setup` as information (a missing field is OK with the default `lokalnie`, never BRAK; an unknown value is a warning). A missing field or `lokalnie` keeps the 1.24.0 behaviour of `work` and `work-simple` unchanged. `plugin/scripts/toolchain_fields.py` (stdlib only, copied by `scripts/sync_skills.py` into `scripts/` of the `work`, `work-simple` and `setup` skills only) normalizes the value: `python3 <skill dir>/scripts/toolchain_fields.py --value <raw value>` or `--file <file with the page content>` (exactly one of the two), one JSON line on stdout with the keys `pelny_przebieg` (`lokalnie` or `ci`), `zrodlo` (`pole`, `domyslna`, `nieznana`) and `ostrzezenia`, each warning also on stderr as `toolchain_fields: ostrzezenie: <text>`; exit codes 0 (computed, an unknown or empty value included: it maps to `lokalnie` with a warning, never to `ci`), 2 input error of `--file` (missing file, directory, unreadable, not UTF-8, empty), 64 usage error. In `ci` mode (procedure in `plugin/skills/work/lint-test.md`) lint runs in full, the full-suite test command is never run locally, and the skills run the `test:` command with the test paths of the changed area instead of the default suite path: input `git diff --name-only <BASELINE_SHA>` plus new files from `git status --porcelain --untracked-files=all` (without the flag a new directory collapses to one `?? dir/` line), output the changed and new test files plus the tests matching the changed source files; an empty list is not an error (lint only, noted in the report), while a test command that takes no paths is a blocker. The narrowed runs still go through `test_lock.py` and the `izolacja testów: tak` switch, and defect mode stays local. `ci` needs a merge request, so right after resolving the mode the skills require `MONOLYNX_AUTOCOMMIT`, `MONOLYNX_AUTOPUSH` and `MONOLYNX_AUTOMR` set to `true` and a working `glab`; otherwise a background session ends the turn with `SPRINT-RUN STOP: pełny przebieg ci bez MR` (or `SPRINT-RUN STOP: pełny przebieg ci - testów nie da się zawęzić` for the path blocker) and an interactive session asks once: full local run in this session, or stop. A ticket in `ci` mode reaches `in_review` only after the merge request exists, never without a full run or an MR. After `glab mr create` the procedure in `plugin/skills/work/commit-mr.md` reads `head_pipeline` (`id`, `status`) from `glab mr view <iid> -F json`, with one re-read when the field is still empty and no wait loop, and the skill adds a `**Pełny przebieg (CI)**` comment with the MR URL, the pipeline id and its status at report time; the plan comment carries a `Pełny przebieg:` field. The ticket session neither waits for the MR pipeline nor fixes it: a red MR pipeline has one owner, `/monolynx:mr-queue` KROK 5 (unchanged), except when the user asks for the fix in the same interactive session. Tests: `tests/unit/test_toolchain_fields.py`, `tests/unit/test_sync_skills.py`, `tests/unit/test_plugin_distribution.py`
- Critic through Codex CLI (MON-274): in Claude Code only, `work` (not `work-simple`) can run the critic as a Codex session instead of a Claude `opus` team member. `plugin/scripts/critic_backend.py` (stdlib only, copied by `scripts/sync_skills.py` into `scripts/` of the `work` skill only) has two subcommands. `python3 <skill dir>/scripts/critic_backend.py preflight` (also the call with no arguments) probes `shutil.which("codex")`, `codex --version` and `codex login status` (logged in means exit 0 and a case-sensitive `Logged in`; in detection mode a probe that does not answer in time or cannot start gives `backend=claude` with its own hint, which the skill treats as a normal result, never as an error to fix or a reason to rerun the preflight), always exits 0 and ends with the frozen line `CRITIC: backend=codex|claude codex=<version|none> auth=ok|missing model=<id|inherit>`; with `backend=claude` a `CRITIC-HINT: <reason>` line precedes it. The switch `MONOLYNX_CRITIC` has three modes: empty or `auto` is detection (the probes decide), `codex` is forced mode, and `claude` forces the Claude critic; any other value maps to `claude` with a hint (the unknown literal takes the safe variant). In forced mode the preflight gives `backend=codex` whenever the `codex` binary is on PATH and the model is valid; the version and login probes still fill `codex=` and `auth=` but do not decide, so an unconfirmed probe yields one `CRITIC-HINT: Tryb wymuszony (MONOLYNX_CRITIC=codex): ...` line together with `backend=codex` (e.g. `CRITIC: backend=codex codex=none auth=missing model=inherit`), while a missing binary or an invalid model still gives `backend=claude`. Forcing covers the preflight decision only: the fallback after a failed `run` is unchanged. `MONOLYNX_CRITIC_CODEX_MODEL` must match `^[A-Za-z0-9][A-Za-z0-9._:-]{0,63}$`; empty means `model=inherit` (model from `~/.codex/config.toml`), an invalid value gives `backend=claude`. `run --prompt-file <file> --out <file> --cwd <dir> [--timeout <s>]` (integer 30..3600, default 900) validates the input before any side effect, removes an existing `--out`, and runs `codex exec -C <cwd> --sandbox read-only -c model_reasoning_effort="high" [-m <model>] -o <out> -` with the prompt on stdin, without `--worktree` (the review covers the uncommitted working tree) and without `--json`; on timeout it kills the process group (`SIGTERM`, then `SIGKILL` after 5 s). The verdict file must be UTF-8 and hold the literal `**Code Review**` plus at least one `N/100` score in 0..100, otherwise the content moves to `<out>.rejected`; the script never reads the verdict as APPROVED or NEEDS WORK. Frozen last line: `CRITIC-RUN: status=ok out=<path>` (exit 0) or `CRITIC-RUN: status=error reason=<timeout|exit|verdict|input|disabled|missing>` (exit 2); exit 64 is a usage error with no `CRITIC-RUN:` line. In the skill the whole branch sits inside flat `runtime:claude-code` blocks, so a skill running in Codex never calls `codex exec` (recursion guard; environment detection is ruled out because `CODEX_COMPANION_SESSION_ID` also exists in a Claude Code session). The preflight runs once in KROK 1 and its result (`KRYTYK_BACKEND`) goes into the `Krytyk:` field of the plan comment, the source for a resume. With `backend=codex` the critic is not a team member (no spawn named `krytyk`, the developers' prompt loses the `SendMessage` to the critic) and the review starts in 6.6 like the "Bez Teams" matrix row: the Team Manager writes the full critic prompt to a file outside the repository and calls the wrapper with literal paths, because `bash_guard.py` judges argument text and has no exception for `codex`. A re-review is a fresh wrapper call with the full prompt. Any failed call (exit 2, an unfixable exit 64, a permission refusal, which is possible in a `--bg` session) falls back to the Claude `opus` critic started like the path without Agent Teams, with a `**Krytyk: fallback na Claude Opus**` ticket comment; the review is never skipped or counted as APPROVED, a failed call uses no fix-limit slot, and the fallback is never a `SPRINT-RUN STOP`. The rubric, the threshold of 82, the `REGULA:` lines and the shared limit of 3 fixes are unchanged, and with `backend=claude` the flow is the same as before. In Pipelines the Codex critic job (`agent_type` `codex-critic`) is run by the Team Manager: scores on developer jobs, the verdict in the job log, `attempt` on a re-review, the working time from the Team Manager's stopwatch and the job closure; on fallback the same job gets `failed` with the reason and is then reused with a raised `attempt` by the Claude critic, because a job left as `failed` fails the whole `coding` step. Fixtures captured from codex-cli 0.160.0 live in `tests/fixtures/codex/`.
