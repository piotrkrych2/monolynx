# Architecture: Claude Code plugin (overview, skills, versioning)

Detail moved out of CLAUDE.md. Hooks: `arch-plugin-hooks.md`. Dispatcher and work skills: `arch-plugin-sprint.md`. Merge queue: `arch-plugin-mr-queue.md`. Transport: `arch-plugin-transport.md`.

- Bundles skills (`/monolynx:*` commands), 7 role agents, hooks, and remote MCP access into one installable plugin; marketplace manifest at `.claude-plugin/marketplace.json` (root), plugin manifest at `plugin/.claude-plugin/plugin.json`
- Connector MCP declared in BOTH `.claude-plugin/plugin.json` (`mcpServers`) and `.mcp.json`, with identical literal content (`https://monolynx.com/mcp`, no `${user_config.*}` placeholders - those only expand in Claude Code, elsewhere they break the connector). Auth via OAuth 2.1 + Dynamic Client Registration. The `monolynx` key is part of every tool name (`mcp__monolynx__*`) referenced by all skills - never rename it
- `userConfig`: `mcp_token` (sensitive, optional - only for manual MCP setup), `mcp_endpoint` (used by skills, NOT by the connector), `project_slug` (optional fallback)
- Skill project slug resolution order: `MONOLYNX_PROJECT_SLUG` from project `.env` → `user_config.project_slug` → `"monolynx"`; works cross-project
- Preferred path for Claude Code CLI users; `install_monolynx_skills` remains the manual/fallback path. Plugin only declares access to the existing MCP server; `mcp_server.py` is unchanged. See `plugin/README.md`
- `plugin/scripts/mutation_report.py` (MON-149, plugin 1.9.0) normalizes a mutation-tool report into one survivor model: `--report <file> --format <mte-json|pit-xml|mutmut|cargo-mutants>` (Mutation Testing Elements JSON covers Stryker, Stryker.NET and Infection) prints `{"score", "total", "killed", "survived", "survivors": [{file, line, mutator, original, replacement, status, description}]}` on stdout, stdlib only. Exit codes are 0 OK, 2 input error (missing file, bad JSON/XML, empty or off-schema report), 64 usage error; never a silent empty list, `score` is null only when `total == 0`, invalid mutants (CompileError, Ignored, NON_VIABLE, Unviable, skipped) stay out of `total` and an unknown status counts as a survivor. Fixtures from real runs live in `tests/fixtures/{stryker,pitest,mutmut,cargo-mutants}/`, tests in `tests/unit/test_mutation_report.py`; mutmut requires `mutmut results --all true` output. The script never runs the tool, gates anything or writes files - it is the input for the `mutation-check` skill (MON-150), the CI step (MON-151) and the `work` / `sprint-end` hook-up (MON-152)
- Plugin 1.11.0 (MON-151) adds the `create-mutation-ci-script` skill: it detects the CI system (GitLab, GitHub Actions, Bitbucket, Jenkins) and generates a separate non-blocking `mutation` stage that runs only on MR/PR, in diff mode, publishing the tool report as an artifact. Command, report path and report format come from the `## Mutacje` section of the project's `toolchain` wiki page (contract of `/monolynx:project-toolchain`); a missing page or `komenda diffowa: brak` ends the skill without generating anything. The step never installs the mutation tool (per-ecosystem presence guard, missing tool means a message and `exit 0`), and the hardcoded base branch in the diff command is swapped for the CI variable of the detected system. The ratchet `plugin/scripts/mutation_baseline.py` (copied into `cicd/` next to `mutation_report.py`) compares the run against `cicd/mutation-baseline.json`: statuses `first`, `up`, `same`, `down`, `no-mutants`, `scope-mismatch`, exit code 0 for all of them, frozen last line `MUTATION-BASELINE: status=... score=... baseline=... delta=... survived=... total=... scope=...`. The baseline only grows and is committed by a human from the artifact (CI has no token and does not push); a drop is a visible warning, never a red build, and in diff mode the survivor count is the primary signal because the percentage swings on a handful of mutants
- Plugin 1.14.0 (MON-179) adds the `setup` skill: `/monolynx:setup` (no arguments) is a project configuration checklist covering the project slug, the `toolchain` wiki page, the LLM Wiki method, the code graph and mutation testing in CI, and the `MONOLYNX_*` flags (including `MONOLYNX_BASE_BRANCH` and `MONOLYNX_MR_TARGET`, with a warning when both are set to different branches). It marks each item OK or BRAK and, only with the user's consent, delegates the fix to the matching skill (`project-toolchain`, `wiki-init`, `create-graph-ci-script`, `create-mutation-ci-script`; a project without CI can run `graph-sync` itself instead of the graph CI step); the skill itself is read-only (one exception since MON-232: allowlist entries for the CLI, see "Skill transport" below) and reports the autonomy flags without ever setting them. In the same release `/monolynx:help` became a map of at most 100 lines: 6 groups (Setup, Planowanie, Praca, Integracja, Sprint, Wiki), one line per skill with its `argument-hint`, the manual and autopilot (`/loop` over `sprint-run` + `mr-queue`) work paths, and `/monolynx:next` as the first command to remember; the variable table, runtimes, the `work` vs `work-simple` comparison and per-skill details live in `plugin/README.md`. Every skill-count phrase (`main.py`, `mcp_guide.html`, `how-to-use-monolynx.md`, `plugin/README.md`, `agent-bootstrap.md`) must equal the number of `plugin/skills/*/SKILL.md` directories, enforced by `tests/unit/test_skill_counters.py`
- MON-181 adds `/monolynx:next`, a read-only router over git, ticket, sprint, sessions, MR and configuration. It recommends 1-3 commands with reasons and ends with `NEXT: <command>`; it never executes the recommendations or changes state. The plugin remains version 1.14.0 and contains 23 skills.
- MON-265 adds the `blog-post` skill (the plugin now contains 24 skills): `/monolynx:blog-post [temat | page_id szkicu]` takes a blog post through KROK 0-6: slug, transport, session mode and argument, brief (reader, the question the post answers, language, sources), outline, draft as a private wiki page under the parent page titled `Blog` (`create_wiki_page(..., is_public=false)` + `set_blog_post_meta`; with no such page or more than one the skill asks instead of creating it), a `lint_blog_post` loop until `error_count` is 0 (at most 5 rounds, then the remaining errors are reported), the preview address `<instance>/dashboard/<slug>/wiki/pages/<page_id>/blog-preview` (instance from `MONOLYNX_URL`, then the client's `mcp_endpoint` without `/mcp`, then `https://monolynx.com`), and publication. `publish_blog_post` appears only in `## KROK 6` and is called only with zero lint errors and after the user's explicit consent in the current turn, by default without `force`; `force=true` is passed only when the user, unprompted and explicitly, asks to publish despite the errors after seeing their list in the refusal, and the skill never proposes it first. A lint-gate refusal goes back to the lint loop and voids the consent. Under `MONOLYNX_SPRINT_RUN=1` KROK 6 is skipped as a whole and the skill ends at the KROK 5 report (draft, lint result, preview address), so a background session has no path to publication; every question becomes an assumption written to the report or a `SPRINT-RUN STOP: <reason>` line. A UUID argument resumes an existing draft. An already public post (`is_public` true) is edited only after the user's explicit "tak", once the skill has said that every content change is visible publicly at once; under `MONOLYNX_SPRINT_RUN=1` the turn ends with `SPRINT-RUN STOP` and nothing is written. Blog permission (MON-270): setting the metadata and publishing need the account-level `blog:write`, granted only by a superuser on the account edit page `/dashboard/users/{user_id}`. On the refusal `Brak uprawnienia blog:write`, or when the blog write tool is missing from the MCP tool list, the skill stops, asks the user to have a superuser grant the permission, and never works around it through `update_wiki_page` with `is_public` (that path has the same gate); under `MONOLYNX_SPRINT_RUN=1` it ends the turn with a `SPRINT-RUN STOP` line. The block syntax has one source, the public guide `src/monolynx/static/blog-authoring.md` (English, Polish examples; served at `/blog-authoring.md` by `main.py::blog_authoring`, listed in `robots.txt`, the sitemap, `llms.txt` and the landing markdown): H2 sections `## Block catalog` (one `### \`name\`` per block of `blog_blocks.py`, 19 in total, no other `## ` line inside), `## Lint rules` (table `Rule | Level | What it checks` over the codes of `blog_lint.py`), `## Markdown twin` and `## Connector operations`. `scripts/sync_skills.py` cuts the `## Block catalog` section out of the guide (`block_catalog()`, `ValueError` on a missing or empty section) and writes it as `references/bloki.md` of the `blog-post` skill, in the plugin and in `src/monolynx/static/skills/`; that file is generated and never edited by hand. `tests/unit/test_blog_authoring_guide.py` keeps the guide equal to the code (every block and every lint code present, nothing extra) and checks the skill contract (publication only in KROK 6, the `MONOLYNX_SPRINT_RUN` condition, the `help` line with the `argument-hint`)
- Plugin versioning (MON-177, `.claude/rules/plugin-version-bump.md`): a ticket never bumps the version. It adds its changelog entry under `### Unreleased` at the top of `## Changelog` in `plugin/README.md`, every top-level bullet prefixed with the ticket key (`- MON-123: ...`), and leaves `plugin/.claude-plugin/plugin.json` and `plugin/.codex-plugin/plugin.json` alone; `work` and `work-simple` paste this rule into every developer prompt as the shared block `changelog-unreleased`. The merger assigns the number: minor for a new skill, hook or script since the last release, patch otherwise, `Unreleased` -> `X.Y.Z` plus both manifests in one commit. When tickets merge into an integration branch (`MONOLYNX_MR_TARGET`, the dispatcher's target mode) the number is assigned on that branch before it merges to `main`, so `main` never sees `Unreleased`; when a ticket merges straight to `main`, the merger bumps on the MR branch before merging (a human - `mr-queue` does not do it), and `sprint-end` targeting `main` is only a safety net after a merge without a number. The bump is done by the `version-bump` job (4c) of `/monolynx:sprint-end`, which proposes the number, asks (no question under `MONOLYNX_SPRINT_RUN=1`, since the result still waits for a human MR merge), prepares `release/plugin-X.Y.Z` in a separate worktree from `origin/<target>`, checks it with `validate_plugin_consistency.py --release` and commits/pushes/opens the MR per `MONOLYNX_AUTOCOMMIT`/`AUTOPUSH`/`AUTOMR`. Exception: a hotfix released on its own may take a number if it is the only open MR changing the plugin, recorded in the plan comment. `scripts/validate_plugin_consistency.py` accepts `### Unreleased` as the first entry on a branch (the manifest version must then equal the first numeric `### X.Y.Z` below it) and rejects it in release mode (`--release` or `CI_COMMIT_BRANCH=main`, so the `plugin-consistency` job on `main` goes red after a merge without a number); in both modes `Unreleased` in a later position, an empty section or a bullet without a ticket key is an error. Release mode also rejects a tracked `.claude/settings.json` carrying `MONOLYNX_SPRINT_RUN`, `MONOLYNX_BASE_BRANCH` or `MONOLYNX_MR_TARGET` in `env` (MON-207): `sprint-run` passes `MONOLYNX_SPRINT_RUN=1` inline to each child session, the branch flags live in the dispatcher's environment or `settings.local.json`, and `version-bump` restores `env` from `main` before the release commit
- LLM Wiki skills added in plugin 1.1.1: `wiki-init` (runs `bootstrap_wiki_llm`), `wiki-ingest` (the INGEST workflow), `wiki-lint` (the audit workflow); the existing `search` skill is extended with QUERY (writes the answer back into the wiki)
