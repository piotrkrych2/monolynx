# Architecture: mr-queue skill

Detail moved out of CLAUDE.md.

- Plugin 1.13.0 adds the `mr-queue` skill: `/monolynx:mr-queue [!iid | #pr | URL ...]` is one idempotent tick over a merge queue kept in `$(git rev-parse --git-common-dir)/monolynx/mr-queue.json`. It takes the first unmerged MR (GitLab, `glab`) or PR (GitHub, `gh`) and does exactly one action in the user's order: conflict -> merge the target branch into the MR branch (conflict resolution subagent with `model="opus"`) -> red CI -> fix in a temporary detached worktree (`git worktree add --detach`, subagent with `model="sonnet"`, push `HEAD:refs/heads/<branch>`, never force/rebase, max 2 rounds) -> missing approval -> ask the user (chat approval is bound to the head SHA; batch mode ends with `MR-QUEUE STOP: <ref> <reason>`) -> ready -> merge with `--sha` / `--match-head-commit` and no auto-merge. After a merge into the repository's default branch the item goes to `merging` and the queue waits for green CI on the target branch before the next item; after a merge into an integration branch (target differs from the default branch, e.g. `sprint/*`; decided by `post-merge --target-branch T --default-branch D`, an unknown default branch means `merging`) the same tick closes the item at once on the strength of the MR's own green CI (MON-233, replacing the `verifying` path of MON-221): `post-merge` returns `{"status": "done", "close_now": true}` for an integration branch and `{"status": "merging", "close_now": false}` otherwise, never `verifying`; the tick moves the ticket to `done` (the comment names the MR pipeline, not the branch pipeline), fast-forwards the local target branch, sets the item to `done`, and as part of the same action cancels the integration-branch pipeline triggered by the merge push (`glab ci cancel pipeline <id>` / `gh run cancel`). The ids come from `target-cancel` (`--provider glab --pipelines-file P` or `--provider gh --runs-file R`) -> `{"cancel": [...], "skipped": [{"id", "status"}], "reason"}`, which picks only merge-commit pipelines/runs in an active status and puts every other or unknown status into `skipped` (canceling is irreversible); a missing pipeline or a failed cancel is a warning in the report, never a queue stop. The `verifying` status is still recognized when reading an existing queue file (field `verifying` in `queue-show`), and the first tick closes such leftover items the same way without waiting for branch CI. Red CI on the target branch in the `merging` path (default branch only) sets `stopped` without a `stop_reason`, as before. No new merge sets `stop_reason=target_ci_failed` any more (only the old step 3.0 did), so the output field `halted` now comes only from a `stopped` item with `stop_reason=target_ci_failed` left in the queue file by the 1.22.0 path; it blocks the queue until a human runs `queue-update --ref <ref> --status closed`. The same closing and pipeline cancel also apply to an MR/PR merged outside the queue (`merged` verdict) into an integration branch; on the default branch the ticket goes to `done` only after green CI of the target branch. Since MON-220 a conflict wins over every CI state: the `conflict` verdict carries `pipeline_id`/`pipeline_status`, and the tick cancels the active MR pipeline (`glab ci cancel pipeline <id>` / `gh run cancel`) before merging the target branch; a pipeline canceled on the MR head without a conflict yields `needs_human` and is never retried (canceling is a human decision). The shared closing step (on green target-branch CI in the `merging` path, right after the merge on an integration branch; before `queue-update --status done`) fast-forwards the local target branch in the user's main checkout via `target-sync`: `git merge --ff-only origin/<b>` when the checkout is on `<b>` and clean, `git fetch origin <b>:<b>` when it is on another branch, a warning with a manual command on local commits, uncommitted changes or any git error - never reset/rebase/stash/force; this is the only exception to "the user's checkout stays untouched" (MON-219). Without arguments it proposes the queue from open MRs/PRs (stacked MR right after its base, oldest first, drafts and their children skipped). Verdicts come from `plugin/scripts/mr_queue_state.py` (`queue-propose`, `queue-set`, `queue-show`, `queue-update`, `classify`, `target-ci`, `ticket-key`, `target-sync`, `post-merge`, `target-cancel`, and `config-check`, which the preflight uses to reject different `MONOLYNX_BASE_BRANCH` / `MONOLYNX_MR_TARGET` with exit 2), stdlib only, exit codes 0/2/64, literals derived from captured `glab 1.100.0` / `gh 2.100.0` output in `tests/fixtures/{glab,gh}/` (runner IPs redacted); an unknown literal maps to `wait`, never `ready`. GitLab `approved=true` with `approvals_required=0` and empty `approved_by` is not an approval; a target-branch pipeline in status `manual` (manual `deploy-staging`) counts as green when no automatic job failed. Frozen last line `MR-QUEUE: remaining=<n> current=<ref> verdict=<v> done=<d>`; env `MONOLYNX_AUTOMERGE`, `MONOLYNX_MERGE_METHOD` (`merge`/`squash`/`rebase`). Tests: `tests/unit/test_mr_queue_state.py`
