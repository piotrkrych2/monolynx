# Architecture: skill transport (CLI or MCP)

Detail moved out of CLAUDE.md. Rule: `skill-transport.md`.

- Skill transport (MON-232, `.claude/rules/skill-transport.md`): a `mcp__monolynx__<tool>(...)` line in a skill names an operation, not a channel. Skills run it through the `monolynx` CLI when the CLI is installed and logged in, and through the MCP tool of the same name otherwise; the CLI is never required. `plugin/scripts/monolynx_transport.py [--session-id ID]` is the preflight, run once per skill start: always exit 0 (64 usage), at most one `TRANSPORT-HINT: ...` line (missing CLI > not logged in > update available; once per session via a marker under `~/.cache/monolynx/transport-hint/`, never under `MONOLYNX_SPRINT_RUN=1`) and the frozen last line `TRANSPORT: mode=cli|mcp cli=<version|none> auth=ok|missing latest=<version|unknown> update=yes|no install=brew|pipx|uv|unknown|none`. `plugin/scripts/monolynx_op.py <op> --project_slug <slug> [--<param> <value>]` is the wrapper: `<op>` is the MCP tool name and flags are its exact parameter names (`-` reads stdin, `@<path>` a file, lists as a JSON array), mapped onto CLI commands by the `OPS` table (36 operations: 25 ticket, sprint and wiki ones plus, since MON-248, the 5 graph reads `list_graph_nodes`, `get_graph_node`, `query_graph`, `find_graph_path` and `get_graph_stats`, and, since MON-261, the 3 blog ones `list_blog_posts`, `get_blog_post` and `set_blog_post_meta`, mapped onto `blog list`, `blog get` and `blog meta`, where a `tags` JSON array becomes repeated `--tag` and an empty array `--no-tags`, and, since MON-262, the read `lint_blog_post`, mapped onto `blog lint` with `page_id` as the positional argument, and, since MON-263, the writes `publish_blog_post`, mapped onto `blog publish` (`force` true becomes the `--force` flag, false sends no flag), and `unpublish_blog_post`, mapped onto `blog unpublish`, both with `page_id` as the positional argument; checked against captured `--help` fixtures in `tests/fixtures/monolynx/`). Exit codes: 0 with API v2 JSON on stdout, 3 with the last line `OP-FALLBACK: mcp tool=<op>` (use the MCP tool; nothing was written), 2 operation error (a write may have reached the server, never retry blindly), 64 usage. One exception to "CLI exit code 1 is wrapper exit code 2" (MON-262): `blog lint` prints the report and then exits with 1 when the post has a lint error, so for `lint_blog_post` a CLI exit code 1 whose stdout is a JSON object with an `issues` list is passed through as wrapper exit code 0 (the report is the result, and the caller reads `error_count` or the levels in `issues`); any other exit code 1 stays an operation error (exit 2). `lint_blog_post` is in `READ_OPS` and in `MONOLYNX_READ_OPS` of `bash_guard.py`. `publish_blog_post` and `unpublish_blog_post` are writes and are in neither set; a publication refused by the lint is a 422, so CLI exit code 1 and wrapper exit code 2 with the reason on stderr (the `lint_blog_post` exception does not apply). Pipelines, `log_time`, `get_work_report`, the graph write tools (`replace_graph`, `create_*`, `delete_*`, `bulk_create_*`) and the LLM Wiki tools always go through MCP; under `mode=cli` skills read the graph through the CLI, and `find_graph_path` without `source_id` or `target_id` is exit 64 before the CLI is called. Since MON-246 the CLI JSON of `get_ticket` carries `spec_page_id` and each `list_tickets` item carries `blocked_by`, so skills read both from the wrapper output. Since MON-247 the wrapper also takes `compact` (`list_tickets`) and `brief` (`create_ticket`, `update_ticket`), mapped onto the CLI flags `--compact` and `--brief`; they are wrapper parameters that the MCP tools do not have, so under `mode=mcp` and on an `OP-FALLBACK` the tool is called without them. `MONOLYNX_TRANSPORT=mcp` forces MCP (preflight `mode=mcp`, wrapper exit 3) and is the off switch. The instruction block between `<!-- shared:transport -->` and `<!-- /shared:transport -->` (exactly one pair in each of the 19 skills whose `SKILL.md` contains `mcp__monolynx__`, `blog-post` included since MON-265; `brief`, `help`, `resume`, `retro` and `create-graph-ci-script` have none) is generated: its only source is `plugin/references/transport.md`, injected by `scripts/sync_skills.py`, which also copies both scripts into `scripts/` of every marked skill; `tests/unit/test_skill_transport_block.py` guards the markers. `/monolynx:setup` gains a seventh item, "CLI `monolynx`" (installed, logged in, up to date, Bash allowlist), prints the install/login/upgrade command for the user to run, and adds the proposed allowlist patterns (`Bash(python3 *scripts/monolynx_op.py *)`, `Bash(python3 *scripts/monolynx_transport.py*)`, `Bash(monolynx *)`) to a settings file only after separate explicit consent - its single own write.
