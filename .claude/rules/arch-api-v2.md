# Architecture: API v2, schemas, MCP parity

Detail moved out of CLAUDE.md. Rule for new tools: `mcp-cli-parity.md`.

**API v2** (`api/v2/`): skeleton REST API under `/api/v2`, foundation for domain endpoints (MON-142). `api/v2/__init__.py` - `router` (placeholder root available both with and without a trailing slash - `GET /api/v2/` and `GET /api/v2`, no redirect between them; `/api/v2/openapi.json` + `/api/v2/docs` built exclusively from `router`'s own routes; the `/me` router (`api/v2/me.py`, MON-125) included via `router.include_router(me_router)`; a catch-all `/{full_path:path}` registered last, handling GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS and returning 404 problem+json for any unmatched v2 path - HEAD/OPTIONS must be listed explicitly, otherwise Starlette treats the request as a path match with the wrong method and returns 405 instead of 404) and `register_api_v2(app)` (a pure ASGI `X-Request-Id` middleware class, registered via `app.add_middleware`, deliberately not `@app.middleware("http")`/`BaseHTTPMiddleware` because MCP is mounted at `/` and serves streamable HTTP/SSE that a buffering middleware would break; plus problem+json exception handlers for `ApiV2Error`/`HTTPException`/`RequestValidationError`. Both the middleware and the handlers use one shared boundary helper, `_is_v2_path()` (`path == "/api/v2"` or `path.startswith("/api/v2/")`), so a route under an unrelated prefix like `/api/v2foo` is never mistaken for v2; outside that boundary the handlers delegate to FastAPI's default handlers, so the dashboard and API v1 keep their existing `{"detail": ...}` format). The `HTTPException` handler preserves `exc.headers` (e.g. `Allow`, `WWW-Authenticate`) in the problem+json response. `api/v2/deps.py` - `get_api_user()` (authorizes `Authorization: Bearer <token>` via `verify_bearer_token()`, every 401 problem+json response carries `WWW-Authenticate: Bearer` per RFC 6750) and `get_api_user_and_project()` (active project by slug + membership check, 404/403 problem+json). `api/v2/errors.py` - `ApiV2Error(status, title, detail=None, type="about:blank", headers=None)`, with `headers` propagated to the response the same way as `headers` on `fastapi.HTTPException`. `api/v2/me.py` - `GET /me` (MON-125), protected by `get_api_user`, returns `MeResponse(id, email)` for the token's owner; 401 problem+json comes from `get_api_user` itself.

**API v2 domain routers** (MON-142): `api/v2/projects.py`, `tickets.py`, `sprints.py`, `wiki.py`, `graph.py` (MON-248, read-only) and `blog.py` (MON-261) are thin FastAPI routers with no prefix of their own, attached via `include_router` to `router` in `api/v2/__init__.py` BEFORE the catch-all. They map MCP tools 1:1 (Projects 11, Tickets 14 incl. `get_board`, comments and acceptance criteria, Sprints 7 incl. `get_burndown`, Wiki 8, Graph 5 reads, Blog 4) onto the same service functions (`services/projects.py`, `services/tickets.py`, `services/sprint.py`, `services/burndown.py`, `services/wiki.py`, `services/embeddings.py`, `services/graph.py`, `services/blog.py`, `services/blog_lint.py`), so business logic lives in one place. Request/response schemas live in `schemas/api_v2/`.
- Blog post metadata (MON-261): `api/v2/blog.py` exposes 6 routes under `/projects/{slug}/blog/posts`, one per tool: three over `services/blog.py`, since MON-262 the lint over `services/blog_lint.py`, and since MON-263 publish and unpublish over `services/blog.py` (the last three described at the end of this entry): `GET .../blog/posts` (`list_blog_posts`; optional `status=published|draft`, `PaginatedResponse[BlogPostResponse]` with the default `per_page=100` through `paginate()`), `GET .../blog/posts/{page_id}` (`get_blog_post`; `BlogPostDetailResponse`, the same fields plus `content`) and `PATCH .../blog/posts/{page_id}` (`set_blog_post_meta`; `BlogPostResponse`). Schemas in `schemas/api_v2/blog.py`; `BlogPostMetaUpdateRequest` has `slug`, `description`, `author_name`, `tags`, `lang`, `translation_of_id`, `cover_attachment_id` and `last_verified_at`, all optional, and deliberately neither `published_at` nor `is_public`. The PATCH body goes to `set_post_meta` through `model_dump(exclude_unset=True)`: an absent field stays unchanged, `null` clears `translation_of_id`, `cover_attachment_id` and `last_verified_at` and is a 422 for the other fields, `"tags": []` clears the tags, and `{}` is 200 with no change. The service checks the permission first (`wiki:read` for both GETs; `wiki:write` and then the account-level `blog:write` for PATCH, MON-270), so a role or an account without it gets 403 for a nonexistent `page_id` too; a page outside the project (`Strona wiki nie istnieje`) and a wiki page without a `BlogPost` row (`Wpis bloga nie istnieje`, added to the not-found list of `service_error()`) are 404, an unknown `status` and a validation error are 422, and a malformed `page_id` is 422 from FastAPI validation. `public_url` and `markdown_url` are `null` for a non-public page. Only the detail GET reads the content from MinIO: a storage error there is logged (`logger.exception`) and answered with 503 problem+json (`title` "Service Unavailable", `detail` "Treść wpisu jest chwilowo niedostępna"), never 500; the list and PATCH do not read MinIO. Post lint (MON-262): `GET .../blog/posts/{page_id}/lint` (`lint_blog_post`) calls `lint_post_by_id` and returns `BlogLintResponse` (`page_id`, `score`, `error_count`, `warning_count`, `info_count`, and `issues`, a list of `BlogLintIssueResponse` with `rule`, `level`, `line`, `message`), without the `table` field of the MCP tool (a `known_differences` entry in the parity map). It is a pure read with the same order and errors as the detail GET: `wiki:read` first (403 for a nonexistent `page_id` too), 404 for a page outside the project and for a page without a `BlogPost` row, 422 for a malformed `page_id`, and, because it reads the content from MinIO as well, a logged storage error answered with 503 problem+json. A post with lint errors is still 200: the errors are the result, not a failure. Publication (MON-263): `POST .../blog/posts/{page_id}/publish` (`publish_blog_post`) takes an optional JSON body `BlogPublishRequest` (`force`, default `false`; no body means `false`), calls `publish_post` and returns `BlogPublishResponse`, the fields of `BlogPostResponse` plus `lint` (a `BlogLintResponse`); `POST .../blog/posts/{page_id}/unpublish` (`unpublish_blog_post`) takes no body, calls `unpublish_post` and returns `BlogPostResponse`. The service checks `wiki:write` and then the account-level `blog:write` (MON-270) first in both, before the page lookup and before the lint, so a role without `wiki:write` or an account without the blog permission gets 403 problem+json (`detail` "Brak uprawnienia wiki:write" / "Brak uprawnienia blog:write") for a nonexistent `page_id` too, and nothing is written. Publish: a refusal by the lint (lint errors without `force`) and a slug collision with a public page are service `ValueError`s, so 422 problem+json with the message in `detail`, and the page stays private; a page outside the project is 404; a page without a `BlogPost` row gets one; the lint reads the content from MinIO, so a storage error is logged and answered with 503 problem+json, like the lint route. Unpublish: 404 for a page outside the project and for a page without a `BlogPost` row, 200 for an already private post; it does not read MinIO. A malformed `page_id` is 422 in both. Tests: `tests/integration/api_v2/test_blog.py`
- `api/v2/common.py` - `service_error()` maps a service `ValueError` to problem+json: 404 for a closed list of "resource from the path does not exist" messages (full match, so e.g. an invalid blocker in the body stays 422), 403 for messages starting with "Brak uprawnienia", 422 otherwise (usage: `except ValueError as exc: raise service_error(exc) from exc`). Role permissions are enforced in both channels (MON-241): membership from `get_api_user_and_project()` is no longer enough for the Scrum and Wiki routes. Service functions that take `(db, user, project, ...)` call `ensure_permission()` from `services/permissions.py` themselves; it raises `ValueError("Brak uprawnienia {module}:{action}")`, which `service_error()` maps to 403, so every endpoint calling such a service needs the `except ValueError` clause above (without it the refusal is a 500). `require_permission(db, user, project, module, action)` (403 problem+json with the same text in `detail`) stays in the router for service functions that take no user (`start_sprint`/`complete_sprint` - `scrum:write`, burndown - `scrum:read`, wiki page create/update - `wiki:write`, wiki page delete - `wiki:delete` and, since MON-272, `blog:write` when the page or any of its descendants is public (`wiki_service.ensure_can_delete_page()` after the page lookup, 403 problem+json with `detail` "Brak uprawnienia blog:write", nothing deleted), wiki search - `wiki:read`) and for the 5 endpoints that had it before (update/delete project - `settings:write`/`settings:delete`, invite/remove member - `users:write`/`users:delete`, `set_wiki_config` - `settings:write`). Permission map: reads -> `scrum:read` / `wiki:read`, creates and updates -> `scrum:write` / `wiki:write`, `delete_ticket`, `delete_acceptance_criterion` and `delete_wiki_page` -> `scrum:delete` / `wiki:delete`; publishing has a separate, account-level permission (MON-270): `is_public=true` in `POST .../wiki/pages`, any change of `is_public` in `PATCH .../wiki/pages/{page_id}` (publishing and unpublishing) and, since MON-271, a `PATCH` that changes the title or the content of an already public page need `blog:write` on top of `wiki:write`, the same rule as the dashboard form and the MCP tools, and so do the three blog write routes (PATCH post metadata, publish, unpublish). `blog:write` is not a role permission: it is `User.can_edit_blog` (a superuser always has it), checked by `ensure_blog_permission()` in `services/wiki.py` and `services/blog.py`, whose `ValueError("Brak uprawnienia blog:write")` goes through `service_error()` to 403 like any other refusal; a refused request writes nothing. The check is the first thing the handler and the service do, before the resource lookup and before any validation of their own, so a role without the permission gets 403 for a nonexistent resource too and cannot tell 404 from 403. FastAPI's request validation still runs before the handler: a malformed UUID in the path or an invalid body yields 422 regardless of the role. An endpoint that reads the resource back after a write (`POST`/`PATCH` tickets -> `get_ticket`, start/complete sprint -> `get_sprint`) checks `scrum:write` and then `scrum:read` in the router before the write, so a role with write but no read is refused before anything is committed. This is a known channel difference: the MCP tools `create_ticket`, `update_ticket`, `start_sprint` and `complete_sprint` check only `scrum:write`, so such a role writes through MCP while v2 refuses. `get_project_summary` still checks membership only. Tests: `tests/integration/test_rbac_scrum_wiki_channels.py` (roles member, read-only and owner through MCP and v2). `paginate()` pages lists the service returns in full. A malformed `page_id`, `sprint_id` or `member_id` yields 422 problem+json (FastAPI validation of a `uuid.UUID` parameter, or a `ValueError` mapped by `service_error()`), while a malformed `ticket_id` (UUID or key) or `criterion_id` yields 404, because their messages are on the not-found list of `service_error()`
- Conventions: lists return `PaginatedResponse[T]` (`list_tickets`/`search_tickets` with `per_page=20` like the tools, all other lists default to `per_page=100`); `search_wiki` and `get_board` are not paginated. `ticket_id` in the path accepts a UUID or a key (e.g. `MON-12`). The static routes `/tickets/search` and `/tickets/bulk` are registered before `/tickets/{ticket_id}`. `DELETE .../members/{member_id}` takes the `user_id` returned by `list_members` (the service takes an email, the router resolves it). `POST .../members` sends the invitation email in the router (`send_invitation_email`, like the MCP wrapper), because the service does not. Acceptance criteria are nested under the ticket. `GET .../burndown` without `sprint_id` uses the active sprint. `start_sprint`/`complete_sprint` return an error as a string, which the router turns into problem+json. Ticket blockers and spec page (MON-246): every item of `GET .../tickets` carries `blocked_by`, a list of `{id, key, title, status}` (empty when the ticket has no blockers), and the ticket detail (`TicketDetailResponse`, returned by get/create/update) adds `spec_page_id` (UUID string or `null`) next to `blocks`; `search_tickets` items carry neither. Compact list (MON-247): `GET .../tickets?compact=true` returns items without `description` through a separate schema, `TicketListItemCompact` (the fields of `TicketListItem` minus `description`), so `TicketListItem` and the default response stay unchanged
- Graph reads (MON-248): `api/v2/graph.py` exposes 5 GET routes under `/projects/{slug}/graph`, one per read tool (`list_graph_nodes`, `get_graph_node`, `query_graph`, `find_graph_path`, `get_graph_stats`), calling the same `services/graph.py` functions: `/graph/nodes` (`type`, `search`, `limit` 1..1000 default 100; a bare JSON list, not paginated), `/graph/nodes/{node_id:path}` (`depth` >= 1, default 1, capped at 5 by the service, repeatable `relation_types` and `node_types`; `{node, nodes, edges, depth_map}`; the `path` converter is there because node ids may contain `/`), `/graph/query` (`node_type`, `search`, `limit` 1..1000 default 200; `{nodes, edges}`), `/graph/path` (required `source_id` and `target_id`; `{nodes, edges}`, empty lists when there is no path) and `/graph/stats` (`total_nodes`, `total_edges`, `nodes_by_type`, `edges_by_type`). Schemas in `schemas/api_v2/graph.py`; an edge lifts `confidence` and `source_relation` out of `metadata` to the top level and keeps `metadata` intact. The shared dependency `graph_project` fixes the order of checks: token 401, project 404, membership 403, `connections:read` 403 (`require_permission()`), then graph disabled (`ENABLE_GRAPH_DB=false`) 503. A Neo4j failure during the call (`RuntimeError`, `DriverError`, `Neo4jError`) is also 503 problem+json, never 500; a `depth` below 1 or a `limit` outside 1..1000 is 422 from FastAPI validation, before the service is called; a service `ValueError` goes through `service_error()` (422), and a missing node is 404 "Node nie istnieje". Two pure helpers in `services/graph.py` are shared by MCP and v2: `ensure_search_not_blank()` (a blank `search` is an error in both channels) and `format_graph_dsl()` (the MCP tools return this Arrow DSL text, v2 returns the JSON it is built from). Graph writes (`create_*`, `delete_*`, `bulk_create_*`, `replace_graph`) have no v2 endpoint and no CLI command: the only writer is the `cicd/sync_graph.py` sync through MCP
- Tests: `tests/integration/api_v2/` (one file per resource)
- Purpose and layering: API v2 is the REST API for the `monolynx` CLI (`cli/`) and external integrations. Auth is shared with MCP: `api/v2/deps.py::get_api_user` calls the same `verify_bearer_token()` from `services/mcp_auth.py` as the MCP server, so one token (OAuth access token or legacy `osk_*`) works in both channels. Every error is `application/problem+json` (`type`, `title`, `status`, `detail`, `instance`). Business logic lives in `services/`; the MCP tools in `mcp_server.py` and the v2 routers are thin adapters over the same service functions, and a service `ValueError` becomes MCP error text or a v2 problem+json via `service_error()`. Unlike `/api/v1` (Django SDK event ingest with the `X-Monolynx-Key` project API key, health check, issue status), v2 authenticates a user, and every project route also checks membership (`get_api_user_and_project()`); on top of membership the Scrum and Wiki routes check the role permission (`scrum:*` / `wiki:*`, MON-241, see `api/v2/common.py` above), the same one the MCP tool checks, and the graph routes check `connections:read` (MON-248)
- Parity MCP <-> v2 (MON-131): `tests/integration/tool_endpoint_map.py` maps each MCP tool either to its v2 endpoint in `TOOL_TO_ENDPOINT` (`ToolEndpointSpec`: `method`, `path`, `is_write`, `field_map`, `known_differences`) or to a reason in `INTENTIONALLY_UNMAPPED`; `tests/integration/test_api_v2_parity.py` (`TestMapCompleteness`) fails on any registered tool missing from both dictionaries or on a mapped route absent from `/api/v2/openapi.json`, and `TestToolEndpointParity` runs one scenario per mapped tool through both channels. Since MON-263 (`publish_blog_post` and `unpublish_blog_post`, the fifth and sixth blog tools after the 3 of MON-261 and `lint_blog_post` of MON-262) the map holds 51 mapped tools and 74 intentionally unmapped ones (asserted in `test_every_mcp_tool_has_exactly_one_entry`); the 7 graph write tools are unmapped with one shared reason (the graph is written only by the `cicd/sync_graph.py` sync through MCP). The rule for new tools: `.claude/rules/mcp-cli-parity.md`

**Schemas** (`schemas/`) - Pydantic models for validation: `events.py`, `issues.py`, `scrum.py`, `time_tracking.py` (includes `WorkReportResult` for aggregated reports), `graph.py` (GraphNodeCreate/Update/Response, GraphEdgeCreate/Response, GraphSearchResult), `wiki.py` (`WikiBacklinkResponse`), `pipelines.py` (list-item and full-tree response builders for the live JSON API: `build_list_item`, `build_pipeline_response`); `schemas/api_v2/` - API v2 request/response schemas: `pagination.py` (`PaginatedResponse[T]` using PEP 695 generic syntax: generic envelope `{"items", "page", "per_page", "total", "total_pages"}`) plus per-resource modules `project.py`, `ticket.py`, `sprint.py`, `wiki.py` (MON-142), `graph.py` (MON-248, response-only: `GraphNodeResponse`, `GraphEdgeResponse`, `GraphSubgraphResponse`, `GraphNodeDetailResponse`, `GraphStatsResponse`) and `blog.py` (MON-261: `BlogPostResponse`, `BlogPostDetailResponse`, `BlogPostMetaUpdateRequest`; MON-262: `BlogLintResponse`, `BlogLintIssueResponse`; MON-263: `BlogPublishRequest`, `BlogPublishResponse`)

## Decisions

- MCP / API v2 / CLI parity: one shared service layer (`services/`), two frontends over it (MCP tools and API v2 endpoints) plus the CLI on top of v2. A new or changed MCP tool comes with its v2 endpoint and CLI command in the same ticket, or with an explicit entry and reason in `INTENTIONALLY_UNMAPPED` (`tests/integration/tool_endpoint_map.py`); `tests/integration/test_api_v2_parity.py` enforces that every tool is in the map, but not that the CLI command or its `cli/README.md` description exists. See `.claude/rules/mcp-cli-parity.md`
