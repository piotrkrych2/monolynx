# Architecture: Wiki module and LLM Wiki

Detail moved out of CLAUDE.md. Blog metadata service: `arch-blog-service.md`. Blog permission: `arch-rbac-mcp.md`.

## Dashboard router

- `dashboard/wiki.py` - Wiki module: page CRUD, tree hierarchy, markdown rendering, image upload to MinIO, semantic search via pgvector (`/dashboard/{slug}/wiki/*`); page detail shows an "incoming links" (backlinks) panel, gated on `wiki_llm_enabled`. Blog authoring in the dashboard (MON-264), the human counterpart of the `set_blog_post_meta` connector:
  - Post metadata form: the edit form (`templates/dashboard/wiki/page_form.html`) has a section `<details id="blog-meta-section">` titled "Wpis na blogu" with the fields `blog_slug`, `blog_description` (max 300, with a character counter), `blog_author_name`, `blog_tags` (comma-separated), `blog_lang` (pl/en), `blog_translation_of_id`, `blog_cover_attachment_id` (picked from the page attachments) and `blog_last_verified_at`, plus the hidden marker `blog_meta=1`. The section is open when `blog_is_post` (the page has a `BlogPost` row or is public) and absent on the two create forms (`blog_meta` is `None` there, there is no page yet). Template context of the edit form: `blog_meta` (dict of strings; without a `BlogPost` row the slug is the page slug, the author `DEFAULT_AUTHOR_NAME`, the language `pl`), `blog_is_post`, `blog_translation_candidates` (dicts `{page_id, title, lang}` for the other pages of the project that have a `BlogPost` row, ordered by title), `attachments`, `block_templates` and `image_upload_url`, all built by `_edit_form_context`; the create forms use `_creation_form_context` (`blog_meta=None`, `blog_is_post=False`, an empty candidate list)
  - Save (`POST .../pages/{page_id}/edit`): `services.blog.set_post_meta` is called only when the marker `blog_meta` is present AND at least one of: the `is_public` checkbox is ticked, the page already has a `BlogPost` row, or the section was touched (`_blog_meta_touched`: a slug other than the page slug, an author other than `DEFAULT_AUTHOR_NAME`, a language other than `pl`, or any non-empty description, tags, translation, cover or verified date; an empty field never counts). So a regular wiki page with an untouched section never gets a `BlogPost` row. `_blog_meta_kwargs` maps the fields: an empty `blog_slug` or `blog_author_name` is not passed (unchanged), the description is passed as typed (empty clears it), tags are split on commas with empty items dropped, and an empty translation, cover or verified date is `None`; a malformed UUID or date is a `ValueError` of its own (`Nieprawidłowy identyfikator ...`, `Data weryfikacji ma nieprawidłowy format (RRRR-MM-DD)`). The user comes from `get_session_user` (a missing one is 303 to `/auth/login`). `set_post_meta` runs BEFORE `update_wiki_page`, and both error branches share one helper, `rerender_after_error`: a flash with the error text, a re-query of the project and the page, and the form re-rendered with status 200 and the typed values (title, content and every `blog_*` field, passed as `typed_blog_meta`, which wins over the database values in `_edit_form_context`). The metadata branch does NOT call `db.rollback()`: `set_post_meta` validates everything before its first mutation, so the session is clean and the page content is not saved; the rollback belongs to the `update_wiki_page` branch only, where `services/wiki.py` does it. The `is_public` checkbox and its paths (MON-203) are unchanged for an account with the blog permission
  - Blog permission in the form (MON-270): an account without `blog:write` (`has_blog_permission()` is false) sees the state of `is_public` read-only and gets no "Wpis na blogu" section, so saving the form neither changes `is_public` nor calls `set_post_meta`. Since MON-271 such an account cannot edit the title or the content of an already public page either: the gate covers a change of `is_public`, the post metadata and a changed title or content of a public page. The form always posts both fields, so a save that leaves them as they are (content compared with `\r\n` normalized to `\n`) still passes, while a save that changes either is refused by `services/wiki.py` through the form's existing error path. A request that changes `is_public` anyway is refused by `services/wiki.py` (`Brak uprawnienia blog:write`) and saves nothing
  - Draft preview: `GET /dashboard/{slug}/wiki/pages/{page_id}/blog-preview` renders `templates/blog/page.html` through `render_post_html` and `collect_block_assets` for a private page (a public one works too), with the dashboard `templates` instance and a reduced context (`preview=True`, `preview_back_url`; no `json_ld`, `md_url`, `related`, `translations`, `hreflang_links`, breadcrumbs, children or backlinks). Checks in this order: no session is 303 to `/auth/login`, an unknown project is 404, a missing `wiki:read` is 403 (`require_permission`), an unknown page is 404, and a storage error while reading the content (in an executor, logged with `logger.exception`) is 404 too. The interface and post language is the post's `lang`, or `pl` without a `BlogPost` row; there is no `?lang=` here. It is a pure read: no `ensure_post`, no commit, and a page without a `BlogPost` row is previewed with in-memory defaults. The response carries `X-Robots-Tag: noindex`; with `preview` set the template shows a "Podgląd szkicu" bar with a back link and `<meta name="robots" content="noindex">` and renders no canonical, JSON-LD or alternate link, while without `preview` the public render is unchanged. The preview lives only under `/dashboard/`, so it is in no sitemap, feed or `/llms.txt`. The page detail links to it with a "Podgląd wpisu" button (`target="_blank"`)
  - Editor: a "Wstaw blok" menu in the EasyMDE toolbar of the wiki form (not in the ticket or comment editors) inserts the syntax template of a block at the cursor. Its list is generated, never typed by hand in JS: the router passes `block_templates = list_block_templates()` (`services/blog_blocks.py`) to the edit form and to both create forms, and the template prints it as `<script type="application/json" id="blog-block-templates">`, the only source the menu reads
  - Image upload: `POST /dashboard/{slug}/wiki/upload` takes an optional query parameter `page_id` (the edit form sets `imageUploadEndpoint` to `image_upload_url`, i.e. the upload address with `?page_id=<page.id>`; the create forms get it without the parameter, built from the route slug in `_creation_form_context`, because `project` can be `None` there after a rollback). The route still requires `wiki:write`. With `page_id` the page must belong to the project (otherwise 404 JSON `{"error": "Strona nie istnieje"}`, checked before the file); when that page is `is_public`, the account also needs `blog:write` (MON-272: `has_blog_permission()`, otherwise 403 JSON `{"error": "Brak uprawnienia blog:write"}` before the file is read or stored, because a file of a public page is served anonymously under `/blog/...`), and the FilePond route `wiki_page_attachment_upload` has the same gate; a private page needs only `wiki:write`, and deleting an attachment of a public page still needs only `wiki:delete`. Then `_store_page_image` stores the file as a `WikiAttachment` of that page through `_save_page_attachment`, the helper it shares with the FilePond route `wiki_page_attachment_upload` (MinIO upload in an executor, then `db.add` + `db.commit()`; a storage error raises before anything reaches the database). A storage error is a 500 JSON, logged with `logger.exception` on the editor path. The response is `{"data": {"filePath": <url>}}` with the file name URL-quoted: `/blog/<BlogPost.slug>/attachments/<attachment_id>/<filename>` when the page is `is_public` and has a `BlogPost` row, otherwise `/dashboard/<slug>/wiki/pages/<page_id>/attachments/<attachment_id>/<filename>`, which the public render rewrites after publication (`rewrite_attachment_urls`, see `services/blog.py`). Without `page_id` the behaviour and the response are unchanged

## Services

- `services/wiki.py` - Wiki CRUD, markdown rendering (`render_markdown_html()`), page tree, breadcrumbs; content stored in MinIO, metadata in DB. LLM Wiki additions: backlink parser (`extract_wiki_links`, `sync_backlinks`, `get_backlinks`, `get_outlinks`) and system-page helpers (`ensure_system_page`, `regenerate_index`, `append_log`); `RESERVED_SLUGS` constant guards the reserved system slugs (`wiki-index`, `wiki-log`, `wiki-schema`). MON-139 additions behind the `list_wiki_pages`/`get_wiki_page`/`get_wiki_config`/`set_wiki_config` MCP tools, same `(db, user, project, ...)` + dataclass-result convention as `services/projects.py`: `list_pages_flat` (pre-order DFS with depth), `get_wiki_page_detail` (takes an injectable `content_fn`, defaulting to `get_page_content`, so the MCP wrapper can pass its own patchable reference), `get_wiki_config`/`set_wiki_config` (the latter checks `settings:write` and commits). `WikiPageFlat` carries `parent_id` (MON-142), so the CLI (`wiki list --tree`) can rebuild the tree from the flat list. Role permissions (MON-241): `list_pages_flat`, `get_wiki_page_detail` and `get_wiki_config` call `ensure_permission()` for `wiki:read`. The low-level functions (`create_wiki_page`, `update_wiki_page`, `delete_wiki_page`, `regenerate_index`, `append_log`, `get_backlinks`, `get_outlinks`) check nothing, because the dashboard, pipelines, `wiki_bootstrap` and the admin CLI call them too; there the adapter checks (`ensure_permission` inline in the MCP tool, `require_permission` in the v2 router). The same holds for `embeddings.search_wiki_pages` and `services/wiki_lint.py`. Deleting a public page (MON-272): `ensure_can_delete_page(db, user_id, page)` raises `ValueError("Brak uprawnienia blog:write")` when the account has no blog permission and the page itself or any of its descendants (`_collect_descendants`) is `is_public`; the adapters call it after their `wiki:delete` check and the page lookup and before `delete_wiki_page` (MCP tool: error text; v2 router: 403 through `service_error()`; dashboard `wiki_page_delete`: 403 with the text as the body; CLI through v2: exit code 3), because `delete_wiki_page(page, db)` itself still checks nothing and removes the MinIO objects before its commit. Blog (MON-254): `create_wiki_page` and `update_wiki_page` call `services/blog.py::ensure_post` before their own commit whenever the resulting `is_public` is `True`, so publishing a page through the dashboard, MCP or API v2 always leaves a `BlogPost` row; an `IntegrityError` is still mapped to `ValueError`. Storage on a failed save (MON-272): `update_wiki_page` calls `ensure_post` BEFORE `upload_markdown` (the object key is fixed per page, so an upload ahead of a slug error would replace content the database rolls back), and `create_wiki_page` deletes the object it uploaded (`delete_object(minio_path)`) when the save ends in an `IntegrityError` or a `ValueError`, so no orphan stays in MinIO. Blog permission (MON-270), the one check these two low-level functions do themselves: `create_wiki_page` with `is_public=True` and `update_wiki_page` with a CHANGE of `is_public` (publishing or unpublishing; passing the current value is not a change) call `ensure_blog_permission(db, user_id)` before any write, the MinIO upload included, so a refusal (`ValueError("Brak uprawnienia blog:write")`) leaves no page, no content and no `BlogPost` row. MON-271 extends the gate in `update_wiki_page` to the content of a public page: when `page.is_public` and the title (after `strip()`) differs from `page.title`, or `content` is not `None` and differs from the stored content (compared with `\r\n` normalized to `\n`; the stored content is read only when the page is public and `content` was passed), the same `ensure_blog_permission()` runs at the very start of the function, before the slug, the MinIO upload and any field is written. An unchanged title and content of a public page pass without the permission (e.g. a change of position or parent only), private pages behave as before, and there is no exception for pipelines (`services/pipelines.py` writes private pages). A content write (`content is not None`) also sets `page.updated_at` explicitly, because an edit of the content by the same user changes no column and would otherwise leave `updated_at` (the source of `modified`, `Last-Modified`, the sitemap `lastmod` and the `/llms-full.txt` fingerprint) where it was. The dashboard form, the MCP tools `create_wiki_page` / `update_wiki_page`, the v2 `POST` / `PATCH` of wiki pages and the CLI `--public` / `--no-public` all get the gate from here
- `services/wiki_lint.py` - LLM Wiki audit: detects orphans, dead_links, contradictions, gaps
- `services/wiki_bootstrap.py` - `bootstrap_wiki_llm` idempotent setup: creates the system pages and seeds the default schema page
- `services/wiki_templates.py` - `DEFAULT_WIKI_SCHEMA`: the editable LLM Wiki method "rulebook" used to seed `wiki-schema`
- `services/wiki_attachments.py` (MON-139) - logic behind the wiki attachment/file MCP tools (`get_wiki_attachment`, `add_wiki_page_attachment`, `list_wiki_page_attachments`, `add_wiki_file`, `get_wiki_file`, `update_wiki_file`, `list_wiki_files`); same `(db, user, project, ...)` + dataclass-result convention. Role permissions via `ensure_permission()` (MON-241): `get_wiki_attachment`, `list_wiki_page_attachments`, `get_wiki_file`, `list_wiki_files` -> `wiki:read`; `add_wiki_page_attachment`, `add_wiki_file`, `update_wiki_file` -> `wiki:write`. Since MON-272 `add_wiki_page_attachment` on a page with `is_public=True` also calls `ensure_blog_permission()` (`ValueError("Brak uprawnienia blog:write")`, raised after the page lookup and before the upload, so nothing is stored), because a file of a public page is served anonymously under `/blog/...`; a private page needs only `wiki:write`. Filename/base64/size/mime_type validation lives once in private module helpers (`_validate_filename`, `_decode_base64`, `_validate_mime_type`), shared by the page-attachment and global-file paths. MinIO calls are injected (`upload_object`/`get_object` keyword params, default `None` resolved at call time to the module's own `upload_object`/`get_attachment` import from `services/minio_client.py`) so the MCP wrapper can pass its own `minio_upload_object`/`minio_get_attachment` reference, keeping `tests/unit/test_mcp_server.py`'s existing patches on `monolynx.mcp_server.minio_*` working

## Decisions

- LLM Wiki method (Karpathy-style): opt-in per project via `Project.wiki_llm_enabled` (bool, default False); gated like `embeddings.is_enabled()` - when OFF the tools/skills return a clear no-op/ValueError. Treats the wiki as a growing artifact (vs RAG from scratch) curated through INGEST/QUERY/LINT operations. Reserved system-page slugs `wiki-index`, `wiki-log`, `wiki-schema` (prefix `wiki-`, since `SLUG_PATTERN` forbids underscores); the schema is itself an editable page seeded from `DEFAULT_WIKI_SCHEMA`. Backlinks are stored in PostgreSQL via the `WikiBacklink` model (NOT in Neo4j - Neo4j stays exclusively for the Connections/code module); backfill via `make backfill-backlinks`. Contradictions are flagged inline with the marker `> **Sprzeczność [date]:**`
- Blog authoring in the dashboard (MON-264): a person gets in the wiki form what an agent has through the connectors, with no new model, migration or MCP tool. Metadata goes through the same `set_post_meta` as MCP, API v2 and the CLI, so validation lives in one place and a validation error never saves the page content. The draft preview reuses the public template (`blog/page.html` with `preview=True`) instead of a second one, lives only under `/dashboard/` behind the session and `wiki:read`, writes nothing and answers `X-Robots-Tag: noindex`; no public `/blog/` route serves a private page. The "Wstaw blok" menu is generated from the block registry (`syntax_template` per block, `list_block_templates()`), never from a list typed in JS. An image uploaded in the editor is a page attachment: a draft gets the dashboard address, and the public render rewrites only the addresses whose `page_id` is the post's own page (`rewrite_attachment_urls`), so pointing at another page's attachment does not make it public. Tests: `tests/integration/test_wiki_dashboard.py`, `tests/unit/test_blog_service.py`, `tests/unit/test_blog_blocks.py`
