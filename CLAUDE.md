# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What is this project?

Monolynx is a multi-module project platform. It started as a minimalist error-tracking system (500ki module — named after HTTP 500 errors) and now includes a Scrum module (backlog, Kanban board, sprints, story points), a Monitoring module (URL health checks with uptime tracking), a Wiki module (markdown pages with semantic RAG search via pgvector, plus an opt-in "LLM Wiki" method with backlinks, system pages, and INGEST/QUERY/LINT operations), a Connections module (code dependency graph visualization using Neo4j), a Work Plan / Gantt module (personal per-user cross-project scheduling with Gantt and calendar views), a Pipelines module (observability over AI agent work, modeled on GitLab CI/CD; pipeline -> step -> job hierarchy where job logs are stored as wiki pages), and a public blog (wiki pages published at `/blog/` as HTML with a markdown twin for AI readers, behind an AI-readiness lint). The architecture supports adding new modules via the sidebar navigation.

## Commands

All commands run inside Docker. Never run Python commands locally — always use `docker compose exec app <command>`. Exception: stdlib-only repo scripts in `scripts/` and `plugin/scripts/` (`sync_skills.py`, `validate_plugin_consistency.py`, `*_state.py`) run on the host with `python3`, exactly as the `Makefile` targets `sync-skills`, `sync-skills-check` and `validate-plugin` do. Application code under `src/`, `pytest`, `ruff` and `mypy` still run only in Docker.

```bash
# Development environment (Docker Compose: PostgreSQL + FastAPI with hot reload)
make dev                              # Start dev env (port 8000, configurable via APP_PORT)
make down                             # Stop dev env (app + worker)
make worker                           # Start monitor worker separately (dev)
make logs                             # Tail app logs
make setup                            # Configure local dev environment
make help                             # Show available commands

# Code quality
make lint                             # ruff check --fix + ruff format + mypy (auto-fixes!)
make fmt                              # ruff check --fix + ruff format (same as lint, without mypy)

# Testing (inside Docker)
make test                             # All tests with coverage
docker compose exec app python -m pytest tests/unit/ -v                 # Unit tests only
docker compose exec app python -m pytest tests/integration/ -v          # Integration tests
docker compose exec app python -m pytest tests/unit/test_fingerprint.py::TestFingerprintGeneration::test_same_exception_same_location_same_fingerprint -v  # Single test
make prune-test-dbs                   # Drop leftover per-run test databases (open_sentry_test_*) with no active connections

# Database migrations
make migrate                          # Run pending migrations
make migration msg="description"      # Generate new migration

# Admin
make createsuperuser                  # Create admin user (interactive prompt)

# Wiki RAG
make backfill-embeddings              # Generate embeddings for existing wiki pages
make backfill-backlinks               # Generate backlinks for existing wiki pages (LLM Wiki)
make backfill-dependencies            # Move prose ticket dependencies into blocked_by_ids (dry-run; ARGS=--apply writes)

# Build
make build                            # Build production Docker image

# CLI (cli/, package monolynx-cli): build and run in a throwaway container, from the repo root.
# The mount is read-only and the package is copied inside the container, because pip install
# as root would write build/ and *.egg-info into the repo.
docker run --rm -v "$PWD/cli":/src:ro python:3.10-slim sh -c "cp -r /src /cli && pip install -q /cli && monolynx --help"
```

**Important**: When generating Alembic migrations with autogenerate, always review the output — it may include tables from a previous migration if the DB was empty at generation time. Each migration must only contain its own new/changed tables.

## Architecture

Three separate packages in one repo: the backend (`src/monolynx/`), the Django SDK (`sdk/`) and the command-line client (`cli/`).

**Backend** (`src/monolynx/`) — FastAPI async server:
- `main.py` registers routers lazily via `_register_routers()` to avoid circular imports; lifespan optionally starts monitor checker loop (controlled by `ENABLE_MONITOR_LOOP`, default true for dev, false in prod)
- `config.py` uses pydantic-settings, reads from env vars / `.env` file (see `.env.example`)
- `database.py` provides async SQLAlchemy session via `get_db()` FastAPI dependency
- `constants.py` — shared constants for Scrum (ticket statuses, priorities, sprint statuses, member roles, label mappings), Monitoring (interval units, Polish labels), Time Tracking (entry statuses, report defaults), and Graph (node types, edge types, Polish labels)

**Dashboard module system** (`dashboard/`):
- `dashboard/__init__.py` — combines all sub-routers into one `router`; ordering matters: static routes (users, settings, profile) before dynamic `{slug}` routes to avoid slug collision
- `dashboard/helpers.py` — shared `_get_user_id()`, `SLUG_PATTERN`, `templates` instance, `flash()` helper for session-based flash messages
- `dashboard/auth.py` — login/logout (`/auth/*`), invitation acceptance (`/auth/accept-invite/{token}`)
- `dashboard/projects.py` — project list, create (`/dashboard/`, `/dashboard/create-project`)
- `dashboard/profile.py` — user API token management for MCP access (`/dashboard/profile/*`)
- `dashboard/users.py` — user management, superuser-only (`/dashboard/users/*`); invitation system with token generation and email
- `dashboard/sentry.py` — error tracking module "500ki": issues list, issue detail, SDK setup guide (`/dashboard/{slug}/500ki/*`)
- `dashboard/scrum.py` — Scrum module: backlog (with pagination + filtering), Kanban board, ticket CRUD with comments, sprints with status filtering (`/dashboard/{slug}/scrum/*`)
- `dashboard/monitoring.py` — URL monitoring module: monitor CRUD, check history with pagination, toggle on/off (`/dashboard/{slug}/monitoring/*`); includes SSRF protection (blocks localhost, private IPs), limit 20 monitors per project
- `dashboard/wiki.py` — Wiki module: page CRUD, tree hierarchy, markdown rendering, image upload to MinIO, semantic search via pgvector (`/dashboard/{slug}/wiki/*`); page detail shows an "incoming links" (backlinks) panel, gated on `wiki_llm_enabled`. Blog authoring in the dashboard (MON-264), the human counterpart of the `set_blog_post_meta` connector:
  - Post metadata form: the edit form (`templates/dashboard/wiki/page_form.html`) has a section `<details id="blog-meta-section">` titled "Wpis na blogu" with the fields `blog_slug`, `blog_description` (max 300, with a character counter), `blog_author_name`, `blog_tags` (comma-separated), `blog_lang` (pl/en), `blog_translation_of_id`, `blog_cover_attachment_id` (picked from the page attachments) and `blog_last_verified_at`, plus the hidden marker `blog_meta=1`. The section is open when `blog_is_post` (the page has a `BlogPost` row or is public) and absent on the two create forms (`blog_meta` is `None` there, there is no page yet). Template context of the edit form: `blog_meta` (dict of strings; without a `BlogPost` row the slug is the page slug, the author `DEFAULT_AUTHOR_NAME`, the language `pl`), `blog_is_post`, `blog_translation_candidates` (dicts `{page_id, title, lang}` for the other pages of the project that have a `BlogPost` row, ordered by title), `attachments`, `block_templates` and `image_upload_url`, all built by `_edit_form_context`; the create forms use `_creation_form_context` (`blog_meta=None`, `blog_is_post=False`, an empty candidate list)
  - Save (`POST .../pages/{page_id}/edit`): `services.blog.set_post_meta` is called only when the marker `blog_meta` is present AND at least one of: the `is_public` checkbox is ticked, the page already has a `BlogPost` row, or the section was touched (`_blog_meta_touched`: a slug other than the page slug, an author other than `DEFAULT_AUTHOR_NAME`, a language other than `pl`, or any non-empty description, tags, translation, cover or verified date; an empty field never counts). So a regular wiki page with an untouched section never gets a `BlogPost` row. `_blog_meta_kwargs` maps the fields: an empty `blog_slug` or `blog_author_name` is not passed (unchanged), the description is passed as typed (empty clears it), tags are split on commas with empty items dropped, and an empty translation, cover or verified date is `None`; a malformed UUID or date is a `ValueError` of its own (`Nieprawidłowy identyfikator ...`, `Data weryfikacji ma nieprawidłowy format (RRRR-MM-DD)`). The user comes from `get_session_user` (a missing one is 303 to `/auth/login`). `set_post_meta` runs BEFORE `update_wiki_page`, and both error branches share one helper, `rerender_after_error`: a flash with the error text, a re-query of the project and the page, and the form re-rendered with status 200 and the typed values (title, content and every `blog_*` field, passed as `typed_blog_meta`, which wins over the database values in `_edit_form_context`). The metadata branch does NOT call `db.rollback()`: `set_post_meta` validates everything before its first mutation, so the session is clean and the page content is not saved; the rollback belongs to the `update_wiki_page` branch only, where `services/wiki.py` does it. The `is_public` checkbox and its paths (MON-203) are unchanged
  - Draft preview: `GET /dashboard/{slug}/wiki/pages/{page_id}/blog-preview` renders `templates/blog/page.html` through `render_post_html` and `collect_block_assets` for a private page (a public one works too), with the dashboard `templates` instance and a reduced context (`preview=True`, `preview_back_url`; no `json_ld`, `md_url`, `related`, `translations`, `hreflang_links`, breadcrumbs, children or backlinks). Checks in this order: no session is 303 to `/auth/login`, an unknown project is 404, a missing `wiki:read` is 403 (`require_permission`), an unknown page is 404, and a storage error while reading the content (in an executor, logged with `logger.exception`) is 404 too. The interface and post language is the post's `lang`, or `pl` without a `BlogPost` row; there is no `?lang=` here. It is a pure read: no `ensure_post`, no commit, and a page without a `BlogPost` row is previewed with in-memory defaults. The response carries `X-Robots-Tag: noindex`; with `preview` set the template shows a "Podgląd szkicu" bar with a back link and `<meta name="robots" content="noindex">` and renders no canonical, JSON-LD or alternate link, while without `preview` the public render is unchanged. The preview lives only under `/dashboard/`, so it is in no sitemap, feed or `/llms.txt`. The page detail links to it with a "Podgląd wpisu" button (`target="_blank"`)
  - Editor: a "Wstaw blok" menu in the EasyMDE toolbar of the wiki form (not in the ticket or comment editors) inserts the syntax template of a block at the cursor. Its list is generated, never typed by hand in JS: the router passes `block_templates = list_block_templates()` (`services/blog_blocks.py`) to the edit form and to both create forms, and the template prints it as `<script type="application/json" id="blog-block-templates">`, the only source the menu reads
  - Image upload: `POST /dashboard/{slug}/wiki/upload` takes an optional query parameter `page_id` (the edit form sets `imageUploadEndpoint` to `image_upload_url`, i.e. the upload address with `?page_id=<page.id>`; the create forms get it without the parameter, built from the route slug in `_creation_form_context`, because `project` can be `None` there after a rollback). The route still requires `wiki:write`. With `page_id` the page must belong to the project (otherwise 404 JSON `{"error": "Strona nie istnieje"}`, checked before the file) and `_store_page_image` stores the file as a `WikiAttachment` of that page through `_save_page_attachment`, the helper it shares with the FilePond route `wiki_page_attachment_upload` (MinIO upload in an executor, then `db.add` + `db.commit()`; a storage error raises before anything reaches the database). A storage error is a 500 JSON, logged with `logger.exception` on the editor path. The response is `{"data": {"filePath": <url>}}` with the file name URL-quoted: `/blog/<BlogPost.slug>/attachments/<attachment_id>/<filename>` when the page is `is_public` and has a `BlogPost` row, otherwise `/dashboard/<slug>/wiki/pages/<page_id>/attachments/<attachment_id>/<filename>`, which the public render rewrites after publication (`rewrite_attachment_urls`, see `services/blog.py`). Without `page_id` the behaviour and the response are unchanged
- `dashboard/connections.py` — Connections module: graph visualization with Cytoscape.js, node/edge CRUD forms, graph API endpoint, setup guide page (`/dashboard/{slug}/connections/*`); graceful degradation when Neo4j unavailable. The graph is populated by the external [graphify](https://github.com/Graphify-Labs/graphify) extractor (offline tree-sitter AST, installed by the runner owner, never by CI) via `cicd/sync_graph.py` -> `replace_graph`; skills `/monolynx:create-graph-ci-script` (CI) and `/monolynx:graph-sync` (local, guided). Edge metadata carries `confidence` (EXTRACTED/INFERRED/AMBIGUOUS) and `source_relation`; taxonomy mapping lives on the wiki page "Mapowanie taksonomii Graphify -> Monolynx"
- `dashboard/settings.py` — project settings, member management (`/dashboard/{slug}/settings`)
- `dashboard/reports.py` — global cross-project work reports with multi-select filtering (project, user, sprint), date range, and PDF export via weasyprint (`/dashboard/reports`)
- `dashboard/work_plan.py`: Work Plan module (prefix `/dashboard/plan`): personal per-user cross-project scheduling via junction model (`User x Ticket x Date`), Gantt view (frappe-gantt) and monthly calendar, REST endpoints for entries CRUD plus JSON data and ticket autocomplete; independent of sprint assignment
- `dashboard/pipelines.py` - Pipelines module: pipeline list (with status/type filtering + pagination), pipeline detail (step columns research/coding/wrap-up with job cards), job detail (markdown log rendered from wiki), JSON API endpoints and HTMX partials for 15s live polling (`/dashboard/{slug}/pipelines/*`); session auth plus `scrum:read` (superuser bypass, no membership needed), read-only UI (pipelines are created by skills via MCP, not from the dashboard)

**Public blog** (`blog.py`, `blog_ai.py`): two routers with prefix `/blog`, both registered in `main.py` unconditionally (not gated by `SKIP_LANDING_PAGE`), with no session and no RBAC: `blog.py` serves the HTML pages and attachments, `blog_ai.py` (MON-258) the markdown twins `/blog/index.md` and `/blog/{slug}.md`. A post is a wiki page with `is_public=True` plus its `BlogPost` row (MON-254); the routes join the two explicitly (`BlogPost.page_id == WikiPage.id`) and filter `WikiPage.is_public` in SQL, so a private page, an unknown slug and a public page without a `BlogPost` row are all 404, never 403.
- `GET /blog/` - post list through `services/blog.py::list_public_posts`, 20 per page, ordered by `published_at DESC` (then `slug`), so editing an older post does not reshuffle the list. The teaser is `BlogPost.description`; when it is empty the route falls back to a summary extracted from the page content with the block markers removed first (`extract_summary(strip_block_markers(content))`, MON-255, so an alert marker like `[!TLDR]` never shows up in a teaser), read from MinIO in parallel (`asyncio.gather`). Since MON-260 the content of every card is read, also when `description` is set, because the same single read (`_fetch_card_data`) gives the reading time (`reading_time_minutes(render_post_markdown(content))`); a MinIO error degrades that one card (`reading_time=None`, teaser = `description` or empty) and the list still answers 200. The date shown is `published_at`, falling back to the page's `created_at`. Filters (MON-260): `?tag=` and `?lang=` are passed to `list_public_posts`. A `lang` from `POST_LANGS` (`pl` / `en`) filters posts by content language AND sets the interface language; a missing or other value means no filter and the `en` interface. An empty `tag` means no filter; a tag rejected by `is_valid_tag()` answers 200 with an empty list and never reaches the database (a NUL byte in the parameter would make PostgreSQL fail), and it does not enter the context or any generated URL. All list URLs are built by `_index_path(tag, lang, page)`: query order `tag`, `lang`, `page`, values through `urlencode`, `page` only when above 1 (so page 1 is `/blog/?tag=x`, never `page=1`). Each item of `posts` keeps `title`, `slug`, `published_at`, `summary` and gains `tags`, `reading_time` (int or `None`), `cover_image_url` (relative path from `get_cover_urls`, or `None`) and `lang`; the new context keys are `filter_tag`, `filter_lang` (the active valid filters or `None`), `canonical_url` (absolute, `{APP_URL}` + `_index_path` of the current page with its filters, so each pagination page is its own canonical instead of always `/blog/`), `prev_url` / `next_url` (relative, filters kept, `None` at the ends) and `lang_switch_url` / `lang_switch_url_en` (`/blog/?lang=pl|en` with `tag` kept, read by the layout's language switch). `templates/blog/index.html` renders `<link rel="canonical">` and, in `{% block head %}`, `<link rel="prev">` / `<link rel="next">` with `app_url` prepended, loads `static/blog/blog.css` only (no `blocks.css`), and shows the language filter (all / PL / EN), the active tag with a "clear filter" link, and cards whose tag links keep the language filter. The response goes through `blog_ai.conditional_response` (`media_type="text/html; charset=utf-8"`): `ETag` + `Last-Modified` and 304 on a matching `If-None-Match`, with `last_modified` as the newest `page.updated_at` among the posts of the current list page, or 1970-01-01 UTC for an empty list
- `GET /blog/{slug}` - lookup by `BlogPost.slug` through `get_public_post_by_slug`: the current slug renders the post (200), a slug from `previous_slugs` of a public post answers 301 to `/blog/{current slug}` with the query string preserved (`?lang=`), anything else is 404. There is no fallback to the wiki slug. Content goes through `render_post_html()` (`services/blog_blocks.py`, MON-255: markdown plus the post block renderers, sanitized with `nh3`); `render_markdown_public()` stays in `services/wiki.py` with unchanged behaviour (the shared markdown renderer followed by `nh3.clean()` with an allow-list of tags, attributes and URL schemes), but nothing in `src/` calls it any more (only its tests do). A MinIO error while reading the content is mapped to 404. `templates/blog/page.html` has no inline `<style>` block any more (MON-260): the post typography, layout, table of contents, footer and list-card styles live in `static/blog/blog.css`, loaded BEFORE `static/blog/blocks.css` (both use `.blog-content ...` selectors and the block styles must win), followed by `static/blog/blocks.js` (copy button, video, diagrams, terminals, graphics and table of contents; all served under `/static/blog/`). Since MON-257 the route also computes `collect_block_assets(content)` and passes `has_diagram` (bool) and `graphics` (list of names from `BLOG_GRAPHICS`) to the template, which loads the Mermaid library from the CDN only for a post with a diagram and the `static/blog/graphics/<name>.css|.js` pair only for a post that uses that component (details under `services/blog_blocks.py`). Interface language (MON-260): `?lang=` when it is `pl` / `en`, otherwise the post's own `lang` (before, a missing `?lang=` meant `en`). Breadcrumbs, child pages and backlinks list only `is_public` pages and link by `BlogPost.slug`. Meta description and Open Graph come from `description` (fallback: the content summary, `extract_summary(strip_block_markers(content))`), `article:published_time` from `published_at` (fallback `created_at`), and `og:image` / `twitter:image` from the cover attachment when `cover_attachment_id` is set and the attachment still belongs to the page (absolute URL of the attachment route below; otherwise the layout's default image). Content negotiation (MON-258): when the `Accept` header lists the exact media type `text/markdown` (matched case-insensitively by `blog_ai.wants_markdown()`; `*/*` and `text/*` do not trigger it, and neither does `text/markdown;q=0` or an unparsable `q`), the route returns the markdown twin through `blog_ai.markdown_twin_response()`, the same document and the same `ETag` as `/blog/{slug}.md` (200 or 304), with `Vary: Accept` and no `Link` header. The HTML response goes through `blog_ai.conditional_response` (MON-260; `media_type="text/html; charset=utf-8"`, `last_modified` = `page.updated_at`), so it is 200 or, on a matching `If-None-Match`, 304 with an empty body; both carry `ETag`, `Last-Modified`, `Vary: Accept` and `Link: <{APP_URL}/blog/{slug}.md>; rel="alternate"; type="text/markdown"`, and the 301 for an old slug carries `Vary: Accept` too and still points at `/blog/{current slug}`, also when markdown was requested. A 404 is a plain `HTTPException` with neither `Vary` nor `Link`. The template context gains `md_url` (the absolute `.md` address) and `json_ld` (the string from `dump_jsonld(build_post_jsonld(...))`, with `wordCount` counted on `render_post_markdown(content)` and `image` set to the cover URL when there is one); `templates/blog/page.html` renders them in `{% block head %}` as `<link rel="alternate" type="text/markdown" href="{{ md_url }}">` and `<script type="application/ld+json">{{ json_ld|safe }}</script>`, each only when the variable is set. `GET /blog/` passes `json_ld` as well (`dump_jsonld(build_blog_jsonld(...))` over the posts of the current list page), rendered by `templates/blog/index.html` in its own `{% block head %}`. `|safe` is allowed there only because the string was neutralized in Python by `dump_jsonld()`; no JSON is assembled in a template. Post page for people (MON-260): the context also carries `post_lang`, `description` (`post.description`, shown under the title only when set), `author_name`, `last_verified_at`, `tags`, `reading_time` (`reading_time_minutes(render_post_markdown(content))`), `toc` (`extract_toc(content_html)`, objects with `level`, `id`, `text`; empty below 3 headings), `related` (max 3 dicts `{title, slug, description, published_at, tags}` from `list_related_posts`), `translations` (dicts `{lang, slug, title}` from `list_public_translations`, titles fetched in one query), `hreflang_links` (dicts `{lang, url}` with absolute URLs, the current post first and then its translations; an empty list when there is no public translation) and `lang_switch_url` / `lang_switch_url_en` (`/blog/{slug}?lang=pl|en`, read by the layout). The template treats every one of these keys as optional and renders no empty element for a missing value. It renders `<link rel="alternate" hreflang="..." href="...">` per `hreflang_links` item in `{% block head %}` (no `hreflang=` anywhere in the HTML without a public translation), a header (tags linking to `/blog/?tag=<tag>`, title, description, author, publication date, "updated", "verified", reading time, cover), the table of contents as `<details class="blog-toc-wrap">` around `<nav class="blog-toc">` (sticky side column from 1024 px, collapsible below; the text column is capped at `70ch`), and a footer with the "AI version" link to the `.md` twin, the translation links and the related posts. The `blog-*` class hooks are a contract asserted by the tests, attribute order included: `blog-toc`, `blog-meta`, `blog-author`, `blog-published` (`<time class="blog-published" datetime="...">`), `blog-verified`, `blog-reading-time` (`N min czytania` / `N min read`), `blog-tags` / `blog-tag`, `blog-cover`, `blog-related`, `blog-translations`, `blog-md-link` on the post, and `blog-card`, `blog-card-cover` on the list. `blocks.js` (MON-260) takes the first `nav.blog-toc`, opens its `<details>` and adds the class `is-wide` at `(min-width: 1024px)`, and highlights the current section with an `IntersectionObserver` (`rootMargin: "-80px 0px -70% 0px"`; the link of the first visible heading gets the class `is-active` and `aria-current="true"`); without JavaScript the links still work and the `<details>` stays collapsed
- `GET /blog/{slug}/attachments/{attachment_id}/{filename}` - public attachment of a post, looked up by the current `BlogPost.slug` only (an old slug is 404 here, no redirect). The attachment must belong to that page (`WikiAttachment.wiki_page_id`), otherwise 404. Only PNG, JPEG, GIF and WebP are served `inline`; every other type, SVG included, goes out as `attachment`. Every response, 404 included, carries `X-Content-Type-Options: nosniff`, and a MinIO error is 404
- Dashboard attachment addresses in a post (MON-264): `blog.py::public_page` passes the content through `services/blog.py::rewrite_attachment_urls(content, page_id=..., post_slug=...)` before `render_post_html` / `collect_block_assets`, so an image uploaded in the dashboard editor while the page was a draft is served to an anonymous reader through the public attachment route above. The markdown twin and the feeds (`blog_ai.py`) do not call it
- `blog_ai.py` (MON-258) - AI layer of the blog: `router = APIRouter(prefix="/blog", tags=["blog-ai"])` with two read-only markdown routes (plus the three feed routes added in MON-259, below), `GET /index.md` declared before `GET /{slug}.md`. `main.py::_register_routers` includes `blog_ai_router` BEFORE `blog_router`, because `/blog/{slug}` in `blog.py` also matches `x.md` and would otherwise swallow both twins. The module imports nothing from `blog.py` or `main.py` (import cycle; `blog.py` imports `conditional_response`, `markdown_twin_response` and `wants_markdown` from it) and builds its own `Response` with `MARKDOWN_MEDIA_TYPE` (`text/markdown; charset=utf-8`), so `_markdown_response` in `main.py` (`/index.md`, `/features/{slug}.md`) is untouched
  - `GET /blog/{slug}.md` - lookup through `get_public_post_by_slug`, like the HTML route: a slug from `previous_slugs` answers 301 to `/blog/{current slug}.md` with the query string preserved; a private post, an unknown slug, a public page without a `BlogPost` row and a MinIO error while reading the content are all 404 (never 403 or 500; the storage error is logged with `logger.exception` in `markdown_twin_response`, which reads the content in an executor)
  - Document: `render_post_markdown_document(post, page, content, translations)`, a synchronous function and the only builder of the document, used by the `.md` route and by `blog.py` for `Accept: text/markdown`. Shape: `---`, the fields, `---`, an empty line, the body and a final newline (frontmatter only when the body is empty). The body is `absolutize_markdown_urls(render_post_markdown(content), APP_URL)`: no HTML added by the server and no `:::` lines. Frontmatter fields, always present and in this order: `title` (`page.title`), `description` (`post.description`, falling back to `extract_summary(strip_block_markers(content))`), `url` (the canonical HTML address `{APP_URL}/blog/{slug}`, `APP_URL` without a trailing `/`), `lang` (`post.lang`), `author` (`post.author_name` or `DEFAULT_AUTHOR_NAME`), `published` (`(post.published_at or page.created_at).isoformat()`), `modified` (`page.updated_at.isoformat()`), `last_verified` (`post.last_verified_at.isoformat()` or `null`), `tags` (list of strings, `[]` when empty), `translations` (list of `{lang, url}` for the other public language versions from `list_public_translations`, `url` being the HTML address, `[]` when none), `reading_time_minutes` (int, `max(1, ceil(word_count / 200))`) and `word_count` (int, `len(body.split())` on the final body)
  - Serialization is manual, with no PyYAML in production code: `pyyaml` is not a production dependency and must not become one (tests may import `yaml`, it is in the dev/CI environment). `_yaml()` writes every string, list and object as `json.dumps(value, ensure_ascii=False)`, i.e. YAML flow style with double-quoted strings, so a quote, a colon or a newline in a title cannot break the document, and additionally replaces every character matched by `_YAML_UNSAFE_CHARS` (the range U+007F-U+009F, plus U+2028 and U+2029) with its four-hex-digit unicode escape, because YAML treats some of them as line breaks and rejects the other control characters. The three dates are quoted strings, so `yaml.safe_load` returns `str` for them, never `datetime`; ints are bare and a missing `last_verified` is a bare `null`
  - `absolutize_markdown_urls(markdown_text, base_url)` prefixes `base_url` (trailing `/` dropped) to every `](...)` target, link or image, that starts with a single `/`. Unchanged: `http://`, `https://`, `mailto:`, `#anchor`, `//host`, paths without a leading `/`, and everything inside fenced code (three or more backticks or tildes, closed by a fence of the same character and at least the same length) and inline code
  - `conditional_response(request, body, *, last_modified, media_type=MARKDOWN_MEDIA_TYPE, headers=None)` adds a strong `ETag`, the first 32 hex characters of sha256 over `last_modified.isoformat() + "\n" + body` (UTF-8, `last_modified` normalized to UTC, a naive value taken as UTC) in double quotes, and `Last-Modified` as an HTTP-date, so the tag changes with the content and with `updated_at`. `If-None-Match` is read as a comma-separated list, a `W/` prefix is ignored in the comparison and `*` always matches; a match answers 304 with an empty body and the same `ETag`, `Last-Modified` and passed `headers`. `If-Modified-Since` is deliberately not implemented
  - `GET /blog/index.md` - one call to `list_public_posts` with `per_page=1000` (no pagination, newest first), `?lang=` and `?tag=` passed through as filters (since MON-260 `/blog/` takes the same two filters, but there an invalid `lang` means no filter instead of an empty list, and a valid one also sets the interface language). An empty `?lang=` or `?tag=` means no filter. Both are validated before the query, since they come straight from the URL (a value such as NUL would make PostgreSQL fail with a 500): a `lang` outside `POST_LANGS` or a `tag` rejected by `services/blog.py::is_valid_tag()` answers 200 with the empty list and never reaches the database. Body: `# Blog`, then one item per post, `- [<title>]({APP_URL}/blog/{slug}.md) - <YYYY-MM-DD> - <description>` plus ` (tagi: a, b)` when the post has tags; in the title whitespace is collapsed and `\`, `[`, `]` are backslash-escaped, the date is the UTC date of `published_at` (fallback `created_at`), and the description is `post.description` with whitespace collapsed and no MinIO fallback (an empty one drops that part). No posts gives the heading and the line `Brak wpisów.`. **API v2** (`api/v2/`): skeleton REST API under `/api/v2`, foundation for domain endpoints (MON-142). `api/v2/__init__.py` - `router` (placeholder root available both with and without a trailing slash - `GET /api/v2/` and `GET /api/v2`, no redirect between them; `/api/v2/openapi.json` + `/api/v2/docs` built exclusively from `router`'s own routes; the `/me` router (`api/v2/me.py`, MON-125) included via `router.include_router(me_router)`; a catch-all `/{full_path:path}` registered last, handling GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS and returning 404 problem+json for any unmatched v2 path - HEAD/OPTIONS must be listed explicitly, otherwise Starlette treats the request as a path match with the wrong method and returns 405 instead of 404) and `register_api_v2(app)` (a pure ASGI `X-Request-Id` middleware class, registered via `app.add_middleware`, deliberately not `@app.middleware("http")`/`BaseHTTPMiddleware` because MCP is mounted at `/` and serves streamable HTTP/SSE that a buffering middleware would break; plus problem+json exception handlers for `ApiV2Error`/`HTTPException`/`RequestValidationError`. Both the middleware and the handlers use one shared boundary helper, `_is_v2_path()` (`path == "/api/v2"` or `path.startswith("/api/v2/")`), so a route under an unrelated prefix like `/api/v2foo` is never mistaken for v2; outside that boundary the handlers delegate to FastAPI's default handlers, so the dashboard and API v1 keep their existing `{"detail": ...}` format). The `HTTPException` handler preserves `exc.headers` (e.g. `Allow`, `WWW-Authenticate`) in the problem+json response. `api/v2/deps.py` - `get_api_user()` (authorizes `Authorization: Bearer <token>` via `verify_bearer_token()`, every 401 problem+json response carries `WWW-Authenticate: Bearer` per RFC 6750) and `get_api_user_and_project()` (active project by slug + membership check, 404/403 problem+json). `api/v2/errors.py` - `ApiV2Error(status, title, detail=None, type="about:blank", headers=None)`, with `headers` propagated to the response the same way as `headers` on `fastapi.HTTPException`. `api/v2/me.py` - `GET /me` (MON-125), protected by `get_api_user`, returns `MeResponse(id, email)` for the token's owner; 401 problem+json comes from `get_api_user` itself.

An empty inside gets no label, and no line of the result starts with `:::` outside a fenced code block. `extract_structured_data(markdown) -> dict` (MON-256) always returns `{"faq": [...], "steps": [...], "videos": [...]}` (empty lists when the post has no such block) and never raises: `faq` items are `{"question", "answer"}` as text without markdown or HTML markup, `steps` items are `{"name", "text"}` (`name` is an empty string for an item without a bold start), `videos` items are `{"url", "description"}` for allowlisted addresses only. Containers inside fenced code are skipped (same parser) and `glossary` is deliberately left out. Nothing in `src/` calls it yet: it is the input for the AI-layer ticket (JSON-LD). Security model: there is ONE `nh3` pass and it runs on the author's content only. `render_post_html` first renders registered containers (all author markdown in them goes through `_clean`, the same `nh3` call: the block bodies, and through `_inline`, which is `_clean` minus the wrapping `<p>`, also the short values, i.e. a FAQ question, a step name, a stat value and label, a glossary term and definition, so inline markdown works in them; `html.escape` covers what is not markdown: the `details` title, the video address and id, and the `src`/`alt` of a gallery image and the `href` of the CTA button, both re-escaped after being read back from cleaned HTML; the tag and attribute allowlists in `services/wiki.py` are not widened for them, so `details`, `summary`, `dl`, `iframe` or `class` written by the author are still removed, inside a container too), then cuts fenced code, quotes and footnote definitions out of the source and parks each as a placeholder token carrying a per-render random nonce (so a post cannot fake a block), then renders the rest to HTML and cleans it with `nh3` using the tag list and URL schemes imported from `services/wiki.py` (`_PUBLIC_ALLOWED_TAGS`, `_PUBLIC_URL_SCHEMES`: `http`, `https`, `mailto`) and its own attribute list (`href`, `title` on `a`; `src`, `alt`, `title` on `img`), which has no `class` and no `id`. The order after that is fixed: captioned figures are built on the cleaned HTML, then the tokens are replaced by block HTML, and only then heading anchors and footnote references are added over the whole result, so headings and footnote references work inside alerts and quotes too. A token is replaced only where it stands as a paragraph of its own (`<p>token</p>`); a token anywhere else is removed, because a block must not land in an unknown context such as an attribute value. Known limitation: a block with its own renderer (code, alert, quote with author) placed inside a raw HTML block written by the author is not rendered. Every author value inside a block is either escaped with `html.escape` (code, file name, quote author, and the `src`, `alt` and caption of a figure, re-escaped explicitly because the caption moves from an attribute into element content) or was cleaned by the same `nh3` call (alert and quote bodies, footnote text). So `class` and `id` come only from the renderers (prefix `blog-`, `language-*` on `<code>`, heading anchors), and a hand-written `class="blog-callout-note"` or `id` in raw HTML is removed, like `<script>`, `on*` attributes and `javascript:` / `data:` URLs; links keep `rel="noopener noreferrer nofollow"`. The dashboard renderer `render_markdown_html()` is untouched: no sanitization and no blocks. Graphic blocks (MON-257): four containers whose source is text (a table, a description, code) with the graphic as a layer over it, so a model reading the markdown twin and a reader without JS get the same content; no block accepts raw HTML, CSS or JS from the author. They go through the same dispatch as the structural containers (rendered onto a token, inserted after the `nh3` pass), attribute values (`title`, `type`, `name`) are read with `dict(_ATTR.findall(container.attrs))`, and the fenced block inside `diagram` and `terminal` is found by `_split_fenced` (the first closed fence of the container, language lowercased) and always escaped, never interpreted. Titles placed in element content (the `<figcaption>` of a chart and of a diagram, `blog-terminal-title`) go through `_text_escape`, i.e. `html.escape` plus `[` written as `&#91;`, because `_link_footnotes` runs after the blocks are inserted and would otherwise turn a `[^label]` in a title into a footnote reference. `chart` (`:::chart type="bar|line|pie" title="..."` over a markdown table): `<figure class="blog-chart blog-chart-{type}">` with the inline SVG from `services/blog_chart.py` and the table in `<details class="blog-chart-data"><summary>Dane wykresu</summary>`; when the table cannot be read as chart data, `type` is missing or unknown, or the data cannot be drawn (`pie` with a negative value or a sum of 0), it is `<figure class="blog-chart">` with the inside through `_clean`, no `<svg>` and no `<details>`; a non-empty title is an escaped `<figcaption>` in both variants. `diagram` (`:::diagram title="..."`: a description paragraph plus a `mermaid` fence): `<figure class="blog-diagram" data-blog-diagram>` with the optional `<figcaption>`, `<div class="blog-diagram-description">` (omitted when there is no description), `<div class="blog-diagram-canvas" hidden>` and `<pre class="blog-diagram-source"><code>` holding the escaped source, deliberately without `language-mermaid`, so that the word `mermaid` in the page HTML means only the library script; the source is the first closed fence of the container and only when its language is `mermaid` and it is not empty. A first fence in another language is the author's content: it stays in the description (rendered as ordinary markdown, kept in the `.md` twin too) and the figure carries the description alone (no `data-blog-diagram`, canvas or source), as it does without any fence; an empty `mermaid` fence is dropped, and when nothing else is left the inside degrades to ordinary markdown. `terminal` (`:::terminal title="..."` over a fence, `console` by convention but any language or none is accepted): `<figure class="blog-terminal" data-blog-terminal>` with `blog-terminal-bar` / `blog-terminal-title` (escaped title) and `<pre class="blog-terminal-body"><code>` holding the full escaped content from the start; no fence or an empty one degrades to ordinary markdown. `graphic` (`:::graphic name="<name>"` plus a description paragraph): `<div class="blog-graphic" data-blog-graphic="<name>">` around `<div class="blog-graphic-description">` (through `_clean`); `BLOG_GRAPHICS` (`frozenset`, today only `agent-loop`) is the closed registry of component names, the attribute is emitted only on an exact match, and an unknown or missing name renders the same wrapper without `data-blog-graphic`, i.e. the description alone, so an author's name never reaches a file path. A graphic must have content: a `:::graphic` without a description renders nothing (empty inside, like any container), loads no component and is reported by `find_block_issues`. Markdown form (`to_markdown`, no HTML in any of them): `chart` is `**title**` (when non-empty) and the inside, i.e. the source table; `diagram` is `**title**`, the description and a `mermaid` fence; `terminal` is `**title**` and a `console` fence whatever the source language was; `graphic` is the description alone, without a label or the component name. A rebuilt fence is made longer than any backtick run in its content, and a block without its fence falls back to title plus inside (for a `diagram` with an empty `mermaid` fence: title plus the description, the empty fence dropped). `collect_block_assets(markdown) -> BlockAssets` (frozen dataclass: `has_diagram: bool`, `graphics: tuple[str, ...]`) tells the page what to load, over the same `_split_containers` path as the renderer, so containers inside fenced code and unclosed ones do not count: `has_diagram` is true when at least one `:::diagram` has a non-empty `mermaid` fence (exactly the ones that get `data-blog-diagram`), and `graphics` lists the `BLOG_GRAPHICS` names used by a `:::graphic` with a non-empty inside, without duplicates, in order of first use; it never raises (`BlockAssets(False, ())` on error). `blog.py::public_page` passes both to the template as `has_diagram` and `graphics` (a list), and `templates/blog/page.html` emits, in `{% block head %}` after `blocks.css` / `blocks.js`, one `<link>` and one `<script defer>` per name from `/static/blog/graphics/<name>.css|.js` and, only when `has_diagram`, exactly one `<script src="https://cdn.jsdelivr.net/npm/mermaid@11.17.2/dist/mermaid.min.js" integrity="sha384-..." crossorigin="anonymous" defer>` (pinned version with SRI; an external script on top of the Tailwind CDN one that `layouts/landing.html` loads on every page), so a post without a diagram contains the string `mermaid` nowhere in its HTML; `layouts/landing.html` is unchanged. `static/blog/blocks.js` then calls `mermaid.initialize({startOnLoad: false, securityLevel: "strict", theme})` and renders each source (read with `textContent`) into the canvas, adding `blog-diagram-rendered`, which hides the source in CSS, while a missing library or a render error leaves description and source visible; types `[data-blog-terminal]` content when it scrolls into view, skipped under `prefers-reduced-motion: reduce`; and calls `window.BlogGraphics[name].mount(el)` for each `[data-blog-graphic]`, adding `blog-graphic-mounted` on success (the description then stays in the DOM for screen readers only), with an exception in `mount` leaving the description. Components live in `static/blog/graphics/<name>.js` and `.css`; the contract (one `mount(el)` function, no external requests, `prefers-reduced-motion`, rules scoped to `.blog-graphic[data-blog-graphic="<name>"]`, dark theme through `.dark`) is in `static/blog/graphics/README.md`, and a new component is its two files plus an entry in `BLOG_GRAPHICS`, reviewed in an MR. Chart colours come from the CSS variables `--blog-chart-1..6` (plus axis, grid, label and surface) defined on `.blog-content .blog-chart` and overridden under `.dark` in `static/blog/blocks.css`. `find_block_issues(markdown) -> list[BlockIssue]` (frozen dataclass: `rule`, `level`, always `error`, `line`, the 1-based line of the container's opening, taken from the new `_Container.line`, and a Polish `message`) is the lint helper for graphic blocks, with fixed rule names: `graphic-missing-description`, `graphic-unknown-name` (a name outside `BLOG_GRAPHICS` or no `name`), `chart-missing-data` (no table that `parse_chart_table` can read), `diagram-missing-description`, `diagram-missing-source` (no non-empty `mermaid` fence), `terminal-missing-content` (no fence or an empty one). One container can yield two issues, a post without graphic blocks or with correct ones yields an empty list, and it never raises (empty list on error). It checks neither the chart `type` nor whether a `pie` can be drawn, and since MON-262 its only caller is the post lint, `services/blog_lint.py`. `iter_source_lines(markdown) -> list[SourceLine]` (MON-262; frozen dataclass: `number` from 1, `text`, `in_code`, true for a fence line and its content, and `container`, the type of the closed registered container the line belongs to, its `:::` marker lines included, or `None`) gives the lint the source lines with the context the renderers use, following the rules of `_split_containers`, so an unclosed container and a container of an unknown type are plain lines; it never raises (empty list on error) and changes neither `find_block_issues` nor any renderer. Tests: `tests/unit/test_blog_blocks.py`, `tests/unit/test_blog_chart.py`, `tests/integration/test_blog_public.py`
- `services/blog_chart.py` (MON-257) - server-side SVG chart for the `:::chart` block, stdlib only, called by `blog_blocks.py`. `parse_chart_table(markdown) -> ChartData | None` reads the first markdown table (header row, `|---|` separator row, data rows): the first column holds the labels, every further column is a series named by its header. It returns `None` when there is no table, no data row, fewer than 2 columns, a row with a different cell count than the header, or a non-numeric series cell; a number has its whitespace removed and `,` read as the decimal separator, and its shape is checked by a regex before `float()`, so `nan`, `inf` and `1_0` are not numbers. `render_chart_svg(chart_type, title, data) -> str | None` builds the SVG for a type from `CHART_TYPES` (`bar`, `line`, `pie`): `bar` and `line` draw every series (a legend appears above the plot when there is more than one) and accept negative values, `pie` draws the first series only. It returns `None` for an unknown type, no labels or series, a series whose length differs from the labels, and a `pie` with a negative value or a sum of 0 or less. The root is `<svg class="blog-chart-svg" role="img" viewBox="0 0 640 360" xmlns="http://www.w3.org/2000/svg">`, whose first children are `<title>` (`Wykres` for an empty title) and `<desc>` (a Polish text summary of the data: chart kind, series and value per label), and the result is well-formed XML. Security model: the SVG is built only from parsed data and is appended after sanitization, so it never passes through `nh3` and the tag allowlist in `services/wiki.py` is not widened for it; every author text (title, labels, series names) goes through `_esc`, which is `html.escape` plus `[` written as `&#91;` (the SVG lands in the page before `_link_footnotes` runs, so no author text in it may contain the sequence `[^`, or a footnote reference would be substituted inside the chart), every number in an attribute comes from a `float`, so a `<script>` label creates no element. The SVG carries no colour: shapes have `blog-chart-series-N`, legend swatches `blog-chart-swatch-N` (N = 1..6, cycling), axes `blog-chart-axis`, grid lines `blog-chart-grid`, texts `blog-chart-label`, with no hex value and no `style` attribute. `ChartSeries` (`name`, `values`) and `ChartData` (`labels`, `series`) are frozen dataclasses. Neither function ever raises (errors are logged and answered with `None`). Tests: `tests/unit/test_blog_chart.py`
- `services/blog_lint.py` (MON-262) - lint of a blog post for AI readers, behind `lint_blog_post` (MCP), `GET .../blog/posts/{page_id}/lint` (API v2) and `monolynx blog lint` (CLI). `lint_post(markdown, meta, *, today=None) -> LintResult` is pure (no DB, no network) and never raises, whatever the text (empty, frontmatter only, an unclosed container); `today=None` means `date.today()`. `LintMeta` (frozen dataclass: `description`, `last_verified_at`, `has_translation`) carries what the text does not hold, `LintIssue` is `rule`, `level`, `line`, `message` (Polish), and `LintResult` is `issues` sorted by `(line, rule)` plus `score`, with the properties `error_count`, `warning_count`, `info_count` and `has_errors`. Score: `max(0, 100 - 20 * errors - 5 * warnings)` (`ERROR_PENALTY`, `WARNING_PENALTY`); an `info` issue does not lower it. `line` is the 1-based line of the SOURCE: a leading `---...---` frontmatter is skipped by the analysis but does not shift the numbering, and metadata issues and issues with no place in the text have `line = 0`. Rules, errors: `description-missing`, `description-length` (outside 50..300 after `strip()`; the upper bound is `DESCRIPTION_MAX_LENGTH` from `services/blog.py`), `tldr-missing` (the first non-empty line after the frontmatter and an optional single H1 is not `> [!TLDR]`), `tldr-points` (list items in the TLDR block outside 2..5), `image-alt-short` (alt text shorter than 11 characters after `strip()`), `heading-multiple-h1` (the second and every further H1), `heading-level-skip` (a heading more than one level below the previous one; the start level is 1, so a first H3 is a skip), and the six rules of `blog_blocks.find_block_issues` under their own names, with the line in source numbering. Warnings: `h2-starts-with-pronoun` (the first text line under an H2 starts with an entry of `REFERRING_PRONOUNS`, PL and EN), `h2-no-question` (no H2 ends with `?`, also when there is no H2), `link-non-descriptive` (link text in `NON_DESCRIPTIVE_LINK_TEXTS`, e.g. `tutaj`, `kliknij`, `here`, `link`), `last-verified-missing`, `last-verified-stale` (older than `LAST_VERIFIED_MAX_AGE_DAYS`, 180), `em-dash` (U+2014 in a text line, one issue per line). Info: `translation-missing`. Headings, images, links and em-dashes inside fenced code (backticks or tildes) do not count, and a `###` inside `:::faq` is not a section heading. The spec rule "numbers and product claims carry a date or a version" is deliberately not implemented. `lint_post_by_id(db, user, project, page_id, *, content_fn=None)` follows `get_post`: `ensure_permission()` for `wiki:read` first, then `Strona wiki nie istnieje` / `Wpis bloga nie istnieje`, the content through an injectable `content_fn` (lazy import of `services.wiki.get_page_content`), and `has_translation` true when the post has `translation_of_id` or another `BlogPost` points at it; a pure read, no commit. An unexpected error inside `lint_post` is logged and answered with the single error `lint-failed` (line 0) instead of an exception. Two helpers keep the channels equal: `lint_result_dict(page_id, result)` builds the dict shared by the MCP tool and the v2 response, and `format_lint_table(result)` the markdown table with the score line that only the MCP tool adds as `table`. The source lines come from `blog_blocks.iter_source_lines`. `LintResult` is the input of the publish gate: `services/blog.py::publish_post` (MON-263) calls `lint_post_by_id` and refuses the publication on `has_errors` unless `force` is set, naming the rules of level `error`. Tests: `tests/unit/test_blog_lint.py`

- Plugin versioning (MON-177, `.claude/rules/plugin-version-bump.md`): a ticket never bumps the version. It adds its changelog entry under `### Unreleased` at the top of `## Changelog` in `plugin/README.md`, every top-level bullet prefixed with the ticket key (`- MON-123: ...`), and leaves `plugin/.claude-plugin/plugin.json` and `plugin/.codex-plugin/plugin.json` alone; `work` and `work-simple` paste this rule into every developer prompt as the shared block `changelog-unreleased`. The merger assigns the number: minor for a new skill, hook or script since the last release, patch otherwise, `Unreleased` -> `X.Y.Z` plus both manifests in one commit. When tickets merge into an integration branch (`MONOLYNX_MR_TARGET`, the dispatcher's target mode) the number is assigned on that branch before it merges to `main`, so `main` never sees `Unreleased`; when a ticket merges straight to `main`, the merger bumps on the MR branch before merging (a human - `mr-queue` does not do it), and `sprint-end` targeting `main` is only a safety net after a merge without a number. The bump is done by the `version-bump` job (4c) of `/monolynx:sprint-end`, which proposes the number, asks (no question under `MONOLYNX_SPRINT_RUN=1`, since the result still waits for a human MR merge), prepares `release/plugin-X.Y.Z` in a separate worktree from `origin/<target>`, checks it with `validate_plugin_consistency.py --release` and commits/pushes/opens the MR per `MONOLYNX_AUTOCOMMIT`/`AUTOPUSH`/`AUTOMR`. **CLI** (`cli/src/monolynx_cli/`) - standalone command-line client, PyPI package `monolynx-cli` (user docs: `cli/README.md`):
- Typer app with two entry points, `monolynx` and the short alias `mnx` (`[project.scripts]` in `cli/pyproject.toml`, both `monolynx_cli.main:app`); `requires-python = ">=3.10"`, deliberately lower than the backend's Python 3.12, so the CLI installs on older systems
- Depends only on the HTTP API v2 (`/api/v2`, Bearer token), never on backend code: it imports nothing from `src/monolynx/` and the backend imports nothing from `cli/`. Not to be confused with `src/monolynx/cli.py` (`python -m monolynx.cli <command>`), the admin CLI inside the backend container that the `Makefile` targets call (`createsuperuser`, backfills; see `.claude/rules/makefile-cli.md`)
- `main.py` - root callback with the global flags, given BEFORE the group name (`monolynx -o json auth whoami`): `--output/-o table|json|yaml|csv`, `--no-color`, `--quiet/-q`, `--profile`, `--project`, `--debug`, `--timeout`, `--version`; registers 17 command groups plus two standalone root commands (not groups), `completion <shell>` and `version [--check]` (MON-232, `commands/version.py`: `monolynx version` prints `{"current"}` with no network call, `monolynx version --check` adds `latest`, `update_available` and `upgrade_command` from the public PyPI JSON API; an unreachable PyPI is exit 0 with `latest: null`, because the plugin's transport preflight calls it), and maps every `MonolynxError` to an exit code: 0 success, 1 API error (4xx other than 401/403, 429/5xx after retries) or local error, 2 usage error, 3 auth error (401/403, failed refresh, no token), 4 network error
- `client.py` - `MonolynxClient` (httpx): Bearer header, max 4 attempts (GET/DELETE retried on 429 and 5xx, POST/PATCH only on 429), one token refresh after 401, `--debug` log with a masked token; `oauth.py` - OAuth 2.1 Authorization Code + PKCE login with a loopback redirect on `127.0.0.1`
- `config.py` - TOML config at `platformdirs.user_config_dir("monolynx")/config.toml` with named profiles (`[general] active_profile`, `[profile.<name>]`), atomic write, file mode 0600; resolution order: flag, then `MONOLYNX_*` env var, then profile
- `output.py` - commands never print data themselves: they pass a structure to `emit(ctx, data)`, which calls `render()` for the selected format (table in a TTY, JSON otherwise); progress messages go to stderr through `echo_stderr()` (silenced by `--quiet`)
- `commands/` - one `typer.Typer()` per group with real commands (9 groups: `auth`, `config`, `project`, `member`, `ticket`, `sprint`, `wiki`, `blog`, `graph`), shared helpers in `commands/_common.py`; the remaining 8 groups (`monitoring`, `issues`, `time`, `plan`, `rozliczenia`, `pipeline`, `heartbeat`, `role`) are empty placeholders for modules without API v2 endpoints
- `commands/graph.py` (MON-248) - read-only `graph` group over `/api/v2/projects/{slug}/graph/*`: `graph nodes [--type] [--search] [--limit]`, `graph node <node_id> [--depth] [--relation-type ...] [--node-type ...]` (both options repeatable), `graph query [--node-type] [--search] [--limit]`, `graph path --source-id ID --target-id ID` (both required), `graph stats`. Typer enforces the same bounds as the API (`--depth` min 1, with the server capping it at 5; `--limit` 1..1000 in `graph nodes` and `graph query`), so an out-of-range value is exit code 2 with no HTTP request. Filters the user did not set are not sent, so defaults stay on the server. Every response shape is checked before `emit()`: a missing required field or a wrong type is a contract error (`Nieprawidłowa odpowiedź serwera`, exit code 1), never an empty result with exit 0. There are no graph write commands
- `commands/blog.py` (MON-261) - `blog` group over `/api/v2/projects/{slug}/blog/posts*`: `blog list [--status published|draft]` (all pages through `fetch_all`, flat list; an unset filter is not sent; the table format shows only `title`, `slug`, `is_public`, `lang`, `published_at` and `tags` joined with `, `, while json, yaml and csv carry every field), `blog get <page_id>` (metadata, public URLs and markdown content) and `blog meta <page_id> [--slug] [--description] [--author] [--tag ...] [--no-tags] [--lang] [--translation-of] [--cover] [--verified]` (PATCH with only the given options; `--author` is sent as `author_name`, `--tag` is repeatable and replaces the tags, `--no-tags` sends `"tags": []`, and an empty string for `--translation-of`, `--cover` or `--verified` sends `null` and clears the field). `blog meta` without any option, or with `--tag` and `--no-tags` together, is exit code 2 with no HTTP request. Every response shape is checked before `emit()` (`page_id`, `title`, `slug`, `is_public`, a `tags` list, the `public_url` and `markdown_url` keys, plus `content` in `blog get`): a contract error is `Nieprawidłowa odpowiedź serwera`, exit code 1. `blog lint <page_id>` (MON-262) is a GET on `.../blog/posts/{page_id}/lint`: json and yaml carry the full report, the table format prints one row per issue (`line`, `level`, `rule`, `message`) and the line `Ocena: <score>/100` on stderr (silenced by `--quiet`). The report is printed first and only then the command exits with code 1 when at least one issue has the level `error`; warnings and infos alone are exit code 0, so exit code 1 with a report on stdout is a lint result, while exit code 1 without one is an API or contract error (the shape check covers `page_id`, the four integer counters and every element of `issues`). `blog publish <page_id> [--force]` (MON-263) is a POST on `.../blog/posts/{page_id}/publish` that always sends the body `{"force": <bool>}`; the response must pass the post shape check and the lint shape check on its `lint` field. A refusal by the lint is a 422, so exit code 1 with the reason on stderr and nothing on stdout; `--force` is a switch without a value. `blog unpublish <page_id>` is a POST on `.../blog/posts/{page_id}/unpublish` with no body and the post shape check. Post content stays in `monolynx wiki`; `wiki create --public` and `wiki update --public` remain the lower level of publishing, without the lint gate

## Key technical decisions

- All DB columns storing error data use PostgreSQL JSONB (exception, request_data, environment)
- Issue grouping: `UniqueConstraint("project_id", "fingerprint")` — fingerprint ignores line numbers for stability
- `event_count` is denormalized on Issue to avoid COUNT(*) queries
- UUID primary keys everywhere (no auto-increment)
- Session middleware from Starlette (cookie-based, signed with SECRET_KEY)
- Alembic configured for async via `asyncio.run()` in `env.py`
- Slug validation: `^[a-z0-9]+(?:-[a-z0-9]+)*$`
- Project deletion is soft delete (`is_active = False`), filtered in all dashboard queries
- After `db.rollback()` in views, always re-query objects before passing them to Jinja2 templates (avoids MissingGreenlet from lazy loading in sync rendering)
- User invitation flow: superuser creates user → `invitation_token` (UUID4) + 7-day expiry → optional email with link → user sets password via `/auth/accept-invite/{token}` → token cleared
- `is_superuser` flag stored in session at login for navbar visibility (`request.session.get('is_superuser')` in templates); users with `password_hash=None` cannot log in
- SMTP configuration optional (`SMTP_HOST=""` disables email); `APP_URL` used for building invitation links
- Pagination pattern: query param `page` (int, default=1), fixed `per_page`; count total with `func.count()`, then LIMIT/OFFSET; pass `page`, `total_pages`, `has_next`, `has_prev` to template
- Lists default to hiding completed/closed items (completed sprints, tickets from completed sprints); toggle via query params (`status=all`, `show_completed_sprints=1`)
- Flash messages via `flash(request, message, type)` stored in `request.session["_flash_messages"]`
- MCP tokens use `osk_` prefix with SHA256 hash stored in DB; raw token shown only once at creation
- Database name is `open_sentry` (historical, kept for backwards compatibility)
- Time tracking entries have a status workflow: draft → submitted → approved/rejected
- PDF reports generated server-side with weasyprint
- Wiki content stored in MinIO (markdown files), metadata in PostgreSQL; `minio_path` column links to object storage
- Wiki RAG search uses pgvector extension (HNSW index, cosine similarity); chunked embeddings (~500 tokens per chunk with overlap) via OpenAI `text-embedding-3-small`; `OPENAI_API_KEY=""` disables embeddings gracefully
- LLM Wiki method (Karpathy-style): opt-in per project via `Project.wiki_llm_enabled` (bool, default False); gated like `embeddings.is_enabled()` - when OFF the tools/skills return a clear no-op/ValueError. Treats the wiki as a growing artifact (vs RAG from scratch) curated through INGEST/QUERY/LINT operations. Reserved system-page slugs `wiki-index`, `wiki-log`, `wiki-schema` (prefix `wiki-`, since `SLUG_PATTERN` forbids underscores); the schema is itself an editable page seeded from `DEFAULT_WIKI_SCHEMA`. Backlinks are stored in PostgreSQL via the `WikiBacklink` model (NOT in Neo4j - Neo4j stays exclusively for the Connections/code module); backfill via `make backfill-backlinks`. Contradictions are flagged inline with the marker `> **Sprzeczność [date]:**`
- Markdown rendering shared via `render_markdown_html()` from `services/wiki.py` — used in wiki pages, ticket descriptions, and comments; frontend uses Tailwind `prose prose-invert` classes
- Public blog (MON-254): post metadata lives in `blog_posts`, 1:1 with `wiki_pages` (`page_id` is both the primary key and the foreign key, `ON DELETE CASCADE`); `models/wiki_page.py` has no relationship to it, queries join explicitly. `WikiPage.is_public` stays the only exposure switch: a `BlogPost` row alone publishes nothing. The post slug is set once, when the row is created (at first publication, or at the first `set_post_meta` on a page that is not public yet), copied from the wiki slug, and from then on is independent of the page title and of the wiki slug; it is unique globally (`uq_blog_posts_slug`), not per project, and an explicit change keeps the old value in `previous_slugs`, which `/blog/{slug}` answers with a 301. Migration `j1e2f3a4b5c6` creates only this table and backfills a row for every already public page (`slug` = page slug, `published_at` = `created_at`, `lang` = `pl`), so addresses that worked before keep working. `/sitemap.xml` (`main.py::sitemap_xml`) lists `/blog/` and one URL per public post taken from `BlogPost.slug`, with `lastmod` from `last_verified_at`, then `published_at`, then the page's `updated_at`
- Blog post blocks (MON-255, MON-256, MON-257): a block is written as plain, readable markdown (GitHub alerts, a `-- Author, role` line, an image title, `title="..."` on a fence, `:::type` containers) and the server generates its HTML from a closed list of renderers in `services/blog_blocks.py`; every block has two renderers, `to_html` and `to_markdown`. Author content is sanitized by a single `nh3` pass that allows no `class` and no `id`, and block HTML is inserted after it through placeholder tokens with a random nonce, so `blog-*` classes and `id` attributes can only come from a renderer, never from the post. The container registry (`CONTAINER_BLOCKS`) holds 13 blocks: 9 structural ones since MON-256 (`faq`, `steps`, `stats`, `compare`, `details`, `gallery`, `video`, `cta`, `glossary`) and 4 graphic ones since MON-257 (`chart`, `diagram`, `terminal`, `graphic`). A registered container is rendered onto a token before the rest of the post is sanitized, all author markdown in it (bodies and short values such as a FAQ question, a step name or a glossary term) through the same `nh3` cleaning and only non-markdown values (the `details` title, the video address, gallery `src`/`alt`, the CTA `href`) through `html.escape`, without widening the allowlists in `services/wiki.py`; an unknown or unclosed `:::` container, and a registered one with a wrong structure or an empty inside, degrades to ordinary markdown and never to an error. `:::video` accepts only `https` addresses whose host is on an exact YouTube/Vimeo allowlist, and the server emits neither an `<iframe>` nor a thumbnail from the video host: `static/blog/blocks.js` builds the iframe (`youtube-nocookie.com` / `player.vimeo.com`) after a click, from `data-provider` and `data-video-id` only, and without JS a plain link stays. In the markdown twin a registered container loses its `:::` lines and gets a one-line label (`**FAQ**`, `**Kroki**`, ...). `extract_structured_data()` returns the `faq`, `steps` and `videos` of a post as a dict for the future AI layer (JSON-LD), with `glossary` deliberately left out. Graphic blocks (MON-257) keep the rule that the author injects no HTML, CSS or JS: the source of every graphic is text (a table, a description, code) and the graphic is a layer over it, so each one has content without JS and in the markdown twin (`chart` = title + table, `diagram` = description + `mermaid` fence, `terminal` = `console` fence, `graphic` = description). The chart SVG is generated on the server by `services/blog_chart.py` from parsed numbers and escaped texts and appended after sanitization, without widening the `nh3` allowlist, and it carries only `blog-chart-*` classes, with colours from CSS variables for both themes. A diagram is rendered in the browser by Mermaid, loaded from a pinned CDN address (`mermaid@11.17.2` on jsdelivr, with an SRI `integrity` hash and `crossorigin="anonymous"`) only on a post that has a diagram and initialized with `securityLevel: "strict"`; it is an additional external script next to the Tailwind CDN one from `layouts/landing.html`, which every blog page already loads, and the application sends no CSP header. Custom JS lives only in the repository, as a named component in `static/blog/graphics/<name>.js|.css` listed in the closed registry `BLOG_GRAPHICS`; a name outside it renders the description alone and loads nothing, and a component's files are attached only to a post that uses it (`collect_block_assets()` -> `has_diagram`, `graphics` in the template context). `find_block_issues()` reports graphic blocks without their content (description, data, source, registered name) for a future post lint. Block styles live in `static/blog/blocks.css` and the script in `static/blog/blocks.js`; `templates/blog/page.html` loads both, plus the per-post graphic assets since MON-257. Three markdown renderers now coexist: `render_markdown_html()` (dashboard, tickets, comments; no sanitization), `render_markdown_public()` (sanitized, no blocks, kept in `services/wiki.py` with its tests but no caller in `src/`) and `render_post_html()` (blog posts)
- Blog AI layer (MON-258): every public post has a markdown twin at `/blog/{slug}.md` (YAML frontmatter + body with absolute URLs) and the list has one at `/blog/index.md`, both in `blog_ai.py`, whose router must be registered before `blog.py`'s, since `/blog/{slug}` would match the `.md` addresses. One function, `render_post_markdown_document()`, builds the document for the `.md` route and for `/blog/{slug}` with `Accept: text/markdown`, so both addresses return the same body and the same `ETag`; HTML points at the twin through `<link rel="alternate" type="text/markdown">` and a `Link` header, and varies on `Accept`. The frontmatter is serialized by hand as YAML flow style (`json.dumps` per value) instead of adding `pyyaml` as a production dependency. Caching is `ETag` + `Last-Modified` with `If-None-Match` only (`conditional_response()`), no `If-Modified-Since`. Structured data (`BlogPosting` + `BreadcrumbList` on a post, `Blog` on the list) is built as a `dict` in `services/blog.py` and neutralized in Python by `dump_jsonld()` before the template prints it with `|safe`. - Blog pages for people (MON-260): the post page and the list are plain server-rendered templates with one stylesheet, `static/blog/blog.css` (no inline `<style>`, light and dark theme through the `.dark` class of `layouts/landing.html`, long words wrapping (`overflow-wrap: anywhere` on `.blog-content`), while a table and a `<pre>` keep normal word breaking and scroll inside their own box with `overflow-x: auto`, so that a narrow screen does not scroll the page horizontally), loaded before `blocks.css`. Tests: `tests/integration/test_wiki_dashboard.py`, `tests/unit/test_blog_service.py`, `tests/unit/test_blog_blocks.py`

## Test patterns

- `conftest.py` creates real async SQLAlchemy engine (`scope="session"`, `loop_scope="session"`), wraps each test in a connection-level transaction with rollback
- Test database is per pytest run (MON-250), so parallel runs (e.g. sprint sessions in separate git worktrees) never share tables; before, every run used one `open_sentry_test` database and the `drop_all` at the end of one run removed the tables of another. The `engine` fixture creates its own database `open_sentry_test_<8 random hex chars>` (`CREATE DATABASE` + `CREATE EXTENSION IF NOT EXISTS vector` + `Base.metadata.create_all`) and drops it at session end (`DROP DATABASE ... WITH (FORCE)` after `engine.dispose()`); there is no `drop_all` on a shared database any more
- `TEST_DATABASE_NAME` overrides the name (e.g. `-e TEST_DATABASE_NAME=open_sentry_test_MON-250`). It is validated by `validate_test_db_name()` from `src/monolynx/cli.py`: it must start with `open_sentry_test_`, followed only by letters, digits, `_` and `-`, max 63 characters, otherwise `ValueError` at session start. The forced prefix keeps the dev database (`open_sentry`) from being dropped. An existing database with that name (left by an interrupted run) is dropped before creation; two concurrent runs with the SAME manual name still collide
- `make prune-test-dbs` (`python -m monolynx.cli prune-test-dbs`) removes leftovers of interrupted runs: `open_sentry_test_*` databases with no active connections (databases of runs in progress are skipped, no `FORCE`); the old shared `open_sentry_test` database without a suffix is left alone. `make test` and the CI `clean-code` job run with unchanged commands
- `client` fixture uses `httpx.AsyncClient` with `ASGITransport` and dependency overrides for `get_db`
- `login_session(client, db_session, email=...)` helper creates a User and logs in — each test uses a unique email to avoid conflicts
- Markers: `@pytest.mark.unit`, `@pytest.mark.integration`, `@pytest.mark.e2e`
- pytest-asyncio in auto mode with `asyncio_default_fixture_loop_scope = "session"` and `asyncio_default_test_loop_scope = "session"` in pyproject.toml

## Adding a new module

1. Create `dashboard/<module>.py` with its own `router = APIRouter(prefix="/dashboard", tags=[...])`
2. Add router to `dashboard/__init__.py` (respect ordering: static routes before dynamic `{slug}` routes)
3. Create templates in `templates/dashboard/<module>/`, extending `layouts/project.html` with `{% block module_content %}`
4. Pass `active_module: "<module>"` in template context for sidebar highlighting
5. Add module link to sidebar in `layouts/project.html`
6. Add a `_feature_<module>(lang)` builder to `src/monolynx/features.py` (PL + EN), register it in `_FEATURES` and `_other_modules()`, and add a tile to `templates/landing.html` — see `.claude/rules/landing-page-features.md`

- **Docker**: Multi-stage Dockerfile (builder → dev → runtime). Dev target has hot reload, runtime uses non-root user with 2 workers
- **Docker Compose (dev)**: `dev` profile with PostgreSQL 16 (pgvector/pgvector:pg16) + Neo4j 5 (neo4j:5-community) + MinIO + app (monitor loop runs in-process by default). Optional `worker` profile runs monitor loop as separate service (`make worker`)
- **Docker Compose (prod)**: `app` service with `ENABLE_MONITOR_LOOP=false` + separate `worker` service running `python -m monolynx.worker`. Worker has no ports/Traefik — only DB access. Advisory lock ensures only one worker runs checks at a time
- **CI**: `.gitlab-ci.yml` — lint → test (coverage goal 50%) → build (main only) → deploy (manual). Job `dockle-scan` (dockle 0.4.14, obraz `:test`, `--exit-code 1`) biegnie na MR zmieniającym `Dockerfile` albo `.gitlab-ci.yml`; wyjątki: `-af settings.py` (CIS-DI-0010, fałszywy alarm po nazwie pliku, dopasowanie po nazwie bazowej, więc nowy `settings.py` sprawdzić ręcznie) i `-i DKL-DI-0005` (warstwa obrazu bazowego `python:3.12-slim` z `apt-get dist-clean`, którego dockle 0.4.14 i 0.4.15 nie rozpoznają); powody w komentarzu nad jobem
- **Pre-commit**: ruff (check + format) and mypy with pydantic plugin

## Merge requests: pipeline must be green

Every MR is followed to the end, never fire-and-forget. After `glab mr create` (or any push to an MR branch):
1. Monitor the branch pipeline until it reaches a terminal state (`glab ci status --branch <branch>` / `glab ci get --pipeline-id <id> -F json`; poll in the background, roughly every 60s; a full `clean-code` round takes 15-20 min).
2. Merge only when the pipeline is `success`. Red pipeline: read the failing job trace (`glab ci trace <job_id>`), fix the cause on the branch, push, monitor again. `exit status 137` in `clean-code` with no failed test means the test container was SIGKILLed: before MON-175 a concurrent `clean-code` job on the same runner ran `docker rm -f db test-runner` on fixed container names and killed the other job's containers; since MON-175 the job has `resource_group: clean-code` and per-job names (`db-$CI_JOB_ID`, `test-runner-$CI_JOB_ID`, `test-net-$CI_JOB_ID`). If 137 still appears, retry the job (`glab ci retry <job_id>`) and check runner memory; it is not a code failure.
3. After merge, monitor the pipeline on `main` the same way. `deploy-staging` is a manual job and stays `manual`; every other job must be `success`. Retry on 137, fix forward on a real failure.
4. Report the outcome with pipeline ids and job statuses. A ticket goes to `done` only after the `main` pipeline is green.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
