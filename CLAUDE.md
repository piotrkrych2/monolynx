# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What is this project?

Monolynx is a multi-module project platform. It started as a minimalist error-tracking system (500ki module — named after HTTP 500 errors) and now includes a Scrum module (backlog, Kanban board, sprints, story points), a Monitoring module (URL health checks with uptime tracking), a Wiki module (markdown pages with semantic RAG search via pgvector, plus an opt-in "LLM Wiki" method with backlinks, system pages, and INGEST/QUERY/LINT operations), a Connections module (code dependency graph visualization using Neo4j), a Work Plan / Gantt module (personal per-user cross-project scheduling with Gantt and calendar views), and a Pipelines module (observability over AI agent work, modeled on GitLab CI/CD; pipeline -> step -> job hierarchy where job logs are stored as wiki pages). The architecture supports adding new modules via the sidebar navigation.

## Commands

All commands run inside Docker. Never run Python commands locally — always use `docker compose exec app <command>`. Exception: stdlib-only repo scripts in `scripts/` and `plugin/scripts/` (`sync_skills.py`, `validate_plugin_consistency.py`, `*_state.py`) run on the host with `python3`, exactly as the `Makefile` targets `sync-skills`, `sync-skills-check` and `validate-plugin` do. Application code under `src/`, `pytest`, `ruff` and `mypy` still run only in Docker.

```bash
# Development environment (Docker Compose: PostgreSQL + FastAPI with hot reload)
make dev                              # Start dev env (port 8000, configurable via APP_PORT)
make down                             # Stop dev env (app + worker)
make worker                           # Start monitor worker separately (dev)
make logs                             # Tail app logs
make setup                            # Configure local dev environment
make help                             # Show available commands

# Code quality
make lint                             # ruff check --fix + ruff format + mypy (auto-fixes!)
make fmt                              # ruff check --fix + ruff format (same as lint, without mypy)

# Testing (inside Docker)
make test                             # All tests with coverage
docker compose exec app python -m pytest tests/unit/ -v                 # Unit tests only
docker compose exec app python -m pytest tests/integration/ -v          # Integration tests
docker compose exec app python -m pytest tests/unit/test_fingerprint.py::TestFingerprintGeneration::test_same_exception_same_location_same_fingerprint -v  # Single test
make prune-test-dbs                   # Drop leftover per-run test databases (open_sentry_test_*) with no active connections

# Database migrations
make migrate                          # Run pending migrations
make migration msg="description"      # Generate new migration

# Admin
make createsuperuser                  # Create admin user (interactive prompt)

# Wiki RAG
make backfill-embeddings              # Generate embeddings for existing wiki pages
make backfill-backlinks               # Generate backlinks for existing wiki pages (LLM Wiki)
make backfill-dependencies            # Move prose ticket dependencies into blocked_by_ids (dry-run; ARGS=--apply writes)

# Build
make build                            # Build production Docker image

# CLI (cli/, package monolynx-cli): build and run in a throwaway container, from the repo root.
# The mount is read-only and the package is copied inside the container, because pip install
# as root would write build/ and *.egg-info into the repo.
docker run --rm -v "$PWD/cli":/src:ro python:3.10-slim sh -c "cp -r /src /cli && pip install -q /cli && monolynx --help"
```

**Important**: When generating Alembic migrations with autogenerate, always review the output — it may include tables from a previous migration if the DB was empty at generation time. Each migration must only contain its own new/changed tables.

## Architecture

Three separate packages in one repo: the backend (`src/monolynx/`), the Django SDK (`sdk/`) and the command-line client (`cli/`).

**Backend** (`src/monolynx/`) — FastAPI async server:
- `main.py` registers routers lazily via `_register_routers()` to avoid circular imports; lifespan optionally starts monitor checker loop (controlled by `ENABLE_MONITOR_LOOP`, default true for dev, false in prod)
- `config.py` uses pydantic-settings, reads from env vars / `.env` file (see `.env.example`)
- `database.py` provides async SQLAlchemy session via `get_db()` FastAPI dependency
- `constants.py` — shared constants for Scrum (ticket statuses, priorities, sprint statuses, member roles, label mappings), Monitoring (interval units, Polish labels), Time Tracking (entry statuses, report defaults), and Graph (node types, edge types, Polish labels)

**Dashboard module system** (`dashboard/`):
- `dashboard/__init__.py` — combines all sub-routers into one `router`; ordering matters: static routes (users, settings, profile) before dynamic `{slug}` routes to avoid slug collision
- `dashboard/helpers.py` — shared `_get_user_id()`, `SLUG_PATTERN`, `templates` instance, `flash()` helper for session-based flash messages
- `dashboard/auth.py` — login/logout (`/auth/*`), invitation acceptance (`/auth/accept-invite/{token}`)
- `dashboard/projects.py` — project list, create (`/dashboard/`, `/dashboard/create-project`)
- `dashboard/profile.py` — user API token management for MCP access (`/dashboard/profile/*`)
- `dashboard/users.py` — user management, superuser-only (`/dashboard/users/*`); invitation system with token generation and email
- `dashboard/sentry.py` — error tracking module "500ki": issues list, issue detail, SDK setup guide (`/dashboard/{slug}/500ki/*`)
- `dashboard/scrum.py` — Scrum module: backlog (with pagination + filtering), Kanban board, ticket CRUD with comments, sprints with status filtering (`/dashboard/{slug}/scrum/*`)
- `dashboard/monitoring.py` — URL monitoring module: monitor CRUD, check history with pagination, toggle on/off (`/dashboard/{slug}/monitoring/*`); includes SSRF protection (blocks localhost, private IPs), limit 20 monitors per project
- `dashboard/wiki.py` — Wiki module: page CRUD, tree hierarchy, markdown rendering, image upload to MinIO, semantic search via pgvector (`/dashboard/{slug}/wiki/*`); page detail shows an "incoming links" (backlinks) panel, gated on `wiki_llm_enabled`
- `dashboard/connections.py` — Connections module: graph visualization with Cytoscape.js, node/edge CRUD forms, graph API endpoint, setup guide page (`/dashboard/{slug}/connections/*`); graceful degradation when Neo4j unavailable. The graph is populated by the external [graphify](https://github.com/Graphify-Labs/graphify) extractor (offline tree-sitter AST, installed by the runner owner, never by CI) via `cicd/sync_graph.py` -> `replace_graph`; skills `/monolynx:create-graph-ci-script` (CI) and `/monolynx:graph-sync` (local, guided). Edge metadata carries `confidence` (EXTRACTED/INFERRED/AMBIGUOUS) and `source_relation`; taxonomy mapping lives on the wiki page "Mapowanie taksonomii Graphify -> Monolynx"
- `dashboard/settings.py` — project settings, member management (`/dashboard/{slug}/settings`)
- `dashboard/reports.py` — global cross-project work reports with multi-select filtering (project, user, sprint), date range, and PDF export via weasyprint (`/dashboard/reports`)
- `dashboard/work_plan.py`: Work Plan module (prefix `/dashboard/plan`): personal per-user cross-project scheduling via junction model (`User x Ticket x Date`), Gantt view (frappe-gantt) and monthly calendar, REST endpoints for entries CRUD plus JSON data and ticket autocomplete; independent of sprint assignment
- `dashboard/pipelines.py` - Pipelines module: pipeline list (with status/type filtering + pagination), pipeline detail (step columns research/coding/wrap-up with job cards), job detail (markdown log rendered from wiki), JSON API endpoints and HTMX partials for 15s live polling (`/dashboard/{slug}/pipelines/*`); session auth plus `scrum:read` (superuser bypass, no membership needed), read-only UI (pipelines are created by skills via MCP, not from the dashboard)

**Public blog** (`blog.py`): router with prefix `/blog`, registered in `main.py` unconditionally (not gated by `SKIP_LANDING_PAGE`), with no session and no RBAC. A post is a wiki page with `is_public=True` plus its `BlogPost` row (MON-254); the routes join the two explicitly (`BlogPost.page_id == WikiPage.id`) and filter `WikiPage.is_public` in SQL, so a private page, an unknown slug and a public page without a `BlogPost` row are all 404, never 403.
- `GET /blog/` - post list through `services/blog.py::list_public_posts`, 20 per page, ordered by `published_at DESC` (then `slug`), so editing an older post does not reshuffle the list. The teaser is `BlogPost.description`; when it is empty the route falls back to a summary extracted from the page content (`extract_summary`), read from MinIO in parallel (`asyncio.gather`). A MinIO error leaves that one teaser empty and the list still answers 200; with a non-empty `description` MinIO is not read at all. The date shown is `published_at`, falling back to the page's `created_at`
- `GET /blog/{slug}` - lookup by `BlogPost.slug` through `get_public_post_by_slug`: the current slug renders the post (200), a slug from `previous_slugs` of a public post answers 301 to `/blog/{current slug}` with the query string preserved (`?lang=`), anything else is 404. There is no fallback to the wiki slug. Content goes through `render_markdown_public()` (`services/wiki.py`: the shared markdown renderer followed by `nh3.clean()` with an allow-list of tags, attributes and URL schemes); a MinIO error while reading the content is mapped to 404. Breadcrumbs, child pages and backlinks list only `is_public` pages and link by `BlogPost.slug`. Meta description and Open Graph come from `description` (fallback: the content summary), `article:published_time` from `published_at` (fallback `created_at`), and `og:image` / `twitter:image` from the cover attachment when `cover_attachment_id` is set and the attachment still belongs to the page (absolute URL of the attachment route below; otherwise the layout's default image)
- `GET /blog/{slug}/attachments/{attachment_id}/{filename}` - public attachment of a post, looked up by the current `BlogPost.slug` only (an old slug is 404 here, no redirect). The attachment must belong to that page (`WikiAttachment.wiki_page_id`), otherwise 404. Only PNG, JPEG, GIF and WebP are served `inline`; every other type, SVG included, goes out as `attachment`. Every response, 404 included, carries `X-Content-Type-Options: nosniff`, and a MinIO error is 404

**API v2** (`api/v2/`): skeleton REST API under `/api/v2`, foundation for domain endpoints (MON-142). `api/v2/__init__.py` - `router` (placeholder root available both with and without a trailing slash - `GET /api/v2/` and `GET /api/v2`, no redirect between them; `/api/v2/openapi.json` + `/api/v2/docs` built exclusively from `router`'s own routes; the `/me` router (`api/v2/me.py`, MON-125) included via `router.include_router(me_router)`; a catch-all `/{full_path:path}` registered last, handling GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS and returning 404 problem+json for any unmatched v2 path - HEAD/OPTIONS must be listed explicitly, otherwise Starlette treats the request as a path match with the wrong method and returns 405 instead of 404) and `register_api_v2(app)` (a pure ASGI `X-Request-Id` middleware class, registered via `app.add_middleware`, deliberately not `@app.middleware("http")`/`BaseHTTPMiddleware` because MCP is mounted at `/` and serves streamable HTTP/SSE that a buffering middleware would break; plus problem+json exception handlers for `ApiV2Error`/`HTTPException`/`RequestValidationError`. Both the middleware and the handlers use one shared boundary helper, `_is_v2_path()` (`path == "/api/v2"` or `path.startswith("/api/v2/")`), so a route under an unrelated prefix like `/api/v2foo` is never mistaken for v2; outside that boundary the handlers delegate to FastAPI's default handlers, so the dashboard and API v1 keep their existing `{"detail": ...}` format). The `HTTPException` handler preserves `exc.headers` (e.g. `Allow`, `WWW-Authenticate`) in the problem+json response. `api/v2/deps.py` - `get_api_user()` (authorizes `Authorization: Bearer <token>` via `verify_bearer_token()`, every 401 problem+json response carries `WWW-Authenticate: Bearer` per RFC 6750) and `get_api_user_and_project()` (active project by slug + membership check, 404/403 problem+json). `api/v2/errors.py` - `ApiV2Error(status, title, detail=None, type="about:blank", headers=None)`, with `headers` propagated to the response the same way as `headers` on `fastapi.HTTPException`. `api/v2/me.py` - `GET /me` (MON-125), protected by `get_api_user`, returns `MeResponse(id, email)` for the token's owner; 401 problem+json comes from `get_api_user` itself.

**API v2 domain routers** (MON-142): `api/v2/projects.py`, `tickets.py`, `sprints.py`, `wiki.py`, `graph.py` (MON-248, read-only) and `blog.py` (MON-261) are thin FastAPI routers with no prefix of their own, attached via `include_router` to `router` in `api/v2/__init__.py` BEFORE the catch-all. They map MCP tools 1:1 (Projects 11, Tickets 14 incl. `get_board`, comments and acceptance criteria, Sprints 7 incl. `get_burndown`, Wiki 8, Graph 5 reads, Blog 3) onto the same service functions (`services/projects.py`, `services/tickets.py`, `services/sprint.py`, `services/burndown.py`, `services/wiki.py`, `services/embeddings.py`, `services/graph.py`, `services/blog.py`), so business logic lives in one place. Request/response schemas live in `schemas/api_v2/`.
- Blog post metadata (MON-261): `api/v2/blog.py` exposes 3 routes under `/projects/{slug}/blog/posts`, one per tool, over `services/blog.py`: `GET .../blog/posts` (`list_blog_posts`; optional `status=published|draft`, `PaginatedResponse[BlogPostResponse]` with the default `per_page=100` through `paginate()`), `GET .../blog/posts/{page_id}` (`get_blog_post`; `BlogPostDetailResponse`, the same fields plus `content`) and `PATCH .../blog/posts/{page_id}` (`set_blog_post_meta`; `BlogPostResponse`). Schemas in `schemas/api_v2/blog.py`; `BlogPostMetaUpdateRequest` has `slug`, `description`, `author_name`, `tags`, `lang`, `translation_of_id`, `cover_attachment_id` and `last_verified_at`, all optional, and deliberately neither `published_at` nor `is_public`. The PATCH body goes to `set_post_meta` through `model_dump(exclude_unset=True)`: an absent field stays unchanged, `null` clears `translation_of_id`, `cover_attachment_id` and `last_verified_at` and is a 422 for the other fields, `"tags": []` clears the tags, and `{}` is 200 with no change. The service checks the permission first (`wiki:read` for both GETs, `wiki:write` for PATCH), so a role without it gets 403 for a nonexistent `page_id` too; a page outside the project (`Strona wiki nie istnieje`) and a wiki page without a `BlogPost` row (`Wpis bloga nie istnieje`, added to the not-found list of `service_error()`) are 404, an unknown `status` and a validation error are 422, and a malformed `page_id` is 422 from FastAPI validation. `public_url` and `markdown_url` are `null` for a non-public page. Only the detail GET reads the content from MinIO: a storage error there is logged (`logger.exception`) and answered with 503 problem+json (`title` "Service Unavailable", `detail` "Treść wpisu jest chwilowo niedostępna"), never 500; the list and PATCH do not read MinIO. Tests: `tests/integration/api_v2/test_blog.py`
- `api/v2/common.py` - `service_error()` maps a service `ValueError` to problem+json: 404 for a closed list of "resource from the path does not exist" messages (full match, so e.g. an invalid blocker in the body stays 422), 403 for messages starting with "Brak uprawnienia", 422 otherwise (usage: `except ValueError as exc: raise service_error(exc) from exc`). Role permissions are enforced in both channels (MON-241): membership from `get_api_user_and_project()` is no longer enough for the Scrum and Wiki routes. Service functions that take `(db, user, project, ...)` call `ensure_permission()` from `services/permissions.py` themselves; it raises `ValueError("Brak uprawnienia {module}:{action}")`, which `service_error()` maps to 403, so every endpoint calling such a service needs the `except ValueError` clause above (without it the refusal is a 500). `require_permission(db, user, project, module, action)` (403 problem+json with the same text in `detail`) stays in the router for service functions that take no user (`start_sprint`/`complete_sprint` - `scrum:write`, burndown - `scrum:read`, wiki page create/update - `wiki:write`, wiki page delete - `wiki:delete`, wiki search - `wiki:read`) and for the 5 endpoints that had it before (update/delete project - `settings:write`/`settings:delete`, invite/remove member - `users:write`/`users:delete`, `set_wiki_config` - `settings:write`). Permission map: reads -> `scrum:read` / `wiki:read`, creates and updates -> `scrum:write` / `wiki:write`, `delete_ticket`, `delete_acceptance_criterion` and `delete_wiki_page` -> `scrum:delete` / `wiki:delete`; `is_public=true` on a wiki page needs only `wiki:write`, the same rule as the dashboard form (there is no separate permission for publishing). The check is the first thing the handler and the service do, before the resource lookup and before any validation of their own, so a role without the permission gets 403 for a nonexistent resource too and cannot tell 404 from 403. FastAPI's request validation still runs before the handler: a malformed UUID in the path or an invalid body yields 422 regardless of the role. An endpoint that reads the resource back after a write (`POST`/`PATCH` tickets -> `get_ticket`, start/complete sprint -> `get_sprint`) checks `scrum:write` and then `scrum:read` in the router before the write, so a role with write but no read is refused before anything is committed. This is a known channel difference: the MCP tools `create_ticket`, `update_ticket`, `start_sprint` and `complete_sprint` check only `scrum:write`, so such a role writes through MCP while v2 refuses. `get_project_summary` still checks membership only. Tests: `tests/integration/test_rbac_scrum_wiki_channels.py` (roles member, read-only and owner through MCP and v2). `paginate()` pages lists the service returns in full. A malformed `page_id`, `sprint_id` or `member_id` yields 422 problem+json (FastAPI validation of a `uuid.UUID` parameter, or a `ValueError` mapped by `service_error()`), while a malformed `ticket_id` (UUID or key) or `criterion_id` yields 404, because their messages are on the not-found list of `service_error()`
- Conventions: lists return `PaginatedResponse[T]` (`list_tickets`/`search_tickets` with `per_page=20` like the tools, all other lists default to `per_page=100`); `search_wiki` and `get_board` are not paginated. `ticket_id` in the path accepts a UUID or a key (e.g. `MON-12`). The static routes `/tickets/search` and `/tickets/bulk` are registered before `/tickets/{ticket_id}`. `DELETE .../members/{member_id}` takes the `user_id` returned by `list_members` (the service takes an email, the router resolves it). `POST .../members` sends the invitation email in the router (`send_invitation_email`, like the MCP wrapper), because the service does not. Acceptance criteria are nested under the ticket. `GET .../burndown` without `sprint_id` uses the active sprint. `start_sprint`/`complete_sprint` return an error as a string, which the router turns into problem+json. Ticket blockers and spec page (MON-246): every item of `GET .../tickets` carries `blocked_by`, a list of `{id, key, title, status}` (empty when the ticket has no blockers), and the ticket detail (`TicketDetailResponse`, returned by get/create/update) adds `spec_page_id` (UUID string or `null`) next to `blocks`; `search_tickets` items carry neither. Compact list (MON-247): `GET .../tickets?compact=true` returns items without `description` through a separate schema, `TicketListItemCompact` (the fields of `TicketListItem` minus `description`), so `TicketListItem` and the default response stay unchanged
- Graph reads (MON-248): `api/v2/graph.py` exposes 5 GET routes under `/projects/{slug}/graph`, one per read tool (`list_graph_nodes`, `get_graph_node`, `query_graph`, `find_graph_path`, `get_graph_stats`), calling the same `services/graph.py` functions: `/graph/nodes` (`type`, `search`, `limit` 1..1000 default 100; a bare JSON list, not paginated), `/graph/nodes/{node_id:path}` (`depth` >= 1, default 1, capped at 5 by the service, repeatable `relation_types` and `node_types`; `{node, nodes, edges, depth_map}`; the `path` converter is there because node ids may contain `/`), `/graph/query` (`node_type`, `search`, `limit` 1..1000 default 200; `{nodes, edges}`), `/graph/path` (required `source_id` and `target_id`; `{nodes, edges}`, empty lists when there is no path) and `/graph/stats` (`total_nodes`, `total_edges`, `nodes_by_type`, `edges_by_type`). Schemas in `schemas/api_v2/graph.py`; an edge lifts `confidence` and `source_relation` out of `metadata` to the top level and keeps `metadata` intact. The shared dependency `graph_project` fixes the order of checks: token 401, project 404, membership 403, `connections:read` 403 (`require_permission()`), then graph disabled (`ENABLE_GRAPH_DB=false`) 503. A Neo4j failure during the call (`RuntimeError`, `DriverError`, `Neo4jError`) is also 503 problem+json, never 500; a `depth` below 1 or a `limit` outside 1..1000 is 422 from FastAPI validation, before the service is called; a service `ValueError` goes through `service_error()` (422), and a missing node is 404 "Node nie istnieje". Two pure helpers in `services/graph.py` are shared by MCP and v2: `ensure_search_not_blank()` (a blank `search` is an error in both channels) and `format_graph_dsl()` (the MCP tools return this Arrow DSL text, v2 returns the JSON it is built from). Graph writes (`create_*`, `delete_*`, `bulk_create_*`, `replace_graph`) have no v2 endpoint and no CLI command: the only writer is the `cicd/sync_graph.py` sync through MCP
- Tests: `tests/integration/api_v2/` (one file per resource)
- Purpose and layering: API v2 is the REST API for the `monolynx` CLI (`cli/`) and external integrations. Auth is shared with MCP: `api/v2/deps.py::get_api_user` calls the same `verify_bearer_token()` from `services/mcp_auth.py` as the MCP server, so one token (OAuth access token or legacy `osk_*`) works in both channels. Every error is `application/problem+json` (`type`, `title`, `status`, `detail`, `instance`). Business logic lives in `services/`; the MCP tools in `mcp_server.py` and the v2 routers are thin adapters over the same service functions, and a service `ValueError` becomes MCP error text or a v2 problem+json via `service_error()`. Unlike `/api/v1` (Django SDK event ingest with the `X-Monolynx-Key` project API key, health check, issue status), v2 authenticates a user, and every project route also checks membership (`get_api_user_and_project()`); on top of membership the Scrum and Wiki routes check the role permission (`scrum:*` / `wiki:*`, MON-241, see `api/v2/common.py` above), the same one the MCP tool checks, and the graph routes check `connections:read` (MON-248)
- Parity MCP <-> v2 (MON-131): `tests/integration/tool_endpoint_map.py` maps each MCP tool either to its v2 endpoint in `TOOL_TO_ENDPOINT` (`ToolEndpointSpec`: `method`, `path`, `is_write`, `field_map`, `known_differences`) or to a reason in `INTENTIONALLY_UNMAPPED`; `tests/integration/test_api_v2_parity.py` (`TestMapCompleteness`) fails on any registered tool missing from both dictionaries or on a mapped route absent from `/api/v2/openapi.json`, and `TestToolEndpointParity` runs one scenario per mapped tool through both channels. Since MON-261 (the 3 blog tools) the map holds 48 mapped tools and 74 intentionally unmapped ones (asserted in `test_every_mcp_tool_has_exactly_one_entry`); the 7 graph write tools are unmapped with one shared reason (the graph is written only by the `cicd/sync_graph.py` sync through MCP). The rule for new tools: `.claude/rules/mcp-cli-parity.md`

**Models** (`models/`) — 34 SQLAlchemy models: Project, Issue, Event, User, UserApiToken, ProjectMember, Role, Sprint, Ticket, TicketComment, TicketAttachment, TicketAcceptanceCriterion, TicketDependency, Monitor, MonitorCheck, TimeTrackingEntry, WorkPlanEntry, WikiPage, WikiEmbedding, WikiAttachment, WikiFile, WikiBacklink, BlogPost, ActivityLog, Heartbeat, Label, TicketLabel, Pipeline, PipelineStep, PipelineJob, Settlement, SettlementProject, SettlementTicket, SettlementAttachment + OAuth models (OAuthClient, OAuthAuthorizationCode, OAuthAccessToken, OAuthRefreshToken) + Base

**Services**:
- `services/fingerprint.py` — SHA256 of exception type + app-frame filenames:functions
- `services/event_processor.py` — finds-or-creates Issue by fingerprint, increments event_count
- `services/auth.py` — API key validation with in-memory cache (TTL 60s; a cache hit re-checks `Project.is_active`), bcrypt passwords, `get_current_user()` helper for session-based auth; header `X-Monolynx-Key`
- `services/email.py` — SMTP email delivery via `ThreadPoolExecutor(max_workers=1)`; never crashes application; logs warning if SMTP not configured
- `services/sprint.py` — sprint lifecycle (start checks no other active sprint; complete moves non-done tickets to backlog). Takes no user and checks no role permission, like `services/burndown.py`: the dashboard calls both too, so the check sits in the adapter (MCP tool, v2 router)
- `services/permissions.py` - RBAC per module and action: `check_permission(db, user_id, project_id, module, action)` returns a bool (superuser bypass, then the member's `role_obj.permissions`, then `DEFAULT_ROLE_PERMISSIONS` for a legacy `member.role`); `require_permission()` raises `HTTPException(403)` for dashboard routes; `ensure_permission()` raises `ValueError("Brak uprawnienia {module}:{action}")` for services and MCP tools (MON-241), the text `api/v2/common.py::service_error()` maps to 403; `get_user_permissions()` returns the user's full permission map in a project
- `services/monitoring.py` — async `check_url()` using `ThreadPoolExecutor` with configurable timeout
- `services/monitor_loop.py` — extracted monitor checker loop with concurrent checks (`asyncio.gather`), proper advisory lock via dedicated connection, reusable by both `main.py` lifespan and standalone `worker.py`
- `services/mcp_auth.py` — MCP token generation (`osk_<random>` prefix), SHA256 hashing, verification with `last_used_at` tracking; `verify_bearer_token(raw_token, db, *, legacy_verifier=None)` is the shared Bearer-auth entry point for both MCP (`mcp_server._verify_token`) and API v2 (`api/v2/deps.py::get_api_user`) - tries OAuth access token first, then falls back to legacy `osk_*`, rolling back the shared `db` session before the fallback if the OAuth path raises. `legacy_verifier` defaults to `None` and is resolved to this module's own `verify_mcp_token` at call time (never bound as a default argument value), because this module's own unit tests (`tests/unit/test_mcp_auth.py`) patch the module-level name `monolynx.services.mcp_auth.verify_mcp_token`; `mcp_server._verify_token` passes `legacy_verifier=verify_mcp_token` explicitly for a different reason - the pre-existing MCP test suite (`tests/unit/test_mcp_server.py` and others) patches `monolynx.mcp_server.verify_mcp_token` instead, and without the explicit pass that patch would have no effect on the fallback
- `services/sidebar.py` — `SidebarBadges` dataclass providing issue counts, failing monitors, 24h uptime percentage for sidebar indicators
- `services/time_tracking.py` — time tracking CRUD and aggregation for work reports
- `services/ticket_numbering.py` — auto-incrementing ticket numbers per project

- `output.py` - commands never print data themselves: they pass a structure to `emit(ctx, data)`, which calls `render()` for the selected format (table in a TTY, JSON otherwise); progress messages go to stderr through `echo_stderr()` (silenced by `--quiet`)
- `commands/` - one `typer.Typer()` per group with real commands (9 groups: `auth`, `config`, `project`, `member`, `ticket`, `sprint`, `wiki`, `blog`, `graph`), shared helpers in `commands/_common.py`; the remaining 8 groups (`monitoring`, `issues`, `time`, `plan`, `rozliczenia`, `pipeline`, `heartbeat`, `role`) are empty placeholders for modules without API v2 endpoints
- `commands/graph.py` (MON-248) - read-only `graph` group over `/api/v2/projects/{slug}/graph/*`: `graph nodes [--type] [--search] [--limit]`, `graph node <node_id> [--depth] [--relation-type ...] [--node-type ...]` (both options repeatable), `graph query [--node-type] [--search] [--limit]`, `graph path --source-id ID --target-id ID` (both required), `graph stats`. Typer enforces the same bounds as the API (`--depth` min 1, with the server capping it at 5; `--limit` 1..1000 in `graph nodes` and `graph query`), so an out-of-range value is exit code 2 with no HTTP request. Filters the user did not set are not sent, so defaults stay on the server. Every response shape is checked before `emit()`: a missing required field or a wrong type is a contract error (`Nieprawidłowa odpowiedź serwera`, exit code 1), never an empty result with exit 0. There are no graph write commands
- `commands/blog.py` (MON-261) - `blog` group over `/api/v2/projects/{slug}/blog/posts*`: `blog list [--status published|draft]` (all pages through `fetch_all`, flat list; an unset filter is not sent; the table format shows only `title`, `slug`, `is_public`, `lang`, `published_at` and `tags` joined with `, `, while json, yaml and csv carry every field), `blog get <page_id>` (metadata, public URLs and markdown content) and `blog meta <page_id> [--slug] [--description] [--author] [--tag ...] [--no-tags] [--lang] [--translation-of] [--cover] [--verified]` (PATCH with only the given options; `--author` is sent as `author_name`, `--tag` is repeatable and replaces the tags, `--no-tags` sends `"tags": []`, and an empty string for `--translation-of`, `--cover` or `--verified` sends `null` and clears the field). `blog meta` without any option, or with `--tag` and `--no-tags` together, is exit code 2 with no HTTP request. Every response shape is checked before `emit()` (`page_id`, `title`, `slug`, `is_public`, a `tags` list, the `public_url` and `markdown_url` keys, plus `content` in `blog get`): a contract error is `Nieprawidłowa odpowiedź serwera`, exit code 1. Post content and publishing stay in `monolynx wiki`
- Command help texts are in Polish; tests in `cli/tests/`

**Schemas** (`schemas/`) — Pydantic models for validation: `events.py`, `issues.py`, `scrum.py`, `time_tracking.py` (includes `WorkReportResult` for aggregated reports), `graph.py` (GraphNodeCreate/Update/Response, GraphEdgeCreate/Response, GraphSearchResult), `wiki.py` (`WikiBacklinkResponse`), `pipelines.py` (list-item and full-tree response builders for the live JSON API: `build_list_item`, `build_pipeline_response`); `schemas/api_v2/` — API v2 request/response schemas: `pagination.py` (`PaginatedResponse[T]` using PEP 695 generic syntax: generic envelope `{"items", "page", "per_page", "total", "total_pages"}`) plus per-resource modules `project.py`, `ticket.py`, `sprint.py`, `wiki.py` (MON-142), `graph.py` (MON-248, response-only: `GraphNodeResponse`, `GraphEdgeResponse`, `GraphSubgraphResponse`, `GraphNodeDetailResponse`, `GraphStatsResponse`) and `blog.py` (MON-261: `BlogPostResponse`, `BlogPostDetailResponse`, `BlogPostMetaUpdateRequest`)

**Data flow**: Django error → SDK middleware `process_exception()` → background thread POST → FastAPI ingests → fingerprint → find/create Issue → store Event (JSONB)

## Key technical decisions

- All DB columns storing error data use PostgreSQL JSONB (exception, request_data, environment)
- Issue grouping: `UniqueConstraint("project_id", "fingerprint")` — fingerprint ignores line numbers for stability
- `event_count` is denormalized on Issue to avoid COUNT(*) queries
- UUID primary keys everywhere (no auto-increment)
- Session middleware from Starlette (cookie-based, signed with SECRET_KEY)
- Alembic configured for async via `asyncio.run()` in `env.py`
- Slug validation: `^[a-z0-9]+(?:-[a-z0-9]+)*$`
- Project deletion is soft delete (`is_active = False`), filtered in all dashboard queries
- After `db.rollback()` in views, always re-query objects before passing them to Jinja2 templates (avoids MissingGreenlet from lazy loading in sync rendering)
- User invitation flow: superuser creates user → `invitation_token` (UUID4) + 7-day expiry → optional email with link → user sets password via `/auth/accept-invite/{token}` → token cleared
- `is_superuser` flag stored in session at login for navbar visibility (`request.session.get('is_superuser')` in templates); users with `password_hash=None` cannot log in
- SMTP configuration optional (`SMTP_HOST=""` disables email); `APP_URL` used for building invitation links
- Pagination pattern: query param `page` (int, default=1), fixed `per_page`; count total with `func.count()`, then LIMIT/OFFSET; pass `page`, `total_pages`, `has_next`, `has_prev` to template
- Lists default to hiding completed/closed items (completed sprints, tickets from completed sprints); toggle via query params (`status=all`, `show_completed_sprints=1`)
- Flash messages via `flash(request, message, type)` stored in `request.session["_flash_messages"]`
- MCP tokens use `osk_` prefix with SHA256 hash stored in DB; raw token shown only once at creation
- Database name is `open_sentry` (historical, kept for backwards compatibility)
- Time tracking entries have a status workflow: draft → submitted → approved/rejected
- PDF reports generated server-side with weasyprint
- Wiki content stored in MinIO (markdown files), metadata in PostgreSQL; `minio_path` column links to object storage
- Wiki RAG search uses pgvector extension (HNSW index, cosine similarity); chunked embeddings (~500 tokens per chunk with overlap) via OpenAI `text-embedding-3-small`; `OPENAI_API_KEY=""` disables embeddings gracefully
- LLM Wiki method (Karpathy-style): opt-in per project via `Project.wiki_llm_enabled` (bool, default False); gated like `embeddings.is_enabled()` - when OFF the tools/skills return a clear no-op/ValueError. Treats the wiki as a growing artifact (vs RAG from scratch) curated through INGEST/QUERY/LINT operations. Reserved system-page slugs `wiki-index`, `wiki-log`, `wiki-schema` (prefix `wiki-`, since `SLUG_PATTERN` forbids underscores); the schema is itself an editable page seeded from `DEFAULT_WIKI_SCHEMA`. Backlinks are stored in PostgreSQL via the `WikiBacklink` model (NOT in Neo4j - Neo4j stays exclusively for the Connections/code module); backfill via `make backfill-backlinks`. Contradictions are flagged inline with the marker `> **Sprzeczność [date]:**`
- Markdown rendering shared via `render_markdown_html()` from `services/wiki.py` — used in wiki pages, ticket descriptions, and comments; frontend uses Tailwind `prose prose-invert` classes
- Public blog (MON-254): post metadata lives in `blog_posts`, 1:1 with `wiki_pages` (`page_id` is both the primary key and the foreign key, `ON DELETE CASCADE`); `models/wiki_page.py` has no relationship to it, queries join explicitly. `WikiPage.is_public` stays the only exposure switch: a `BlogPost` row alone publishes nothing. The post slug is set once, when the row is created (at first publication, or at the first `set_post_meta` on a page that is not public yet), copied from the wiki slug, and from then on is independent of the page title and of the wiki slug; it is unique globally (`uq_blog_posts_slug`), not per project, and an explicit change keeps the old value in `previous_slugs`, which `/blog/{slug}` answers with a 301. Migration `j1e2f3a4b5c6` creates only this table and backfills a row for every already public page (`slug` = page slug, `published_at` = `created_at`, `lang` = `pl`), so addresses that worked before keep working. `/sitemap.xml` (`main.py::sitemap_xml`) lists `/blog/` and one URL per public post taken from `BlogPost.slug`, with `lastmod` from `last_verified_at`, then `published_at`, then the page's `updated_at`
- EasyMDE (WYSIWYG markdown editor) used in wiki page forms and ticket create/edit forms; dark theme via inline CSS overrides
- Docker uses `pgvector/pgvector:pg16` image for PostgreSQL with vector extension support
- Neo4j graph database for Connections module; node types: File, Class, Method, Function, Const, Module; edge types: CONTAINS, CALLS, IMPORTS, INHERITS, USES, IMPLEMENTS; data isolated per project via `project_id` property; graceful degradation when `ENABLE_GRAPH_DB=false`
- Cytoscape.js (CDN v3.30.4) for interactive graph visualization; force-directed layout (cose); node/edge coloring by type; filtering via checkboxes; side panel with node details on click
- Work Plan uses a junction model `WorkPlanEntry` (`user_id`, `ticket_id`, `scheduled_date`) with `UniqueConstraint(user_id, ticket_id, scheduled_date)`; enables per-user cross-project scheduling independent of sprint assignment; the cross-project list returns only entries owned by the current user from projects where they have membership (no cross-project data leak), re-checked on every read, so entries survive a membership loss or soft delete in the database but stay hidden; the MCP key resolver reports `Ticket nie istnieje` without echoing the key; frappe-gantt renders the Gantt view, calendar mode is a custom monthly grid
- Pipelines model AI agent work as observability (not execution): hierarchy `Pipeline -> PipelineStep -> PipelineJob` in PostgreSQL (not Neo4j). `pipeline_type` is `ticket_work` (steps `research`, `coding`, `wrap-up`) or `sprint_close` (steps `wiki-update`, `wrap-up`; driven by the `/monolynx:sprint-end` skill) - both implemented, step lists in `constants.py` (`PIPELINE_TICKET_WORK_STEPS` / `PIPELINE_SPRINT_CLOSE_STEPS`), validation and seeding in `services/pipelines.py`. Durations are not stored - computed on the fly (`finished_at - started_at`, or `now() - started_at` for running, with a JS timer ticking between 15s polls). Status propagates upward in the service: a failed job -> failed step -> failed pipeline. `is_stale()` flags pipelines stuck in `running` >6h, computed at read time (no cron)
- Pipeline job logs are stored as wiki pages under the `pipeline-logi` parent (content in MinIO, metadata in PostgreSQL), linked via `PipelineJob.wiki_page_id`. These pages set `WikiPage.exclude_from_embeddings=True` so the high volume of agent logs (roughly 6-8 pages per ticket) does not pollute RAG `search_wiki` results. When LLM Wiki is enabled, finishing a pipeline appends a `wiki-log` entry. Skills report to pipelines best-effort: a pipeline MCP error never fails the ticket work (pipelines are observability, not a gate). Every pipeline write MCP tool must `await db.commit()` (MON-71 regression)
- Landing page content lives in `src/monolynx/features.py` (Python builders `_feature_<module>(lang)` returning `features[]`, `steps[]`, `mcp_tools[]`, `tech_details[]` per module, PL + EN), rendered to `/features/<slug>` by `main.py`; the template only renders. Any new MCP tool / module / user-visible feature must be added to `features.py` in BOTH languages (and the `ai_intro` "N MCP tools" counter kept in sync) as part of the same change — see `.claude/rules/landing-page-features.md`
- MCP / API v2 / CLI parity: one shared service layer (`services/`), two frontends over it (MCP tools and API v2 endpoints) plus the CLI on top of v2. A new or changed MCP tool comes with its v2 endpoint and CLI command in the same ticket, or with an explicit entry and reason in `INTENTIONALLY_UNMAPPED` (`tests/integration/tool_endpoint_map.py`); `tests/integration/test_api_v2_parity.py` enforces that every tool is in the map, but not that the CLI command or its `cli/README.md` description exists. See `.claude/rules/mcp-cli-parity.md`
- RBAC is enforced in all three channels with one source of truth, `check_permission()` in `services/permissions.py` (MON-241): the dashboard calls `require_permission()` from that module (`HTTPException(403)`), services and MCP tools call `ensure_permission()` (`ValueError("Brak uprawnienia {module}:{action}")`, returned as MCP error text), and API v2 turns that `ValueError` into 403 problem+json via `service_error()` or calls its own `require_permission()` from `api/v2/common.py` where the service takes no user. Project membership alone no longer grants access to the Scrum, Wiki, 500ki, Monitoring, Heartbeat, Connections or Pipelines modules, or to `get_activity_log`, through a token. The default `member` role has `scrum` and `wiki` `read` + `write` but neither `scrum:delete` nor `wiki:delete` (`DEFAULT_ROLE_PERMISSIONS` in `constants.py`), so a token with that role cannot delete tickets, acceptance criteria or wiki pages; `owner` and `admin` keep full access to both modules. Since MON-242 the 500ki, monitoring, heartbeat, graph and pipelines MCP tools and `get_activity_log` check the role permission through `_require()` in `mcp_server.py` (a thin wrapper over `ensure_permission()`; mapping in the MCP Server section)

## Test patterns

- `conftest.py` creates real async SQLAlchemy engine (`scope="session"`, `loop_scope="session"`), wraps each test in a connection-level transaction with rollback
- Test database is per pytest run (MON-250), so parallel runs (e.g. sprint sessions in separate git worktrees) never share tables; before, every run used one `open_sentry_test` database and the `drop_all` at the end of one run removed the tables of another. The `engine` fixture creates its own database `open_sentry_test_<8 random hex chars>` (`CREATE DATABASE` + `CREATE EXTENSION IF NOT EXISTS vector` + `Base.metadata.create_all`) and drops it at session end (`DROP DATABASE ... WITH (FORCE)` after `engine.dispose()`); there is no `drop_all` on a shared database any more
- `TEST_DATABASE_NAME` overrides the name (e.g. `-e TEST_DATABASE_NAME=open_sentry_test_MON-250`). It is validated by `validate_test_db_name()` from `src/monolynx/cli.py`: it must start with `open_sentry_test_`, followed only by letters, digits, `_` and `-`, max 63 characters, otherwise `ValueError` at session start. The forced prefix keeps the dev database (`open_sentry`) from being dropped. An existing database with that name (left by an interrupted run) is dropped before creation; two concurrent runs with the SAME manual name still collide
- `make prune-test-dbs` (`python -m monolynx.cli prune-test-dbs`) removes leftovers of interrupted runs: `open_sentry_test_*` databases with no active connections (databases of runs in progress are skipped, no `FORCE`); the old shared `open_sentry_test` database without a suffix is left alone. `make test` and the CI `clean-code` job run with unchanged commands
- `client` fixture uses `httpx.AsyncClient` with `ASGITransport` and dependency overrides for `get_db`
- `login_session(client, db_session, email=...)` helper creates a User and logs in — each test uses a unique email to avoid conflicts
- Markers: `@pytest.mark.unit`, `@pytest.mark.integration`, `@pytest.mark.e2e`
- pytest-asyncio in auto mode with `asyncio_default_fixture_loop_scope = "session"` and `asyncio_default_test_loop_scope = "session"` in pyproject.toml

## Infrastructure

- **Docker**: Multi-stage Dockerfile (builder → dev → runtime). Dev target has hot reload, runtime uses non-root user with 2 workers
- **Docker Compose (dev)**: `dev` profile with PostgreSQL 16 (pgvector/pgvector:pg16) + Neo4j 5 (neo4j:5-community) + MinIO + app (monitor loop runs in-process by default). Optional `worker` profile runs monitor loop as separate service (`make worker`)
- **Docker Compose (prod)**: `app` service with `ENABLE_MONITOR_LOOP=false` + separate `worker` service running `python -m monolynx.worker`. Worker has no ports/Traefik — only DB access. Advisory lock ensures only one worker runs checks at a time
- **CI**: `.gitlab-ci.yml` — lint → test (coverage goal 50%) → build (main only) → deploy (manual)
- **Pre-commit**: ruff (check + format) and mypy with pydantic plugin

## Merge requests: pipeline must be green

Every MR is followed to the end, never fire-and-forget. After `glab mr create` (or any push to an MR branch):
1. Monitor the branch pipeline until it reaches a terminal state (`glab ci status --branch <branch>` / `glab ci get --pipeline-id <id> -F json`; poll in the background, roughly every 60s; a full `clean-code` round takes 15-20 min).
2. Merge only when the pipeline is `success`. Red pipeline: read the failing job trace (`glab ci trace <job_id>`), fix the cause on the branch, push, monitor again. `exit status 137` in `clean-code` with no failed test means the test container was SIGKILLed: before MON-175 a concurrent `clean-code` job on the same runner ran `docker rm -f db test-runner` on fixed container names and killed the other job's containers; since MON-175 the job has `resource_group: clean-code` and per-job names (`db-$CI_JOB_ID`, `test-runner-$CI_JOB_ID`, `test-net-$CI_JOB_ID`). If 137 still appears, retry the job (`glab ci retry <job_id>`) and check runner memory; it is not a code failure.
3. After merge, monitor the pipeline on `main` the same way. `deploy-staging` is a manual job and stays `manual`; every other job must be `success`. Retry on 137, fix forward on a real failure.
4. Report the outcome with pipeline ids and job statuses. A ticket goes to `done` only after the `main` pipeline is green.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
